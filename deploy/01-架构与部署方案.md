# Dify 内网私有化部署方案（不使用 Docker）

> 文档编号：DEPLOY-001 ｜ 目标版本：Dify 社区版 **1.17.1** ｜ 目标平台：内网 VM（x86_64，Linux）
> 编写时间：2026-09-21 ｜ 配套文档：`02-VM部署手册.md`、`03-配置填写清单.md`、`04-验收与排障.md`

---

## 0. 一句话结论

用官方的**源码 + 官方镜像里已编译好的产物**，在 VM 上以 **systemd 托管的一堆原生进程**跑起完整 Dify，
全程不安装 Docker；所有依赖预先在联网的 Windows 构建机上打好离线包，用 U 盘摆渡进内网。

---

## 1. 硬性前提：目标机必须是 glibc ≥ 2.28

这是本次部署**最重要的一条结论**，它决定了 VM 能不能用。

Dify 1.17.1 的 Python 依赖里包含 `onnxruntime==1.23.2`（文档解析能力所需），
该包**不提供 manylinux_2_17 的 wheel**，最低只到 `manylinux_2_27 / manylinux_2_28`。

| 目标系统 | glibc | 能否部署 |
| --- | --- | --- |
| CentOS 7 | 2.17 | ❌ **不行**（依赖里存在必须 glibc ≥ 2.27 的二进制包） |
| RHEL 8 / Rocky 8 / Alma 8 | 2.28 | ✅ 可以 |
| openEuler 20.03 LTS | 2.28 | ✅ 可以 |
| openEuler 22.03 LTS / 24.03 LTS | 2.34 / 2.38 | ✅ 推荐 |
| 麒麟 Kylin V10 SP1+ / 统信 UOS 20 | 2.28+ | ✅ 可以 |

> 所以：**如果 VM 装的是 CentOS 7，请先换系统**（重装 openEuler 22.03 或 Rocky 8 最省事），
> 否则后面所有工作都会卡在二进制兼容上。VM 上执行 `ldd --version` 可确认 glibc 版本。

## 2. 为什么不用官方 Docker 镜像直接跑

官方镜像是按"容器内跑"设计的，直接解包到宿主机跑会遇到三类问题：

| 官方镜像 | 基础系统 | 直接复用的结论 |
| --- | --- | --- |
| `dify-api:1.17.1` | Debian 12 (glibc 2.36) | ❌ 不能复用。改为用便携 Python + manylinux_2_28 依赖树自建 |
| `dify-web:1.17.1` | **Alpine (musl)** | ✅ **可以整棵复用**：node 是 musl 构建，不依赖 glibc，任何发行版都能跑 |
| `dify-sandbox:0.2.15` | Debian 13 (glibc 2.41) | ❌ 不能复用，且它依赖 libseccomp（CGO），改为在 VM 上用便携工具链自编译 |
| `dify-plugin-daemon:0.6.10-local` | Ubuntu 24.04 (glibc 2.39) | ❌ 不能复用，但它是**纯 Go、无 CGO**，直接交叉编译出静态二进制即可 |

其中 **dify-web 的复用是本方案的关键省力点**：官方镜像里已经包含了
`node`（musl 版，125MB）、musl 动态加载器、`libstdc++/libgcc_s`，以及构建好的 Next.js standalone 产物。
把它整体搬到 VM 上，用 musl 加载器显式启动即可，**完全绕开 glibc 兼容问题**。

## 3. 最终组件清单

VM 上最终运行 8 个常驻服务，全部由 systemd 管理：

| # | 服务 | 端口 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | PostgreSQL 16 + pgvector | 5432 | 源码编译（VM 上） | 主库 `dify` + 插件库 `dify_plugin`；向量库用 pgvector，不额外装向量数据库 |
| 2 | Redis 7 | 6379 | 源码编译（VM 上） | 缓存 + Celery 消息队列 |
| 3 | dify-api | 5001 | 自建（便携 Python 3.12 + 离线依赖树） | 控制台 API、Service API、WebSocket 合并为一个进程 |
| 4 | dify-worker | — | 同上 | Celery 异步任务（知识库索引、工作流执行等） |
| 5 | dify-worker-beat | — | 同上 | Celery 定时任务 |
| 6 | dify-web | 3000 | **官方镜像产物**（musl node + Next.js） | 前端控制台与 WebApp |
| 7 | dify-sandbox | 8194 | 源码编译（VM 上，Go + zig） | 代码节点沙箱，评分/标注工作流的代码节点靠它执行 |
| 8 | dify-plugin-daemon | 5002 | **交叉编译静态二进制** | 插件守护进程，模型供应商全部以插件形式存在，必须运行 |
| 9 | nginx | 80 | 系统包或源码 | 反向代理，按官方路由规则转发 |

### 明确"不部署"的组件（以及为什么可以省）

| 官方服务 | 为什么不装 | 影响 |
| --- | --- | --- |
| `agent_backend` + `local_sandbox` | 仅 Dify 1.17 新增的 Agent v2 功能需要，前端默认关闭 | 不含 Agent 节点的工作流完全不受影响；设置 `AGENT_BACKEND_USE_FAKE=true` 可避免误建 Agent 节点时报错 |
| `ssrf_proxy`（squid） | 内网无可访问的外部 URL，SSRF 防护意义有限 | 把 `SSRF_PROXY_*` 留空即可 |
| `api_websocket`（独立进程） | 与 api 是同一镜像，仅 worker class 不同 | api 进程直接用 `GeventWebSocketWorker`，同时承担 websocket |
| `certbot` | 内网无公网域名 | 需要 HTTPS 时用自签证书 |
| 其余 20+ 向量数据库容器 | 用 pgvector 复用 PostgreSQL | 无 |

## 4. 目录与端口规划

```
/opt/dify/                    安装目录
├─ api/                       Dify api 源码（含 .env）
├─ api-python/                便携 Python 3.12 运行时 + 依赖树
├─ web/                       前端（node + musl 运行库 + Next.js 产物）
├─ sandbox/                   代码沙箱（二进制 + 配置 + Python 运行时）
├─ plugin-daemon/             插件守护进程（二进制 + 配置）
└─ nginx/                     nginx 配置

/data/dify/                   数据目录（建议独立磁盘）
├─ postgres/                  PostgreSQL 数据
├─ redis/                     Redis 数据
├─ storage/                   上传文件、知识库文件（对应官方 volumes/app/storage）
├─ plugin-storage/            插件安装目录与包缓存
└─ logs/                      各服务日志
```

对外只暴露 **80**（nginx）；5001/5002/3000/8194/5432/6379 全部只监听 127.0.0.1。

## 6. 部署流程总览

1. **联网构建机**（当前这台 Windows）跑 `build\build-all.ps1` 生成上述离线包；
2. U 盘拷进内网，解包到 VM 的 `/opt/dify-bundle`；
3. VM 上编辑 `config/dify.env`（只需填网关地址、密钥、模型名等，见 `03-配置填写清单.md`）；
4. 执行 `sudo bash install.sh`（自动建用户、编译数据库、装依赖、写 systemd、启动、自检）；
5. 浏览器打开 `http://VM的IP` → 设置管理员 → 安装模型插件 → 导入三个 DSL → 建知识库。

---

## 7. 关键取舍说明

- **为什么 PostgreSQL 要在 VM 上编译**：官方二进制和 Debian 包都绑定各自发行版的 glibc；
  从源码编译可保证与本机 glibc 完全匹配，代价是安装时多花约 5 分钟。
- **为什么 sandbox 也要在 VM 上编译**：它依赖 libseccomp 且用到 CGO，
  固件里没有预编译产物；随包携带便携 Go 与 zig 编译器，在 VM 上本地编译可彻底规避 glibc 问题。
- **为什么 api 依赖用"整棵依赖树"而不是 wheel 仓库**：目标机无需 pip、无需解析依赖，
  解包即用；版本与构建机完全一致，避免内网解析行为差异。

## 8. 待确认事项

| # | 事项 | 影响 |
| --- | --- | --- |
| 1 | VM 实际发行版与 glibc 版本（`ldd --version`） | 决定能否部署（必须 ≥ 2.28） |
