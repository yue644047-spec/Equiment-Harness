## 1. 文档说明

### 1.1 目的

系统目前只有两类入口：Dify 后台的画布调试，以及本地命令行的评测服务。
保障人员（资料员、操作手、维修人员、技术军官/教员）**没有可用的日常入口**。

本文回答三个问题：

1. 用 Dify 做 Web 界面有哪几条路，各自的能力边界与代价是什么；
2. 在内网、多用户、日常使用的场景下，哪些做法**不可接受**，为什么；
3. 推荐路线、落地顺序、工作量与验收判据。

### 1.2 读者对象

| 角色 | 关注章节 |
| --- | --- |
| 项目负责人 | 5 对比表、7 推荐路线、8 工作量、10 风险 |
| 开发人员 | 3 硬约束、4 路径详解、6 关键设计、附录 A/B |
| 资料管理员 | 6.2 用户标识、6.3 密级、6.7 看板 |
| 技术军官（教员） | 6.5 引用来源展示、6.6 安全警示展示、6.7 五级评价 |

### 1.3 术语

| 术语 | 含义 |
| --- | --- |
| WebApp | Dify 应用发布后由 Dify 自带的前端页面，形如 `https://<dify>/chat/<token>` |
| Service API | 应用发布后对外提供的 `/v1/*` 接口，用 `app-xxx` 密钥鉴权 |
| BFF | Backend for Frontend，为前端服务的薄后端，持有密钥并代理 Dify |
| SSE | Server-Sent Events，Dify 流式输出（`response_mode=streaming`）使用的协议 |
| 回执通道 | 前端把评价编码为 `#评价 N 建议` 消息发回会话，由 Chatflow 生成 `[[EVAL_RECEIPT]]` |

## 2. 需求与约束

### 2.1 使用侧需求

| # | 需求 | 来源 |
| --- | --- | --- |
| N1 | 保障人员在浏览器里提问并得到基于装备技术资料的答案 | 课题「知识获取平台化」 |
| N2 | 答案必须展示**引用来源**（资料编号 + 版本号 + 命中片段） | 装备资料的可追溯要求 |
| N3 | 涉及操作/维修/应急处置的回答，**安全警示与禁止事项必须醒目可见** | 装备域安全要求 |
| N4 | 用户能对回答作**五级评价**并留下改进建议 | 课题「基于用户实际使用效果的评价」 |
| N5 | 资料管理员与技术军官能看到评价看板与待办（badcase 工单、版本清理清单） | 闭环 SOP 第二章角色职责 |
| N6 | 多轮追问（同一会话内上下文连续） | 排故场景常见「那如果……呢」 |

### 2.2 部署侧约束

| # | 约束 | 影响 |
| --- | --- | --- |
| C1 | 部署在**单位内网**，不外联 | 不能依赖 Dify 云版；前端资源须本地可达 |
| C2 | 使用者是**多名保障人员**，不是单人 | 必须区分用户身份，且会话不能互相串 |
| C3 | 资料密级为**内部** | 会话内容、检索片段属于受控信息，需要有边界与留存策略 |
| C4 | Dify 的 Service API Key 是**高权限凭据** | 绝不能下发到浏览器 |
| C5 | 现有评价闭环（collect → judge → report → badcase → 回归）**不能被破坏** | 界面方案必须与该链路兼容 |
| C6 | 现有工程是**零依赖、Windows 可直接跑**的风格 | 引入 npm/前端构建会显著提高运维成本 |

## 3. 三条硬约束（先于方案选择）

这三条不是偏好，是排除条件。任何违反其中一条的方案都应直接否决。

### 3.1 硬约束一：API Key 不得进入浏览器

Dify 的 Service API 用 `app-xxx` 密钥鉴权，该密钥能读取应用的全部会话与消息。
若前端直连 `POST /v1/chat-messages`，密钥必须写在 JavaScript 里，
**任何一个用户按 F12 就能拿到它，进而读取所有人的会话记录**。

**结论**：任何自建界面都必须有一个**持有密钥的服务端**做代理。
"纯静态页面直连 Dify"这一选项在本项目中被直接排除。

> 附带收益：这个服务端同时可以承担认证、评价落库、看板查询三件事，
> 因此方案 B 与方案 C 的差别主要在前端复杂度，而不在"有没有后端"。

### 3.2 硬约束二：问答必须经过 Dify 的会话通道

`eval_service` 的采集链路是从 Dify 侧拉数据的（`collector.py` 调 `iter_conversations(user=...)`）。
评价工作流要判 `factual_accuracy`、`retrieval_quality`，**必须拿到当时的检索片段**
（`retriever_resources`）。

若界面自己存问答、不走 Dify：

- 拿不到 `retriever_resources` → 检索维度和事实性判定失去依据；
- 拿不到会话与消息 ID → `feedback`、回执无法关联；
- `collect` 拉不到数据 → 报表、badcase、回归全部空转。

**结论**：界面可以是自建的，但**问答本身必须走 Dify 的 `/v1/chat-messages`**，
并传统一的 `user` 标识。这样会话照旧进 Dify，现有闭环完全不受影响。

### 3.3 硬约束三：五级评分不能只靠 Dify 原生反馈

Dify 原生反馈只有 `like`/`dislike`，经 `metrics.normalize_user_score` 映射为 5 / 1，
**2、3、4 分的粒度完全丢失**。
而 `user_score` 在 CSI 中权重为 **0.30**，且 `dislike` 会触发降级规则——
只剩两个取值的用户分，会显著削弱评价的区分度。

**结论**：五级评分必须走**回执通道**（`#评价 N 建议`）或自建评价接口，二选一，见 6.7。

## 4. 三条路径详解

### 4.1 路径 A：Dify 自带 WebApp

**形态**：01 应用 → 发布 → 开启 WebApp 渠道 → 得到访问链接，可直接分发或 iframe 嵌入内网门户。

**能力**

| 具备 | 说明 |
| --- | --- |
| 开场白与建议问题 | DSL 中已配置装备域开场白与 4 条建议问题 |
| 会话历史与多轮 | Dify 原生维护，满足 N6 |
| 👍 / 👎 | 写入 `feedback`，`collector` 可直接采集 |
| 引用来源 | DSL 中 `retriever_resource.enabled = true`，WebApp 会展示引用 |
| 响应式布局 | 手机/平板可用，适合保障现场 |
| 嵌入网站 | Dify 提供 iframe 与脚本两种嵌入方式 |

**缺口**

| 缺口 | 后果 |
| --- | --- |
| 界面不可定制 | 无法做资料编号/版本卡片、安全警示块、失效值红条（N2/N3 不达标） |
| 只有二元反馈 | N4 不达标，见 3.3 |
| 无评价看板 | N5 不达标 |
| 访问控制弱 | 拿到链接即可访问；内网虽物理隔离，但内部人员越权可见受控内容（C3 有风险） |
| 品牌与场景感弱 | 不利于课题演示与推广 |

**工作量**：0.5 天（发布、渠道配置、试用话术、访问控制确认）。

**适用**：试运行期快速收数据；作为自建界面的降级兜底。

### 4.2 路径 B：自建薄后端（BFF）+ 轻量前端

**形态**：一个 Python 标准库写的 BFF + 一套原生 HTML/JS 页面。前端只与 BFF 通信，BFF 持有密钥并代理 Dify。

```
浏览器（原生 HTML/JS）
   │  同源请求，携带会话票据
   ▼
BFF（Python 标准库 http.server，零第三方依赖）
   ├─ 代理 POST /v1/chat-messages ──────► Dify（持 app-xxx 密钥）
   ├─ 代理 POST /v1/messages/{id}/feedbacks
   ├─ 评价落库 ─────────────────────────► SQLite（本地）
   └─ 看板查询（复用 metrics.aggregate）─► SQLite
```

**为什么这个形态合适**

- 满足硬约束一（密钥不出服务端）；
- 满足硬约束二（问答走 Dify）；
- 与现有工程风格一致（`eval_service` 全部是标准库），Windows 上 `python web_service/app.py` 即可运行（C6）；
- **可完全离线演示**：`dify_client.py` 自带 `MockBackend`，无凭据也能把界面跑起来（课题汇报友好）；
- 顺带解决认证问题（见 6.1）。

**能力**：覆盖 N1–N6 全部需求，其中 N2/N3 通过前端渲染实现，N4 通过回执通道实现，N5 通过复用 `metrics.aggregate` 实现。

**代价**：需要自己维护会话列表与多轮上下文（前端存 `conversation_id`）；流式输出需另做（见 6.4）。

**工作量**：3–5 天。

### 4.3 路径 C：自建完整平台

**形态**：在 B 的基础上，扩展为多角色、多模块平台。

| 模块 | 内容 |
| --- | --- |
| 问答 | 同 B |
| 评价工作台 | 技术军官抽检、人工复核、一致率统计 |
| 评价看板 | CSI 趋势、SC/VC/TN 分布、归因分布、badcase 工单 |
| 资料管理 | 资料台账维护、版本换版、`check_corpus` 门禁可视化、入库进度 |
| 账号与权限 | 角色（保障人员 / 资料管理员 / 技术军官 / 管理员）、按密级分级可见 |
| 前端框架 | React 或 Vue + 构建链 |

**代价**：

- 工作量 15–25 天；
- 引入 npm 与构建产物，运维复杂度上升（与 C6 冲突）；
- 需要长期维护，且与 Dify 升级存在耦合风险。

**适用**：已明确为长期生产系统、且有专职前端维护力量时。

> 注意：**C 不是 B 的替代，而是 B 的生长方向**。B 做扎实后，看板只是增加页面与查询接口，
> 不需要重写。因此不建议一开始就上 C。

## 6. 内网部署的关键设计问题

### 6.1 访问控制与认证

内网不等于可信。资料密级为"内部"，且会话里会包含技术参数与安全条款，需要控制可见范围。

| 做法 | 强度 | 说明 |
| --- | --- | --- |
| Dify WebApp 访问控制 | 中 | 视 Dify 版本提供；部署时需确认可用的控制项，并验证生效 |
| Nginx 层 Basic Auth | 中 | 最省事，但凭据共享、无法区分个人 |
| BFF 自建登录（口令 + 会话 Cookie） | 较高 | 可区分个人，便于与 `user` 标识绑定 |
| 对接单位统一认证（SSO/LDAP） | 高 | 需要单位侧配合，工作量取决于对接方式 |

**建议**：路径 B 起步用"BFF 自建登录 + 账号表"，账号与工号绑定；后续若单位有统一认证再接。

### 6.2 用户标识规范与脱敏

Dify 用 `user` 字段隔离会话与反馈，`collector` 按该字段拉取。**这是评价链路能否对齐的关键。**

| 规则 | 说明 |
| --- | --- |
| 唯一且稳定 | 用**工号**或其哈希，**不要用随机 UUID**——每次刷新都变成新用户，会话碎片化，采集与统计全部失真 |
| 全链路一致 | 前端传给 BFF、BFF 传给 Dify、`collect` 的 `user` 参数三者必须一致；落库后体现为 `conversations.from_end_user_id`，可用于核对 |
| 进报表前脱敏 | `docs/02` 第 10 章要求：进入报表前剔除或哈希用户标识 |
| 不使用真实姓名 | 会话记录中不出现真实姓名，避免二次扩散 |

**接口一致性检查**：`collector.py` 的 `collect(user=...)` 若按 user 过滤，传错标识会直接导致"采集到 0 条"。

### 6.3 密级与数据留存

| 事项 | 建议 |
| --- | --- |
| Dify 部署位置 | 与资料本体同密级区域，数据库不外联 |
| 会话留存 | 按单位规定设定保留期限；`docs/02` 10.3 已给出留存与清理口径 |
| 备份 | Dify 数据库与 `eval.db` 同策略备份 |
| 导出控制 | 报表（`report.html` / `badcases.csv`）属受控产物，分发需审批 |
| 检索片段 | 回答中的引用片段来自受控资料，界面不应提供"全文下载"入口 |

### 6.4 会话与多轮上下文

Dify 的多轮上下文由其服务端按 `conversation_id` 维护（三个 LLM 节点均配置了 `memory.window.size = 10`）。

- 首次提问：`conversation_id` 传空，从响应中取得并保存；
- 追问：回传该 `conversation_id`；
- BFF 需按"用户 + 会话"存储，避免跨用户串会话。

### 6.5 流式输出

现有 `dify_client.chat_messages()` 是**阻塞模式**（`response_mode="blocking"`），
响应是一次性返回的完整 JSON；它虽然接受 `response_mode` 参数，但客户端没有实现 SSE 解析。

| 选项 | 体验 | 代价 |
| --- | --- | --- |
| 阻塞模式 | 长回答需等待数秒到十余秒，需前端显示加载态 | 零改动 |
| 流式（SSE） | 打字机效果，感知延迟低 | 客户端与 BFF 需新增 SSE 透传 |

**建议**：路径 B 第一版用阻塞模式 + "生成中"状态；装备问答回答较长，若用户反馈等待感明显，再补 SSE。

### 6.6 引用来源与安全警示的展示

这是路径 B 相对路径 A 最直接的价值，也是装备域特色。

| 展示元素 | 数据来源 | 渲染建议 |
| --- | --- | --- |
| 引用资料卡片 | 响应的 `retriever_resources`（含 `content` / `score` / `document_name`） | 卡片列出「资料名称 + 命中片段 + 相关度」，与 `join_contexts()` 的口径一致 |
| 资料编号与版本 | 片段正文开头的 `【HYS-XX-00X Vn.n 条款号】` | 正则提取后渲染为引用标签（见下方说明） |
| 安全警示 | 回答或片段中的【禁止】【警告】 | 独立色块 + 图标，**不并入正文**，避免被阅读时跳过 |
| 版本失效提示 | 命中作废值清单（300 工作小时 / 14 MPa） | 前端即时红条提示，并记录为一次"版本失效"事件 |

> 前端做本地检测只是**预警**，正式判定仍以评价工作流的 `version_currency` 与
> `error_cause = 版本失效` 为准（`docs/01` 第 7.3 节）。

**引用标签可直接从片段解析**：入库语料的每个分段都以资料标识开头，例如实测的检索片段为

```text
【HYS-WX-003 V2.0 3.1.9】滤芯更换周期为每 500 工作小时或 12 个月，以先到为准；……
```

因此前端无需额外元数据，用正则 `【(HYS-[A-Z]{2}-\d{3})\s+(V[\d.]+)\s+([\d.]+)】` 即可
从 `retriever_resources[].content` 中直接抽出**资料编号、版本号、条款号**三项，
渲染成可点击的引用标签。这也正是 `docs/02` 6.2 节要求"资料编号与版本号必须留在段内"的原因——
分块规则与界面展示在这里是同一件事。

### 6.7 五级评价的实现（两种接法）

| | 接法一：回执通道 | 接法二：独立评价接口 |
| --- | --- | --- |
| 做法 | 前端五颗星 + 建议框 → 编码为 `#评价 4 建议原文` 发回**同一会话** → Chatflow 现有三节点生成回执 | 前端 POST 到 BFF → 直接写本地库 |
| 后端改动 | **零** | 需扩展 `collector` 的合并逻辑 |
| 契约风险 | 无 | 有：下次 `collect` 可能从 Dify 覆盖本地分数 |
| 会话影响 | 评价会作为一条消息出现在会话里（前端可特殊渲染，不显示为普通气泡） | 会话干净 |
| 评价原文留痕 | 完整保留（回执内含 suggestion） | 需自行存储 |
| 与现有测试 | 不触发任何断言变化 | 需同步改契约测试与自检 |

**建议**：采用**接法一**。理由是它复用已经过 72 项契约测试保护的通路，
不改动任何既定接口；界面观感问题完全可以在前端用样式解决。

### 6.8 看板数据来源

不要另写统计逻辑。`metrics.aggregate()` 已经产出报表所需的全部聚合：
CSI 均值/中位数/P90、verdict 分布、维度均值、装备域专项维度（SC/VC/TN）、
归因分布、badcase 率、相关性系数。

BFF 只需：

```python
rows = store.fetch_evaluations(period="week")   # 复用现有查询
agg  = metrics.aggregate(rows)                  # 复用现有聚合
return json.dumps(agg, ensure_ascii=False)      # 交给前端渲染
```

这样看板与 `report.py` 的口径**天然一致**，不会出现"页面数字和周报对不上"。

## 7. 推荐路线

### 7.1 结论

**先 A 后 B，暂不上 C。**

| 阶段 | 内容 | 周期 | 出口条件 |
| --- | --- | --- | --- |
| 阶段一 | 路径 A：发布 WebApp，配置渠道与访问控制，发给小范围试用（10–20 人） | 0.5–1 天 | 能收到真实问答与反馈数据；`collect` 能拉到会话 |
| 阶段二 | 路径 B：BFF + 轻量前端，覆盖 N1–N6 | 3–5 天 | 验收清单（第 9 章）全部通过 |
| 阶段三 | 在 B 上生长看板与资料管理视图（即 C 的一部分） | 按需 | 资料管理员与技术军官可自助处理待办 |
| 阶段四 | 若确认为长期生产系统，再考虑账号体系与前端框架化 | 视规划 | — |

### 7.2 为什么先做 A

- 一天内就能拿到**真实使用数据**，而这些数据正是评价体系此刻最缺的
  （`docs/03` 第 8 章：无数据时指标无意义）；
- A 的链接可以作为 B 的**降级兜底**：B 出故障时用户仍有入口；
- A 暴露出的真实问题（用户实际怎么问、哪些问法命中不了、安全类问题占比多少）
  会直接决定 B 的界面该优先做什么。

### 7.3 为什么暂不上 C

- C 的主要增量是账号体系与多模块，而这些在**用户量和使用模式尚未验证前无法定稿**；
- C 引入前端构建链，与现有"零依赖、Windows 直接跑"的运维风格冲突；
- B 的架构与 C 同构（都有 BFF），**迁移成本低**，不存在"选错要推翻"的风险。

## 9. 验收清单

| # | 验收项 | 判定方法 |
| --- | --- | --- |
| 1 | 密钥不出服务端 | 浏览器开发者工具中 Network 与 Sources 全程检索不到 `app-` 前缀字符串 |
| 2 | 问答经 Dify，链路不断 | 界面提问后执行 `python eval_service/cli.py collect`，能拉到该会话与消息，含 `retriever_resources` |
| 3 | 用户标识一致 | 同一账号多次提问归入同一 `user`；`collect(user=...)` 过滤结果与界面会话一致 |
| 4 | 会话隔离 | 不同账号互不可见对方会话；同一账号多轮追问上下文连续 |
| 5 | 引用来源可追溯 | 回答下方展示资料名称、命中片段与相关度；能定位到 `HYS-XX-00X` 与版本号 |
| 6 | 安全警示醒目 | 对"如何更换滤芯"提问，安全前置与禁止事项以独立色块呈现，不被折叠或省略 |
| 7 | 五级评价可用 | 提交 4 分+建议后，`collect` 能解析出 `receipt_score=4` 与建议原文；`judge` 后 `user_score=4` |
| 8 | 评价回执不干扰 | 评价消息在前端不以普通对话气泡呈现；未触发"回执被当作问答评分"（`selftest` 中该断言须仍通过） |
| 9 | 看板口径一致 | 看板展示的 CSI 均值、verdict 分布与 `python eval_service/cli.py report` 输出一致 |
| 10 | 离线可演示 | 断开网络、不配任何密钥，以 `MockBackend` 启动，界面全流程可走通 |
| 11 | 既有门禁不被破坏 | `check_corpus.py`、`validate_dsl.py`、`test_code_nodes.py`、`test_contract.py`、`selftest.py` 五道全部通过 |
| 12 | 访问控制生效 | 未登录访问任意页面被重定向到登录页；直接访问 BFF 接口返回未授权 |

> 第 11 条是硬性卡点：界面层的改动**不得**触碰 DSL 与评测服务的既定契约。
> 路径 B 采用回执通道的意义正在于此。

## 10. 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 前端直连 Dify 导致密钥泄露 | 全员会话可被任意用户读取 | 架构上强制 BFF 代理；验收第 1 条把关 |

| R9 | Dify 升级导致接口变化 | 界面不可用 | BFF 收敛所有 Dify 调用；升级前跑 `check_env.py` 与冒烟清单 |
