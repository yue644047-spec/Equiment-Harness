## 1. 项目概述

### 1.1 课题背景

装备系统技术日益复杂、资料繁多，原理及规程等分散于各类手册、技术文件等资源中，
用户在学习与查询中使用不便捷。同时，随着装备保障信息化程度提高，
现场积累的**图片、视频**类记录（故障现象照片、操作演示视频、检修过程录像）快速增加，
这些非结构化数据长期处于"存而不用"的状态。

传统知识管理方式存在三个突出问题：

1. **多模态数据无法统一管理**。文本资料已进入电子化，但图片、视频仍散落在各自终端与业务系统中，
   缺乏统一的采集、解析、入库与检索手段。
2. **查询方式单一**。资料类知识依赖人工翻阅，台账类数据依赖固定报表，
   用户无法用自然语言同时查询「资料怎么说」与「数据是多少」。
3. **系统无法自我改进**。用户的使用反馈与评价没有被结构化采集，
   知识缺口、版本过期、术语不统一等问题无法被系统识别，回答质量长期停滞。

针对上述问题，本课题研究利用大模型技术进行数据管理、智能查询和基于用户实际使用效果的评价技术，
为**数据管理集中化、知识获取平台化、评价智能化**提供技术支撑。

### 1.2 研究目标

| 序号 | 目标 | 可度量的达成标准 |
| --- | --- | --- |
| 目标一 | 实现文本、图片、视频多模态数据的统一采集、管理和维护 | 三类模态共 7 种格式（pdf/docx/xlsx/jpg/png/mp4/avi）均可上传、解析、入库、检索 |
| 目标二 | 实现基于大模型的智能化查询及问答 | 知识库问答与数据库交互查询两条链路均可用，回答附文档出处 |
| 目标三 | 实现大模型的训练及优化 | 完成 LoRA 微调闭环，微调后黄金集回归无退化 |
| 目标四 | 建立主客观双维度满意度评价体系 | 主观评价 ≥3 个指标、客观评价 ≥3 个指标，评价结果驱动迭代 |

### 1.3 研究内容

本课题主要开展两项研究内容：

**研究内容一：基于大模型的多模数据管理及智能查询技术研究**

研究文本、图片、视频的多模态解析处理方法，采取本地部署搭建涵盖知识库和数据库的 AI 大模型，
实现多模态数据的统一采集和维护。利用大模型的智能分析和逻辑推理能力，
实现基于知识库的智能化检索和基于数据库的交互查询。

**研究内容二：基于用户评测的 AI 大模型迭代优化技术**

完成基于大模型的 AI 知识库训练和数据库标注，设计多维度满意度评价指标及智能问答满意度评价模型，
通过用户满意度评分、改进建议等，评估模型的知识完备性与回答质量。
基于评价结果，利用通用数据完成智能问答程序的迭代升级。

## 3. 总体技术方案

### 3.1 设计原则

1. **本地化优先**：大模型、知识库、数据库、解析引擎全部本地部署，**不出内网、不调用任何云服务**。
2. **不依赖容器**：目标环境明确不使用 Docker，全部组件以原生进程 + 服务管理器方式运行。
3. **能力外挂**：编排平台不具备的能力（OCR、视频处理、NL2SQL、模型微调）以独立服务形式外挂，
   通过标准 HTTP 接口接入，保持平台轻量且可替换。
4. **证据可追溯**：所有回答可回溯到原始资料的具体位置（章节号 / 图像区域 / 视频时间戳）。
5. **闭环可重复**：采集 → 评价 → 归因 → 整改 → 回归的每个环节都可脚本化重复执行。

### 3.2 总体架构

系统采用**五层架构**，自上而下依次为：接入层、编排层、能力层、数据层、平台层。

### 3.3 技术选型与理由

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 应用编排 | Dify 1.17.1（社区版） | 开源可私有化；工作流编排能力完整；原生支持知识库检索、代码节点、HTTP 节点、视觉模型 |
| 向量数据库 | pgvector（PostgreSQL 扩展） | 复用业务库，不引入独立向量库，降低离线部署与运维成本 |
| 关系数据库 | PostgreSQL 16.15 | 与 pgvector 同源；离线可源码编译，与目标机 glibc 完全匹配 |
| 缓存 / 队列 | Redis 8 | 平台强依赖；轻量、离线可编译 |
| 大模型 | 本地部署（OpenAI 兼容接口） | 满足"本地部署"要求；接口标准化，平台侧通过模型插件接入，更换模型无需改动工作流 |
| 视觉模型 | 本地部署视觉语言模型 | 图片理解、扫描件识别、视频关键帧理解 |
| 嵌入 / 重排 | 本地部署 | 知识库索引与检索质量的关键 |
| 文档解析 | 平台内置解析器 + 自研解析服务 | 文本类走原生，扫描件与图片视频走自研 |
| 语音识别 | 本地部署语音转文本模型 | 视频语音转写、语音输入 |

### 3.4 核心数据流

**采集流（数据入库）**

```
资料 / 图片 / 视频
   → 上传 → 按模态分派解析引擎
   → 归一化（正文 + 模态标记 + 定位锚点 + 版本元数据）
   → 分段 / 嵌入 → 写入 pgvector
   → 记录知识库文档台账（内容哈希、分段数、状态）
```

**查询流（用户提问）**

```
用户提问（可带图片 / 视频）
   → 意图识别
   ├─ 知识库：向量检索 → 重排 → 拼接上下文 → 大模型作答 → 回填出处 → 回答
   ├─ 数据库：NL2SQL → 安全校验 → 只读执行 → 结果转述 → 回答
   └─ 多模态：解析服务 → 结构化文本 → 大模型作答 → 回答
```

**迭代流（闭环优化）**

```
用户评价（主观3项 + 建议）/ 点赞点踩
   → 采集 → 大模型评委（客观6项）→ SSI / OSI / CSI → 落库
   → 聚合报表 → badcase 挖掘 → 知识补全清单 / 提示词优化建议
   → 标注产出训练数据 → LoRA 微调 → 黄金集回归
   → 达标上线 / 不达标回退
```

## 4. 分系统设计

### 4.1 多模态数据接入与解析子系统

#### 4.1.1 设计目标

把三类异构模态统一成同一套可入库、可检索、可溯源的中间表示。

#### 4.1.2 统一中间表示

每条入库数据都携带四个要素：

| 要素 | 说明 | 用途 |
| --- | --- | --- |
| 正文（content） | 归一化后的文本 | 分段与向量化 |
| 模态标记（modality） | text / image / video | 统计各模态覆盖情况，支持按模态筛选 |
| 定位锚点（anchor） | 章节号 / 图像区域 / 视频时间戳 | 回答中回填出处 |
| 版本元数据（version） | 资料编号、版本号、生效状态 | 版本时效性判定与作废版本拦截 |

#### 4.1.3 三类模态的解析路径

**文本类（pdf / docx / xlsx）**

- pdf：平台内置解析器提取文本层与表格结构；若检测到文本层为空（扫描件），
  自动转入图片型 PDF 分支走 OCR。
- docx：按段落与表格结构提取，保留标题层级作为章节锚点。
- xlsx：按工作表与表头提取，每个数据行转为「字段名：取值」的文本行，保留工作表名与行号作为锚点。

**图片类（jpg / png / 图片型 pdf）**

- 第一步 OCR：识别画面中的文字（铭牌、标签、仪表读数、编号），保留文字在原图中的位置区域。
- 第二步视觉理解：由视觉大模型生成画面语义描述（这是什么设备、处于什么状态、有哪些可见部件）。
- 第三步融合：OCR 文字 + 语义描述合成正文，区域描述作为定位锚点。

**视频类（mp4 / avi）**

```
视频文件
  → [avi 前置转码为 mp4]
  → ffmpeg 抽帧（按固定间隔初筛）
  → 关键帧检测（画面变化幅度超过阈值，去冗余）
  → 音轨分离 → 语音识别 → 带标点的转写文本（含时间戳）
  → 关键帧视觉理解 → 每帧的画面描述（含时间戳）
  → 时间轴对齐融合
  → 输出：时间戳 + 画面描述 + 同期台词
```

关键设计：**采用关键帧而非逐帧理解**。一次 10 分钟视频若逐帧处理需数千次视觉推理调用，
采用关键帧检测后可降低一个数量级，在保证语义完整的前提下把算力开销控制在可接受范围。

#### 4.1.4 解析质量保障

| 问题 | 处理方式 |
| --- | --- |
| OCR 识别置信度低 | 低于阈值的文字标注为「疑似」，不进入正文，避免污染知识库 |
| 视频画面模糊 | 记录为「该时段画面不清晰，无法识别」，保留时间戳占位 |
| 解析失败 | 进入人工复核队列，由标注工作流标记，不静默丢弃 |
| 大文件超时 | 解析任务异步化，返回任务号，前端轮询进度 |

### 4.2 知识库构建与智能检索子系统

#### 4.2.1 知识库组织

按**业务域 + 资料类型**组织知识库，支持多知识库并存与选择：

| 知识库 | 内容 | 典型用途 |
| --- | --- | --- |
| 技术资料库 | 原理、操作规程、维修规程、故障案例 | 资料问答 |
| 图片资料库 | 故障现象照片、铭牌与仪表照片、结构图 | 看图问答 |
| 视频资料库 | 操作演示、检修过程、故障复现 | 视频问答 |

#### 4.2.2 分段与索引参数

| 参数 | 默认值 | 调节依据 |
| --- | --- | --- |
| 分段模式 | 通用分段 | 装备资料条款密集，需保留条款完整性 |
| 分段长度 | 512 tokens | 过短会切断条款，过长会稀释检索精度 |
| 重合长度 | 50 tokens | 防止跨段条款被截断 |
| 索引方式 | 高质量（向量） | 语义检索需要 |
| 嵌入模型 | 本地部署嵌入模型 | 需与向量维度严格对应 |
| top_k | 6 | 参数与条款密集，召回不足会漏要点 |
| 重排（Rerank） | 启用 | 显著提升参数类问题的命中质量 |
| 相似度阈值 | 启用，按实验标定 | 过滤低相关片段，降低幻觉 |

> 上述参数均可通过平台界面调整，调整后重新检索即可生效，满足「支持知识切片长度、重合长度等参数配置，
> 支持 top_k、阈值等采样控制参数设置」的要求。

#### 4.2.3 检索链路

```
用户问题
  → 查询改写（可选：指代消解、术语归一）
  → 向量召回（top_k 条）
  → 重排（按相关性重排序）
  → 阈值过滤
  → 拼接上下文（含资料编号与版本号）
  → 交给大模型作答
  → 回答中回填出处
```

#### 4.2.4 文档出处显示

回答中的每条关键结论都标注来源，格式为：

```
【出处】HYS-WX-003 V2.0《某型液压举升系统维修规程》第 4.2 节
【出处】故障照片 IMG-20260815-003，画面右侧压力表区域
【出处】操作视频 VID-20260820-001，第 03:15 - 03:42 段
```

出处信息来自入库时写入的定位锚点，检索命中后由平台原样带回，不依赖模型生成，
避免模型编造来源。

### 4.3 数据库交互查询子系统（NL2SQL）

#### 4.3.1 设计目标

让用户用自然语言查询结构化数据，得到带明确统计口径的答案。

#### 4.3.2 服务架构

```
自然语言问题
   → [1] 意图确认：是否需要查库（由编排层分类器完成）
   → [2] Schema 语义层：注入候选表与字段的业务语义描述（非完整 DDL）
   → [3] SQL 生成：大模型生成候选 SQL
   → [4] 安全校验：语法解析 → 白名单 → 只读断言 → 行数上限
   → [5] 执行：只读账号连接业务库
   → [6] 结果处理：脱敏 → 口径说明生成
   → [7] 返回：{ok, data, row_count, query_scope, sql_preview}
   → [8] 编排层组织成自然语言回答
```

#### 4.3.3 安全防线

| 防线 | 措施 |
| --- | --- |
| 数据库侧 | 独立**只读账号**，仅授予 SELECT 权限 |
| 表层 | 可查询表**显式白名单**，白名单外的表直接拒绝 |
| 语句层 | 仅允许**单条 SELECT**；拒绝 DDL/DML/多语句/存储过程 |
| 字段层 | 敏感字段（人员信息、联系方式等）在服务层**脱敏**后再返回 |
| 资源层 | 强制 **LIMIT**、查询超时、返回行数上限 |
| 审计层 | 记录每次查询的原始问题、生成 SQL、返回行数，供事后审计 |

#### 4.3.4 统计口径复述

同一问题在不同口径下答案不同，因此服务在返回数据的同时返回**结构化口径说明**：

```json
{
  "ok": true,
  "row_count": 17,
  "query_scope": {
    "tables": ["equipment_ledger"],
    "filters": ["status = '在用'", "next_maintenance_date <= 2026-12-31"],
    "group_by": "org_name",
    "time_range": "未来 3 个月"
  }
}
```

编排层把口径说明组织进回答，用户可据此判断结果是否符合预期。

### 4.4 智能问答与编排子系统

#### 4.4.1 意图识别四路分流

| 类别 | 触发特征 | 处理链路 |
| --- | --- | --- |
| 知识库问答 | 询问原理、参数、规程、故障排除方法 | 知识检索 → 判空 → 作答 / 兜底 |
| 数据库查询 | 询问数量、清单、统计、时间范围等结构化信息 | NL2SQL → 判状态 → 组织回答 / 兜底 |
| 多模态理解 | 上传图片或视频并就画面内容提问 | 解析服务 → 判空 → 基于解析作答 / 视觉模型直读 |
| 满意度评价 | 对上一轮回答打分或提改进建议 | 主观指标提取 → 评价回执 |

每路都设有**兜底分支**，保证任何异常输入都有明确、不编造的回应。

#### 4.4.2 作答纪律

在提示词层面固化了以下纪律，并在验收中逐条检查：

1. 只依据检索片段作答，禁止使用片段之外的信息；
2. 技术参数、力矩、周期、温度、压力、编号、条款号必须与原文完全一致，不得改写或换算；
3. 涉及操作、维修、应急处置的回答，必须完整保留安全警示与禁止事项，不得为简洁而删减；
4. 术语规范，缩略语首次出现给出中文全称；
5. 引用资料必须写明编号与版本号；同一主题多版本时以现行有效版本为准，并提示作废版本不得使用；
6. 检索片段不足时，如实说明「知识库未覆盖」，并指出缺口，绝不编造。

#### 4.4.3 多模态问答的双路径设计

| 路径 | 触发条件 | 能力 |
| --- | --- | --- |
| 解析服务路径（主） | 解析服务正常返回 | 图片与视频均可理解，视频可给时间定位 |
| 视觉模型直读路径（备） | 解析服务不可用 | 图片由视觉模型直接读取；视频提示用户改传关键帧截图 |

双路径保证了解析服务故障时图片问答仍可用，不会整体失效。

### 4.5 满意度评价子系统

#### 4.5.1 评价通道

| 通道 | 采集方式 | 数据落点 | 覆盖信息 |
| --- | --- | --- | --- |
| A：原生反馈 | 回答下方点赞 / 点踩 | 平台反馈表 | 仅极性 |
| B：对话内评价 | 发送「#评价 满意度5 有用性4 体验感4 建议…」 | 回答正文中的回执标记 | 主观 3 项分数 + 改进建议原文 |

通道 B 是本系统的关键设计：用户无需进入独立评价页面，
在对话流中即可完成多维评价，采集成本极低。

#### 4.5.2 评价回执格式

采用键值对而非 JSON，原因是用户建议文本中的引号或换行会破坏 JSON 结构：

```
[[EVAL_RECEIPT]]satisfaction=5,usefulness=4,experience=4,suggestion=希望补充滤芯更换周期说明[[/EVAL_RECEIPT]]
```

> **契约约束**：回执字段名变更必须同步修改评测服务的解析逻辑，
> 该约束由跨文件契约测试强制执行，详见 4.8。

#### 4.5.3 评价计算

由「大模型评委 + 代码节点」两段式完成：

1. **大模型评委**：对一次问答给出客观 6 项评分、标注标签、错误归因与知识缺口判定，
   输出严格 JSON；
2. **代码节点**：解析评委输出，合成主观指数 SSI、客观指数 OSI 与综合满意度指数 CSI，
   执行红线降级与 badcase 分级，输出结构化结果供落库。

### 4.6 迭代优化子系统

#### 4.6.1 闭环七步

| 步 | 环节 | 触发 | 产物 |
| --- | --- | --- | --- |
| ① | 用户问答 | 用户提问 | 会话与消息（含检索片段） |
| ② | 评价采集 | 点赞点踩 / 评价指令 | 主观 3 项 + 改进建议 |
| ③ | 数据拉取 | 定时任务 | 落库的会话与反馈 |
| ④ | 客观评分 | 批量调用评价工作流 | 客观 6 项 + CSI + badcase |
| ⑤ | 指标聚合 | 按周期聚合 | 报表（趋势、分布、归因占比） |
| ⑥ | 归因整改 | 人工 | 知识补全清单、提示词优化建议 |
| ⑦ | 回归验证 | 发布前 | 黄金集回归报告 |

#### 4.6.2 标注产出训练数据

由多模态语料标注工作流完成：语料（文本 / 解析后的图片视频文本）→ 问答对抽取 → 自动打标 →
质检（丢弃空问题、超长条目）→ 输出 jsonl 问答对与人工复核表。

复核后的问答对有三个用途：
1. 回灌知识库，提升检索覆盖；
2. 作为黄金测试集，用于回归验证；
3. 构造指令微调数据，用于模型微调。

#### 4.6.3 微调闭环

```
标注产出（jsonl 问答对）
   → 数据构造：按标签筛选高质量样本 + 混入通用语料防退化
   → LoRA 微调（单卡可完成）
   → 权重合并 → 推理服务部署（OpenAI 兼容接口）
   → 黄金集回归对比：准确率 / CSI / 红线触发率
   → 达标：切换线上模型；不达标：回退并分析原因
   → 新一轮用户评价回流
```

**防退化设计**：训练集中按比例混入通用语料，并设置回归红线
（微调后黄金集不得出现新增 P0、CSI 均值不得低于基线），不达标不允许上线。

#### 4.6.4 达标门槛

| 指标 | 门槛 |
| --- | --- |
| 黄金集回归 | 无新增 P0；CSI 均值不低于基线 |
| 安全合规性 | safety_compliance ≤ 2 的条数为 0 |
| 版本时效性 | version_currency = 1 的占比 ≤ 3% |
| 自动评分可信度 | 人工抽检 30 条，完全一致率 ≥ 70%，相邻一致率 ≥ 95% |

### 4.7 平台与部署子系统

#### 4.7.1 部署形态

目标环境为**完全隔离内网 + 银河麒麟 V10 + 不使用 Docker**，
全部组件以原生进程方式运行，由 systemd 统一托管 8 个服务：

| 服务 | 职责 |
| --- | --- |
| PostgreSQL | 业务库 + 插件库 + 向量库（pgvector） |
| Redis | 缓存与任务队列 |
| API | 控制台 API、服务 API、WebSocket |
| Worker | 异步任务（知识库索引、工作流执行） |
| Beat | 定时任务 |
| Web | 前端控制台与问答界面 |
| 代码沙箱 | 工作流代码节点执行环境 |
| 插件守护进程 | 模型插件加载与运行 |

Nginx 作为统一入口反向代理，对外仅暴露一个端口。

#### 4.7.2 离线部署方案

由于内网无法访问任何软件源，全部依赖预先在联网构建机打包，经移动介质摆渡入网：

| 离线包 | 内容 |
| --- | --- |
| 应用源码 | 平台源码（含数据库迁移脚本） |
| 语言运行时 | 便携 Python 运行时（主服务与沙箱各一套，互不干扰） |
| 依赖树 | 完整 Python 依赖树（801 个包，一次解包即用，目标机无需包管理器） |
| 前端产物 | 已构建的前端运行时（采用 musl 运行时，零系统库依赖） |
| 数据库源码 | PostgreSQL / pgvector / Redis 源码（目标机本地编译，匹配本机运行库版本） |
| 便携工具链 | 编译器与 Go 工具链（供目标机本地编译沙箱使用） |
| 模型插件 | 模型供应商插件离线包 |
| 部署脚本 | 安装脚本、服务单元、反向代理配置、自检脚本 |

#### 4.7.3 环境合规前置检查

安装脚本在执行任何变更前先做环境合规判定，
最关键的一条是**运行库版本**（实测本系统依赖树要求 glibc ≥ 2.28）。
不合规立即终止并给出明确结论，避免安装到一半失败。

#### 4.7.4 部署后自检

自检脚本覆盖系统环境、8 个服务状态、端口监听、数据库连通与建表、向量扩展、
缓存响应、API 健康、前端可达、插件守护进程、**代码沙箱真实执行**、磁盘占用与日志错误扫描，
共 24 项检查。其中代码沙箱一项通过真实执行一段代码验证，避免"端口在听但实际不可用"的假阳性。

### 4.8 数据契约与工程化保障

#### 4.8.1 契约风险

系统由**工作流编排文件**与**本地评测服务**两部分组成，两者通过字段名与文本格式通信。
由于横跨 YAML 与 Python 两种语言，无类型系统约束，任一侧改动不同步会导致**静默断裂**：
工作流正常返回，但数据采集不到，往往到生成报表时才发现。

本次指标重构（主观 1 项扩展为 3 项）即同时影响了四处：
工作流回执模板、评测服务解析函数、数据库表结构、历史数据迁移。

#### 4.8.2 保障措施

| 措施 | 说明 |
| --- | --- |
| 跨文件契约测试 | 从工作流文件中提取回执模板，与评测服务解析函数做往返一致性验证 |
| 静态校验前置 | 导入前校验节点连线、变量引用、分支句柄、代码节点语法、模板语法 |
| 指标键名集中化 | 指标定义单一来源，两侧派生，避免手工同步 |
| 增量迁移 | 数据库结构变更提供增量迁移脚本，旧库无需重建 |
| 代码节点自测 | 抽取工作流代码节点逻辑并真实执行，断言评分与质检行为 |

## 5. 关键技术实现要点

本章列出实现过程中必须处理的几个技术要点，完整分析见《05-技术难点分析》。

### 5.1 运行库版本是隐性门槛

系统的 Python 依赖中含有一个不提供低版本运行库二进制的包，
经实测扫描整棵依赖树的 456 个二进制文件，最高运行库需求为 **2.28**。
这意味着目标机必须是 RHEL 8 / openEuler 20.03 以上或同等级国产化系统；
CentOS 7（2.17）无法部署。该结论必须在部署前明确，避免后期返工。

### 5.2 组件复用策略：能复用就复用，不能复用就本地编译

| 组件 | 策略 | 依据 |
| --- | --- | --- |
| 前端 | 复用官方构建产物 | 采用 musl 运行时，实测零系统库依赖 |
| 插件守护进程 | 交叉编译静态二进制 | 纯 Go 无 CGO，产物零依赖 |
| 代码沙箱 | 官方二进制 + 兼容运行时双路径 | 官方二进制要求运行库 2.34，低版本系统用随包运行时 |
| 服务端 | 便携运行时 + 高兼容依赖树 | 便携运行时仅需 2.17，与依赖树短板解耦 |
| 数据库 | 随包源码本地编译 | 保证与目标机运行库完全匹配 |

### 5.3 视频解析的算力控制

采用「固定间隔初筛 + 关键帧检测去冗余」的两级抽帧策略，
把视觉推理调用量降低一个数量级；语音转写与画面描述按时间戳对齐后融合，
使视频内容可被检索、可被引用到具体时间点。

### 5.4 avi 格式的处理

平台原生白名单不含 avi。采用**双保险**：
（1）解析服务入口处做前置转码，把 avi 转为 mp4；
（2）向平台提交白名单补丁，使 avi 可直接上传。
任一路径生效即可满足「支持 avi 格式输入」的指标要求。

## 6. 满意度评价指标体系

### 6.1 体系结构

按需求「主观评价与客观评价 2 个维度，每个维度指标不低于 3 个」设计为 **主观 3 项 + 客观 6 项**。

### 6.2 主观评价维度（3 项，来自用户）

| 指标 | 键名 | 取值 | 获取方式 |
| --- | --- | --- | --- |
| 满意度 | satisfaction | 1-5 | 用户明说则采用；否则按语气映射（很满意=5 … 很不满意=1） |
| 有用性 | usefulness | 1-5 | 用户明说则采用；否则按「是否解决问题」推断 |
| 体验感 | experience | 1-5 | 用户明说则采用；否则默认 4，抱怨啰嗦/看不懂/太慢时降分 |

### 6.3 客观评价维度（6 项，大模型评委）

| 指标 | 键名 | 取值 | 性质 | 红线规则 |
| --- | --- | --- | --- | --- |
| 事实准确性 | factual_accuracy | 1-5 | 质量 | ≤2 直接判不合格，badcase 归 P0 |
| 知识完备性 | knowledge_completeness | 1-5 | 质量 | — |
| 相关性 | relevance | 1-5 | 质量 | — |
| 安全合规性 | safety_compliance | 0-5（0=不涉及） | 红线 | ≤2 直接判不合格，P0，24 小时内修复 |
| 版本时效性 | version_currency | 0-5（0=不涉及） | 红线 | =1 最多判待改进，P1 |
| 术语规范性 | terminology_norm | 1-5 | 专项 | ≤2 计入 badcase，P2 |

### 6.4 指数合成

```
主观指数 SSI = mean(满意度, 有用性, 体验感)          # 用户未评分时为空
客观指数 OSI = mean(事实准确性, 知识完备性, 相关性)
综合满意度指数 CSI = 0.5 × SSI + 0.5 × OSI           # SSI 缺失时 CSI = OSI
```

### 6.5 判定与分级

| CSI | 判定 |
| --- | --- |
| ≥ 4.2 | 优秀 |
| 3.5 ~ 4.2 | 良好 |
| 2.8 ~ 3.5 | 待改进 |
| < 2.8 | 不合格 |

**红线优先于分数**：事实准确性 ≤ 2 或安全合规性 ≤ 2 时直接判不合格，不受 CSI 影响。

| badcase 等级 | 触发条件 | 处理时限 |
| --- | --- | --- |
| P0 | 安全合规性红线 或 事实准确性 ≤ 2 | 24 小时内 |
| P1 | 版本失效 或 CSI < 2.8 | 本周内 |
| P2 | 术语不规范 或 一般质量问题 | 随双周批次 |

### 6.6 错误归因体系

共 14 类归因，每类映射到明确的整改动作：

无、知识库缺失、检索未命中、分块不当、提示词缺陷、模型能力不足、幻觉编造、
知识过期、版本失效、问题歧义、型号适配错误、术语不统一、安全警示缺失、跨文档冲突。

归因到整改的映射（示例）：

| 归因 | 整改动作 |
| --- | --- |
| 知识库缺失 | 补充对应资料入库 |
| 检索未命中 | 调整分段长度 / top_k / 开启重排 |
| 版本失效 | 清理作废版本段落，更新版本台账 |
| 安全警示缺失 | 补充安全条款并复核全部同类回答 |
| 术语不统一 | 统一术语表并回归检查 |

## 10. 风险分析与应对

| 序号 | 风险 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| R1 | 目标机运行库版本过低（如为 CentOS 7） | 无法部署 | 部署前环境合规检查一次性判定；已明确最低要求，可提前更换系统 |
| R2 | GPU 资源未落实 | 无法真实微调 | 前期按「检索增强 + 提示词迭代」路径推进；GPU 到位后补微调环节；微调采用 LoRA 单卡方案降低门槛 |
| R3 | 老旧图片、视频解析质量不足 | 多模态理解效果差 | 低置信度内容标注为「疑似」不入正文；不达标片段进入人工复核队列 |
| R4 | NL2SQL 准确率不达预期 | 数据库查询可用性差 | 维护少样本示例库；口径复述让用户可判断；高价值问题固化为模板查询 |
| R5 | 微调后通用能力退化 | 回答质量下降 | 训练集混入通用语料；设置回归红线，不达标不予上线 |
| R6 | 指标契约变更导致采集断链 | 数据丢失且不易发现 | 跨文件契约测试强制执行；指标键名集中化 |
| R7 | 用户评价采集率低 | 迭代缺少数据 | 对话内评价 + 原生点赞双通道；回执设计极简，降低评价成本 |
| R8 | 离线包体积过大 | 摆渡不便 | 按组件分卷；剔除实验性产物；提供校验清单 |

## 11. 方案优势总结

1. **完全本地化**：大模型、嵌入、重排、视觉、语音、解析全部本地部署，不依赖任何外部服务，
   满足课题「采取本地部署」的要求，也符合内网数据安全要求。

2. **不依赖容器**：针对目标环境明确要求，设计了完整的原生进程部署方案，
   并通过组件复用与本地编译的组合策略解决了国产化平台的二进制兼容问题。

3. **能力边界识别清晰**：对所选编排平台做了完整的能力核查，
   明确了 OCR、视频处理、数据库查询、模型微调四类必须外挂的能力，
   以独立服务形式接入，架构清晰、职责分明、可单独替换。

4. **多模态真正贯通**：不是把图片视频"存起来"，而是解析成带定位锚点的结构化文本，
   使视频内容可被检索、可被引用到具体时间点，满足"统一采集、管理和维护"的实质要求。

5. **评价驱动改进有闭环**：主观 3 项 + 客观 6 项的指标体系，
   配合红线降级与 badcase 分级，评价结果直接映射到整改动作，
   并经黄金集回归验证后才允许发布，形成可重复执行的迭代闭环。

6. **工程化保障到位**：跨文件契约测试、静态校验前置、增量迁移、部署自检，
   把"改一处坏三处"和"部署到一半失败"这两类常见工程风险控制在流程之内。
