# 以文档质量为中心的治理度量框架

> 文档编号：EVAL-GOV-010
> 项目名称：基于大模型的多模数据管理查询及迭代优化技术研究
> 编写时间：2026-09-23
> 密级：内部
> 结论摘要：把问答系统重新定位为**文档质量的探针与证据采集器**——治理闭环的终产物不是「满意度报表」，而是**按文档聚合的质量记分卡 + 可执行的缺陷整改单**。
> 核心算法是**归因前置（retrieval-gated attribution）**：只有「检索到了、忠实引用了、却仍然答不好」，才判定为**文档缺陷**；其余问题不得记到资料头上。
> 关键判断：这条路**今天就能起步**，不依赖 RAGFlow——证据链的原材料已经躺在 messages.retriever_resources_json 里，只是没有被聚合。

---

## 1. 定位重述：从「问答系统」到「文档质量测量仪」

### 1.1 同一个系统，两种叙事

| 维度 | 问答系统叙事（现状） | **文档治理叙事（本框架）** |
| --- | --- | --- |
| 系统是什么 | 一个能回答装备资料问题的助手 | **一台测量装置**：用真实提问去测量资料的可用性质量 |
| 用户是谁 | 操作手、维修员、教员 | 首要是**资料管理员与资料编写单位**，其次才是使用者 |
| 核心指标 | CSI 满意度指数 | **文档缺陷密度、覆盖命中率、整改闭环率** |
| 终产物 | 周报、月报、badcase 清单 | **文档质量记分卡 + 缺陷整改单 + 回归验证结论** |
| 成功判据 | 答得让人满意 | **资料被改好了，且改好的部分经回归验证不再复发** |

两种叙事不冲突：**问答是手段，资料变好才是目的**。本框架不推翻既有交付物，而是给它们换一个主语——从「回答质量」换成「文档质量」。

### 1.2 为什么问答测得出静态检查测不到的东西

tools/check_corpus.py 已经是很好的**形式与一致性**门禁（8 字段文档头、编号版本与台账一致、唯一现行版本、作废值未泄漏、参数一致、术语规范，288 条款 0 错误）。
但它测不了**可用性质量（fitness for use）**——一份资料可以完全合规，却依然难用：

| 静态检查能发现 | **只有问答才能发现** |
| --- | --- |
| 编号 / 版本 / 状态不一致 | 条款写了，但**写得含糊**，不同人读出不同结论 |
| 同一参数在不同资料取值不同 | 参数**正确但缺少适用条件**（型号 / 工况 / 前置步骤） |
| 术语表外的术语出现 | 用户按习惯问法提问时，**资料里根本没有对应的表述** |
| 作废数值残留在台账之外 | 资料内部**步骤缺项**（第七步接第九步，读者必须猜） |
| 缺少安全条款段落 | 安全警示**写在别的章节**，检索到操作步骤时不会带出来 |
| 文档头字段缺失 | 文档**结构不可检索**（无标题层级、表格跨页错乱、扫描件无文字层） |

> 一句话：**静态检查测「资料写得对不对」，问答测「资料用起来行不行」。** 后者才是甲方最关心的质量，也是最难测的质量。

### 1.3 与既有资产的关系

| 既有资产 | 在新叙事中的角色 | 是否改动 |
| --- | --- | --- |
| eval_service（评价闭环） | **测量仪本体**：采集 → 评分 → 归因 → 报表 | 增量扩展（§9） |
| 三个 DSL（问答 / 评价 / 标注） | 探针发射器与评分器 | 少量（提示词补引用契约字段） |
| tools/check_corpus.py | **静态探针**（全量普查） | 增量（输出机器可读条款清单 + 可检索性检查） |
| samples/ 六份语料 + 台账 | 被测量的对象，也是唯一真源 | 不变 |
| docs/09 的 RAGFlow×Dify 融合框架 | **证据链增强器**（不是前置条件） | 不变 |

## 2. 三类探针：谁测什么

```text
探针一：静态探针（check_corpus.py）
   全量 · 形式与一致性 · 不需要用户 · 发现「合规但不实用」的问题

探针二：主动探针（覆盖题集 probe_set，本框架新增）
   按条款抽样 · 测「每一条款能否被正确答出」 · 覆盖已知盲区

探针三：被动探针（真实问答 + 用户评价，现有链路）
   真实问法 · 真实场景 · 暴露高频痛点与资料里根本没有的知识
```

| 探针 | 覆盖范围 | 成本 | 偏差 | 治理用途 |
| --- | --- | --- | --- | --- |
| 静态 | 100% 条款 | 低（纯规则） | 无（确定性） | 一致性、版本、术语、格式类缺陷 |
| 主动 | 可抽样（建议每条款 1~2 问） | 中（题目生成 + 审核 + 模型评分） | 抽样偏差 + 出题者偏差 | 覆盖完备性、表述歧义、步骤缺项、可检索性 |
| 被动 | 真实提问的天然分布 | 低（已有链路） | 人群与场景偏差 | 高频痛点、真实缺口、满意度 |

**三条腿缺一不可**：只有被动探针（现状）会漏掉「从来没人问、但一旦问就出事」的条款（安全类、应急处置类最典型）；
只有主动探针会脱离真实使用场景；只有静态探针只能看到形式。

> 统计纪律：被动探针的结论是**抽样估计**，必须给样本量与置信区间（§6.3）。不能因为 3 道题答得差就判定整份规程不合格。

## 3. 文档质量维度模型（D1~D8）

把现有指标「翻译」成文档质量维度，是这套框架的第一块基石——**同一批数据，换一个聚合主语**。

| 维度 | 含义 | 数据来源（现有） | 文档缺陷判定（举例） | 整改去向 |
| --- | --- | --- | --- | --- |
| **D1 覆盖完备性** | 该有的知识有没有 | KC 分低、knowledge_gap、归因「知识库缺失」 | 被问到的问题在资料中无对应条款 | 补写条款 / 新增资料 |
| **D2 内容准确性** | 写了的内容对不对 | FA 分低、归因「幻觉编造」（需归因前置过滤） | 检索命中且答案忠实于片段，但片段本身与权威值不符 | 更正数值 / 组织技术核定 |
| **D3 一致性** | 文档内与跨文档是否自洽 | 归因「跨文档冲突」、check_corpus 参数一致性 | 两份资料对同一对象给出不同值或不同步骤 | 指定权威源，统一表述 |
| **D4 版本时效性** | 是否为现行有效版本 | VC、归因「知识过期 / 版本失效」、台账 | 作废版本数值仍可被检索或仍被引用 | 清理作废段落 / 换版 |
| **D5 术语规范性** | 术语是否统一、缩略语是否展开 | TN、归因「术语不统一」、术语对照表 | 同一部件在资料中多种叫法，用户按任一种问法无法召回 | 按对照表统一 |
| **D6 安全完备性** | 安全警示是否完备、随取随用 | SC、归因「安全警示缺失」 | 检索到操作步骤时，其前置条件 / 禁止事项未随片段带出 | 安全条款独立成段并建关联 |
| **D7 结构可检索性** | 资料是否机器读得懂 | RQ、归因「检索未命中 / 分块不当」、解析健康度 | 同一条款多种问法均检不到，且静态检查显示无标题层级 / 编号断裂 / 表格跨页错乱 | 重构标题层级与编号 / 重做表格 |
| **D8 引用可追溯性** | 答案能否落到条款与版本 | 引用正确率、C3 引用契约 | 命中片段无法定位到条款号与页码，整改单无法落地 | 解析期写入条款号与页码（docs/09 的 C1/C2 契约） |

**维度归属的争议判定（最容易出错的一条）**：D7 的表面现象是「检不到」，但责任可能在人（文档结构差）也可能在系统（分块 / 索引 / 检索参数）。裁定规则：

1. 若**同一条款换 3 种问法都检不到**，且该条款在资料中确实存在、格式规范 → **系统缺陷**（分块 / 检索），不算资料的问题；
2. 若该条款存在但**无标题、无编号、与其他内容挤在一段**，或位于跨页错乱的表格中 → **文档缺陷（D7）**；
3. 若该条款在资料中**根本不存在** → 计 **D1 覆盖缺陷**，不是 D7。

## 4. 核心算法：归因前置判定树

这是整套框架里**唯一一处绝不能省**的算法。没有它，「用答案质量反映文档质量」就会退化成「把系统的锅甩给资料员」。

```text
一条低分回答进来
  │
  ├─ Q1 检索是否命中「正确的」条款？
  │    （retriever_resources 中的 document_name 含 doc_no+版本，且片段内容覆盖问题要点）
  │    │
  │    ├─ 否 ─┬─ Q1a 该条款在资料中存在吗？（静态探针可查）
  │    │      ├─ 不存在 → 【D1 文档缺陷】覆盖缺口
  │    │      └─ 存在   → 【系统缺陷】分块/索引/检索参数（不算资料的账）
  │    │
  │    └─ 是 ─→ Q2 回答是否忠实于命中片段？（有无幻觉/编造）
  │           ├─ 不忠实 → 【系统缺陷】提示词/模型（编造）
  │           └─ 忠实   → Q3 忠实引用后，答案是否仍然不对/不全？
  │                      ├─ 是 → 【文档缺陷】按 §3 归入 D2~D6
  │                      └─ 否 → 低分来自别处：
  │                             Q4 用户评分低但模型评分高？（认知差异 / 表述不清晰）
  │                             Q5 问题本身有歧义？（需补同义问法与消歧）
```

### 4.1 判定规则（写成代码里的确定性规则，LLM 只做兜底）

| 规则 | 条件 | 判定 | 归属 |
| --- | --- | --- | --- |
| R1 | 无任何 retriever_resources | 检索失败 / 未检索 | 系统 |
| R2 | 命中片段与问题所问条款不匹配（编号或主题不符） | 检索失准 | 系统 |
| R3 | 命中片段匹配，但 hallucination_risk 中/高 | 编造 | 系统 |
| R4 | 命中片段匹配、无幻觉，knowledge_completeness ≤ 3 | 内容不全 | **文档（D1/D2）** |
| R5 | 命中片段匹配、无幻觉，factual_accuracy ≤ 2 且片段本身与权威值不符 | 内容错误 | **文档（D2）** |
| R6 | 命中两份及以上不同资料的片段且结论冲突 | 跨文档冲突 | **文档（D3，需技术核定）** |
| R7 | 命中的 document_name 版本 ≠ 台账现行版本 | 版本失效 | **文档 / 索引（D4）** |
| R8 | 命中片段无编号、无标题，且同条款多变体问法均检不到 | 结构不可检索 | **文档（D7）** |
| R9 | 无命中且静态探针确认条款不存在 | 知识缺失 | **文档（D1）** |

### 4.2 置信度与人工复核

| 情形 | 处理 |
| --- | --- |
| 规则命中（R1~R9） | 自动判定，可入单 |
| 规则未命中、需语义判断 | 交给评价工作流的 LLM 评委，输出 blame + defect_type，标记「机器初判」 |
| 判为文档缺陷且严重度 ≥ P1 | **必须人工确认**后才开整改单（误判会直接损害资料员对系统的信任） |
| 判定分歧（机器 vs 人工） | 记入人工复核记录，用于校准 LLM 判定口径（延续 docs/01 的一致率抽检要求） |

## 5. 证据链：现在有什么，缺什么

这一节回答「本框架是否需要先上 RAGFlow」。答案是**不需要**。

| 证据 | 现在在哪 | 现状 | 缺什么 |
| --- | --- | --- | --- |
| 命中的文档与版本 | messages.retriever_resources_json → document_name（形如 HYS-WX-003 某型液压举升系统维修规程 V2.0） | ✅ **已含 doc_no + 版本号**，可直接正则解析 | 只需在建表时落列 |
| 命中的片段正文与分数 | 同上 → content / score / segment_id | ✅ 有 | — |
| 条款号 | evaluations.contexts（拼接后的上下文） | ⚠️ 正文有、条款号不可靠 | 解析期写入条款号（docs/09 C2 契约） |
| 页码 | — | ❌ 无 | RAGFlow positions 或解析期标注 |
| 版本硬过滤 | — | ❌ 无（作废段落一旦入库就可能被召回） | RAGFlow 元数据过滤（docs/09 §6.4） |
| 解析健康度 | — | ❌ 无 | 解析流水线的失败率 / 表格还原率 |

**结论（重要）**：

- **G0 阶段今天就能做**：解析 retriever_resources_json 得到 doc_no / version，按文档聚合，就能产出第一版「文档质量记分卡」——**零新增组件、零架构改动**；
- RAGFlow 的价值在于把证据链从「文档级 + 片段级」提升到**「条款级 + 页码级 + 硬过滤」**，让整改单能精确到「第 4.2 节第 12 页」，并让作废版本召不回；
- 因此二者关系是：**治理框架是目的，RAGFlow 是证据链的增强件**。顺序上先做 G0~G3，再做 docs/09 的 L1。

## 6. 文档质量记分卡（核心产物）

### 6.1 表结构（每份资料一行）

| 列 | 定义 | 数据来源 |
| --- | --- | --- |
| doc_no / version / status | 资料编号 / 版本 / 状态 | 台账 + retriever_resources 解析（以台账为准） |
| clauses_total / clauses_probed | 条款总数 / 已被探针覆盖数 | 静态探针（条款清单）+ 主动探针 |
| coverage_rate | clauses_probed / clauses_total | 探针覆盖率 |
| probes | 该文档被探针命中的题数 | evaluations（按 doc_no 聚合） |
| csi_mean | 该文档相关问答的 CSI 均值 | metrics.aggregate |
| defects_p0/p1/p2 | 缺陷计数（按严重度） | 归因前置判定（§4） |
| defect_density | 每 100 条探针的缺陷数 | 归一化，便于不同文档比较 |
| dqi | 文档质量指数（§6.2） | 由缺陷密度与严重度加权 |
| ci_low / ci_high | 置信区间 | 自助法 / Wilson 区间 |
| sufficient | 样本是否充分（n ≥ 8 且至少 1 条主动探针） | 不足则**不出结论，只列证据** |
| top_defects | 该文档最高频缺陷类型 Top3 | 缺陷类型分布 |

### 6.2 为什么 DQI 不用 CSI 均值

直接用 CSI 均值排名会奖励「写得简单、只答容易题」的资料，并惩罚「条款多、难题多」的资料。因此：

```text
DQI = 100 × (1 − 缺陷密度加权分)
缺陷密度加权分 = Σ(缺陷严重度权重 × 缺陷数) / 探针数 × 归一化系数
严重度权重：P0 = 5，P1 = 2，P2 = 1
CSI 均值只作为过程指标与趋势参考，不作为文档排名的依据
```

### 6.3 统计纪律（写进 SOP，避免治理被数据误伤）

| # | 纪律 | 理由 |
| --- | --- | --- |
| 1 | 探针数 < 8 的资料**不出结论**，只列证据 | 3 条问答的均值没有统计意义 |
| 2 | 所有比例给区间，不给裸值 | 避免「100% 合格」这种小样本幻觉 |
| 3 | 不同文档**不直接横向排名**，除非都给区间且探针口径一致 | 题量与难度不同，排名会误导 |
| 4 | 缺陷计入前必须过归因前置（§4） | 系统问题不得计入文档 |
| 5 | 结论要连同样本量一起呈现（例如 n=12，缺陷 2，区间 0.02~0.45） | 让读者能自行判断可信度 |

## 7. 治理产物与工单闭环

### 7.1 四类产物

| # | 产物 | 内容 | 使用者 |
| --- | --- | --- | --- |
| 1 | **文档质量记分卡**（Markdown / CSV / HTML） | §6.1 全部列 + 趋势 | 资料管理员、项目负责人 |
| 2 | **缺陷整改单**（CSV / 工单） | 一缺陷一行：doc_no / 条款 / 缺陷类型 / 证据（问答原文 + 命中片段）/ 整改动作（复用 CAUSE_ACTION）/ 责任单位 / 期限 / 回归结果 | 资料编写单位 |
| 3 | **覆盖缺口清单** | 无题覆盖的条款 + 用户问了但资料未覆盖的知识簇 | 资料管理员 |
| 4 | **版本与冲突清单** | 作废版本残留、跨文档冲突对 | 技术核定人 |

### 7.2 闭环率：治理区别于报表的唯一标志

```text
闭环率 = 已验证关闭的缺陷数 / 缺陷总数
已验证关闭 = 该缺陷对应探针重跑通过（verify-defect），而非资料员口头确认
```

单缺陷回归（verify-defect）与现有黄金集回归是两件事，都要有：

| 回归类型 | 作用 | 现状 |
| --- | --- | --- |
| 黄金集回归（g01~g12） | 防全局退化 | ✅ 已有 regression 子命令 |
| **单缺陷回归** | 验证「这一条改好了没有」 | ❌ 需新增（该缺陷关联探针重跑 + 与整改前对比） |

### 7.3 防博弈设计（一旦记分卡进入考核，必须同时上线）

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 删条款提分 | 把答不好的条款删掉，覆盖命中率反而上升 | clauses_total 锁定台账条款清单；条款变更必须走变更流程并留痕 |
| 背题 | 探针题被泄露，回答变成背答案 | 探针集保密；定期生成变体问法；人工抽检校准 |
| 挑题 | 只给容易的条款出题 | 探针抽样按条款类型分层（原理 / 操作 / 维修 / 安全 / 术语），安全类必抽 |
| 甩锅 | 系统缺陷记到资料头上 | 归因前置（§4）+ P1 以上人工确认 |
| 刷满意度 | 引导用户点好评 | 以主动探针与客观维度为主，用户评分为辅 |

## 10. 分期路线（G0~G4）

| 阶段 | 内容 | 工期 | 退出条件（可验收） |
| --- | --- | --- | --- |
| **G0 归因前置 + 文档维度聚合** | 解析 retriever_resources_json 落 doc_no/version；实现 R1~R9 规则；按文档聚合出第一版记分卡 | 1 ~ 2 人·天 | 对现有评价数据跑出「按文档」的缺陷分布；人工抽检 20 条归因，一致率 ≥ 80% |
| **G1 覆盖探针集** | --emit-clauses + 探针自动生成 + 分层抽样 + 人工审核 + 变体问法 | 3 ~ 5 人·天 | probe_set.jsonl 覆盖全部安全类条款与抽样条款；人工审核通过 |
| **G2 记分卡 + 整改单** | doc_score.py + defects 表 + 工单产物 + 区间与样本充分性 | 3 ~ 5 人·天 | 输出记分卡与整改单；资料员可据单执行；例会可用 |
| **G3 单缺陷回归 + 闭环率** | verify-defect 子命令 + 闭环率看板 + 防博弈规则 | 2 ~ 3 人·天 | 至少 1 个真实缺陷完成「发现→整改→回归→关闭」全过程 |
| **G4 证据链增强** | 接 docs/09 的 L1：条款级 + 页码级定位、版本硬过滤、解析健康度 | 5 ~ 8 人·天（依赖 RAGFlow 档位） | 整改单可精确到「节 + 页」；作废版本召回数为 0 |

**实施状态（2026-09-23）**：**G0 已落地并通过自测**——新增 `eval_service/corpus.py`（语料索引：文档头 / 条款清单 / 台账现行版本）、
`eval_service/attribution.py`（归因前置 R1~R9 + 整改动作映射）、`eval_service/doc_score.py`（记分卡 + Wilson 区间 + 缺陷整改单），
`cli.py` 增加 `attribute` / `scorecard` 两个子命令，`store.py` 升到 `SCHEMA_VERSION = 3`（evaluations 增 5 列 + defects 表，旧库自动迁移）。
用 mock 数据实测：15 条评价 → 文档缺陷 1 条、覆盖缺口 2 条、系统侧问题 2 条、未见异常 10 条，产出 `out/doc_scorecard.md` 与 `out/doc_scorecard.csv`。

**G0~G3 合计 9 ~ 15 人·天**，且**不新增任何内网常驻组件**——这是本框架相对「先上 RAGFlow」的最大优势：先让治理跑起来，再谈仪器升级。

### 11.1 三个必须避免的失败模式

| 失败模式 | 表现 | 预防 |
| --- | --- | --- |
| **甩锅型治理** | 系统分块没做好，却给资料员开整改单 | 归因前置（I4），P1 以上人工确认 |
| **报表型治理** | 出了一堆报表，没人整改，闭环率趋近 0 | 以 defects 工单与闭环率为核心 KPI，记分卡只是视图 |
| **小样本型治理** | 3 条问答就判一份规程不合格 | 统计纪律（§6.3）写进 SOP 与代码 |

## 12. 一页话总结

> **问答系统不是终点，它是唯一能测出「资料用起来行不行」的探针。**
> 三类探针（静态 / 主动 / 被动）覆盖不同盲区；归因前置决定「这口锅算谁的」；
> 记分卡回答「哪份资料差」，整改单回答「改什么」，闭环率回答「到底改没改」。
> 顺序上：**先把治理跑起来（G0~G3，不改架构、不加组件），再谈仪器升级（docs/09 的 L1）。**
> 三个必须避免的失败模式：甩锅型治理、报表型治理、小样本型治理。
