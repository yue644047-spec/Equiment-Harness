## 1 概述

### 1.1 任务来源

> 本节按模板要求由甲方（九部）填写。为保持文档完整性，乙方依据已确认的需求方案与技术协议给出草拟内容，最终表述以甲方正式文本为准。

装备系统技术日益复杂、资料繁多，原理及规程等分散于各类手册、技术文件等资源中，用户在学习与查询中使用不便捷；同时，现场积累的故障现象照片、操作演示视频、检修过程录像等非结构化数据长期处于“存而不用”的状态。为提升装备技术资料的获取效率与使用效能，甲方立项开展“基于大模型的智能查询及基于用户评测反馈的闭环迭代技术研究”。

本项目研究利用大模型技术进行数据管理、智能查询和基于用户实际使用效果的评价技术，为**数据管理集中化、知识获取平台化、评价智能化**提供技术支撑。项目研究周期 270 个日历天；质保期 12 个月，自验收交付之日起算，质保期内乙方提供技术咨询服务。

本项目按甲方要求采用**变体 RAGFlow 架构与 Dify 编排平台融合**的技术路线，系统部署于**国产 ARM 架构（飞腾 3000 平台）**、配置 **32GB 显存国产推理加速卡**的服务器上，操作系统为国产 Linux，运行环境为物理隔离内网，且不使用容器。

### 1.2 产品的功能及组成

本系统的产品定位是：**面向装备技术资料、完全本地化部署的多模态智能问答与评价迭代平台**。系统对内是资料使用者的问答助手，对外是资料管理者与装备技术责任人的质量测量装置。

产品的功能可以概括为“**一条主线、两个闭环、一条边界**”：

**一条主线**：多模态数据统一接入 → 语料治理与文本深度解析 → 知识库与资产索引构建 → 智能问答与交互查询 → 带出处的回答。

**闭环一（质量闭环）**：用户评价与自动评分 → 指标聚合 → 坏例归因 → 整改动作 → 黄金集回归 → 发布卡点。

**闭环二（模型闭环）**：语料标注 → 训练数据构造 → 低频适配微调 → 回归对比 → 模型上线切换。

**一条边界（本设计的重要约定）**：**文本以外的模态只检索、不理解。** 系统对图片与视频只做采集、登记、维护、定位与检索呈现，不做光学字符识别、不做画面语义理解、不做视频抽帧与语音转写，因而不对其内容作任何解释或推断。

产品的组成如下：

（1）**接入层**：Web 问答控制台、知识库与资料管理界面、评价看板与报表。

（2）**编排层**：基于 Dify 的多模态智能问答 Chatflow、满意度评价 Workflow、语料标注 Workflow。

（3）**检索层（变体 RAGFlow 架构的核心）**：检索契约层，实现与 Dify 外部知识库协议兼容的检索接口，统一片段结构、引用契约与附件引用关系，执行版本硬过滤，后端可在变体索引与上游 RAGFlow 之间切换。

（4）**解析与索引层**：文本深度解析（版式分析、表格结构化、条款与页码定位）、按条款分段与嵌入、向量与词项混合索引；以及图片与视频的**资产索引**（登记、元数据与缩略图）。

（5）**语料治理层**：文档契约与资产契约生成、版本台账校验、入库门禁、条款清单。

（6）**能力层（自研外挂服务）**：文本深度解析服务、数据库查询服务、模型推理服务、模型微调服务。

（7）**数据层**：向量库、关系数据库、缓存与任务队列、对象存储（本地文件系统）。

（8）**评价层（本地评测服务）**：采集、评分、聚合、报表、坏例归因、回归验证、文档质量记分卡。

（9）**平台层**：国产 ARM 服务器、国产操作系统、原生进程服务托管与反向代理。

**（3）设计边界说明。** 本设计对图片与视频采用“只检索、不理解”的处理方式，其直接影响是：**图片画面内的文字与视频中的语音、画面内容不进入语义检索范围**。因此，图片与视频的可检索性取决于其所属资料、所在章节、图注标题与人工标签的完整程度；对以扫描件形式存在的资料，其正文同样不进入语义检索范围。该边界需在实施阶段与甲方确认，若后续要求对扫描件或图片内容建立语义检索，则需重新引入光学字符识别或视觉理解能力，并相应调整显存预算（见 3.10.2）与工期。

| T7 至 T12 | 统计评价数据 | 主观 3 项与客观 6 项均有数据，CSI 与判定可计算 |
| P1 至 P5 | 性能压测 | 各项响应时间与并发指标达标 |
| S1 至 S6 | 安全核查与审计抽查 | 无外发流量、访问有鉴权、日志留存不少于 6 个月 |
## 3 技术方案设计

### 3.1 设计研制思路

#### 3.1.1 设计原则

**（1）检索与理解分离。** 文本类数据做深度解析与语义检索；图片与视频只做采集、登记、维护、定位与检索呈现，不做内容理解。该原则同时带来三项收益：处理链路显著缩短、算力与显存开销大幅下降、系统不对无法核实的内容作出推断，避免了“看图说话”式的不可靠结论。

**（2）契约先行。** 系统由多个来源不同的组件构成，组件之间只通过显式定义的契约通信。四个契约（文档契约、资产契约、检索契约、引用契约）在编码之前先定稿，任何组件不得绕过契约直接读取对方的内部数据。

**（3）单一真源。** 资料内容以治理后的语料文件为唯一真源，向量索引与检索产物都是可重建的投影；版本状态以《装备技术资料清单与版本台账》为唯一真源；评价口径以本地评测服务为唯一真源；同一时刻只允许一个检索引擎对用户提供服务。

**（4）确定性优先。** 安全与版本两条红线，能用确定性手段就不用概率手段。版本控制由“提示词叮嘱”升级为“检索层元数据硬过滤”，使作废版本片段在物理上无法被召回。

**（5）本地化与国产化。** 大模型、嵌入、重排、知识库、数据库、解析引擎全部在甲方内网本地部署；全部组件以国产 ARM64（飞腾 3000 平台）为第一目标平台，运行期不访问互联网。

**（6）不依赖容器。** 目标环境明确不使用容器，全部组件以原生进程方式运行，由 systemd 统一托管，反向代理对外只暴露一个端口。

**（7）算力与显存预算约束。** 系统在**单张 32GB 显存加速卡**上运行，模型规模与并发能力均由显存预算推导得出。取消视觉与语音理解后，原先用于这两类模型的显存被释放，可直接转化为对话模型的能力提升或上下文预算，见 3.10.2。

**（8）闭环可重复。** 采集、评价、归因、整改、回归的每个环节均可脚本化重复执行，并以回归验证通过作为发布的唯一凭证。
#### 3.1.2 总体技术路线

本项目的技术路线是：**以变体 RAGFlow 架构承担“文档读得懂、片段找得准、引用落得实”，以 Dify 承担“流程编排、会话管理、反馈采集”，两者通过检索契约层解耦融合。**

**（1）为什么采用融合路线而不是单平台。** 单用编排平台，文档解析与检索能力偏弱：表格结构易错行、扫描件无文字层、元数据过滤能力弱，难以满足“文档出处显示”与版本时效性要求。单用 RAGFlow 系的完整栈，其容器化部署形态与重型依赖（默认文档引擎为 Elasticsearch、元数据库为 MySQL、对象存储为 MinIO）在国产 ARM 平台、禁容器、离线摆渡的约束下落地风险高。因此本项目采用**变体形态**：保留其架构分层与契约化接口，用可在 ARM64 上原生运行的轻量服务实现同等能力，同时保留后端切换能力。

**架构说明：**

（1）**为什么把语料治理独立成层。** 本项目的质量瓶颈不在检索算法，而在资料本身的可用性——条款含糊、参数缺适用条件、安全警示分散等问题无法靠检索优化解决。独立治理层使“资料问题”与“系统问题”在架构上各有归属，也为后续的归因前置判定提供依据。

（2）**为什么把检索契约层单独成层。** 该层是变体 RAGFlow 架构与 Dify 之间的唯一耦合点，也是本方案“变体”二字的落点：它把检索引擎的差异全部吸收在层内，向上只暴露稳定契约。因此更换或升级检索后端不需要改动工作流、不需要改动评价口径、不需要改动界面。

（3）**图片与视频在架构中的位置。** 图片与视频不作为独立的可检索语义单元，而是作为**引用附件**挂载在其所属的文本片段上：文本片段负责被检索，附件负责被呈现。这样既满足“统一采集、管理和维护”与“文档出处显示”，又完全不需要对内容作理解。

（4）**三条接缝是架构的红线。** 一旦出现第四条接缝（例如让编排层直接读取解析服务的数据库），系统即开始腐化，必须通过架构评审否决。

（5）**单一真源。** 资料内容以治理后的语料文件为唯一真源；版本状态以版本台账为唯一真源；评价口径以本地评测服务为唯一真源。违反该原则会出现“同一问题答案漂移、报表互不认账”的双源冲突，属于必须避免的系统性错误。
### 3.3 语料治理与文档契约模块设计

#### 3.3.1 功能概述

本模块是三条接缝中最先执行的一环，负责在资料进入解析与索引之前完成一致性与版本校验，并生成机器可读的入库清单（文档契约与资产契约）。它决定了知识库的“底子”是否干净。

#### 3.3.4 使用流程

**（1）资料入库流程：** 上传文件并填写资料元数据 → 一致性校验 → 不通过则拒绝入库并列出问题条目 → 通过则计算内容指纹、生成文档契约 → 写入入库清单并移交解析与索引层 → 记录入库台账。

**（2）资产入库流程：** 上传图片或视频并填写资产元数据（名称、所属资料、章节、页码、图注标题、标签）→ 格式与完整性校验 → 生成缩略图、计算内容指纹 → 生成资产契约并建立与目标片段的关联 → 资产进入资产索引，随所属片段被检索。

**（3）资料换版流程：** 上传新版本 → 校验通过后先完成解析与索引 → 召回测试确认新版本可命中 → 下架旧版本片段及其关联资产 → 更新版本台账。同一资料编号在全库只保留一个现行有效版本。
### 3.4 多模态数据接入与资产索引模块设计

#### 3.4.1 功能概述

本模块承担“文本读得懂、图视频找得到”的职责，实现 F1 与 T1 至 T6。它包含两条处理路径，且两条路径的深度刻意不同：

**文本路径（深度处理）**：做版式分析、表格结构化、条款与页码定位，产出可语义检索的片段。

**图片与视频路径（浅度处理）**：只做采集、格式校验、元数据登记、缩略图生成与附件关联，**不做光学字符识别、不做画面语义理解、不做视频抽帧与语音转写**。资产不独立参与语义检索，而是挂载在文本片段上随片段一并返回。

这样划分的依据是：需求对图片与视频只要求“数据的输入”与“统一采集、管理和维护”，并未要求内容理解；在单张 32GB 显存与国产 ARM 平台的约束下，把算力集中在文本问答质量上，收益更明确，也避免了系统对无法核实的内容作出推断。

**（4）用户上传图片或视频提问：** 系统不对其内容作理解，处理方式为：提示用户补充文字描述，系统据文字描述检索知识库；用户上传的文件仅作为本次会话的上下文留痕，不进入知识库、不参与理解、不用于训练。

| 附件返回 | 开启 | 命中片段所挂载的图片与视频随片段返回 |

分段有四条硬规则：按条款编号切分且一条条款不跨段；资料编号与版本号必须留在段内；表格整表不跨段；每段自解释，不得以“同上”“见前条”开头。以上全部参数均通过管理界面暴露并可调，调整后重新索引即生效，直接对应 F5、F6、F7 的验收要求。

**指数合成与判定：**

```text
主观指数 SSI = mean(满意度, 有用性, 体验感)          # 用户未评分时为空
客观指数 OSI = mean(事实准确性, 知识完备性, 相关性)
综合满意度指数 CSI = 0.5 x SSI + 0.5 x OSI           # SSI 缺失时 CSI = OSI
封顶规则：事实准确性 <= 1 时 CSI 上限 2.00；标注为拒答不当时 CSI 上限 2.50
```

表 36 判定分级

| CSI 区间 | 判定 | 业务含义 | 建议动作 |
| --- | --- | --- | --- |
| 不小于 4.20 | 优秀 | 可直接交付 | 保持，纳入优秀案例库 |
| 3.50 至 4.20 | 良好 | 基本可用，存在局部瑕疵 | 常规优化，纳入周报 |
| 2.80 至 3.50 | 待改进 | 勉强可用 | 立项整改，两周内出结果 |
| 小于 2.80 | 不合格 | 不可交付 | 立即整改，阻断上线 |

**红线优先于分数**：事实准确性不大于 2 或安全合规性不大于 2（且不为 0）时直接判不合格，不受 CSI 数值影响。判定执行顺序固定为：计算 CSI 与封顶保底 → 赞踩降级 → 版本降级 → 事实准确性红线 → 安全红线 → 输出最终判定与坏例等级。装备域专项指标的取值 0 表示“本条不涉及该类内容”，既非最低分也非缺失值，计算均值时从分子分母同时剔除，判红线前先判断是否为 0。

**归因前置判定。** 只有“检索到了正确条款、回答忠实引用了条款、却仍然答不好”才判定为文档缺陷，其余问题不得记到资料头上：

```text
Q1 是否命中正确的条款？
  否 -> Q1a 该条款在资料中存在吗？
          不存在 -> 文档缺陷（覆盖完备性）
          存在   -> 系统缺陷（分块 / 索引 / 检索参数）
  是 -> Q2 回答是否忠实于命中片段？
          不忠实 -> 系统缺陷（提示词 / 模型编造）
          忠实   -> Q3 忠实引用后仍不对或不全？
                     是 -> 文档缺陷（准确性/一致性/版本/术语/安全）
                     否 -> 用户评分低但模型评分高（认知差异）
                        或问题本身有歧义（补同义问法与消歧）
```

判定优先使用确定性规则（如无检索结果、命中编号与所问不符、命中版本非现行、命中两份资料互相冲突等），仅在规则无法覆盖时交由大模型评委判断并标注为机器初判；判定为文档缺陷且严重度不低于 P1 时必须人工确认后方可开单。

**（3）算力侧：并发与吞吐测算。**

性能要求 P5（不少于 20 个用户并发）指的是**在线交互并发**，而非同时推理并发。按人均每分钟 1 次提问、单次生成 300 至 600 tokens 估算，稳态吞吐需求约为每秒 0.3 至 0.7 个请求；对话模型在国产加速卡上采用连续批处理后，单卡吞吐可满足该需求。首字延迟不超过 10 秒（P1）通过三项措施保证：限制单请求上下文体量（召回条数 6、片段长度受控）、对交互请求设置优先级队列（索引等后台任务降级）、对首字延迟做实时监控并在超阈值时自动限流。上述参数需在目标机实测后标定。

### 4.2 国产 ARM 与禁用容器条件下的全栈私有化部署

**技术难点。** 目标环境是国产 ARM64 平台、完全物理隔离的内网，且明确不使用容器。通用的容器化部署方案全部不可用，必须把平台及其全部依赖拆分到裸机上以原生进程方式运行。

**问题根因。** 一是依赖闭包极其庞大：服务端声明了 409 个直接与间接依赖，另有 41 个本地子包与 1 个源码协议依赖，合计需要 801 个包才能完整运行。二是二进制兼容性构成硬性门槛：实测扫描整棵依赖树的 456 个二进制文件，最高运行库需求为 2.28，而文档解析所需的推理运行时根本不提供低版本运行库的预编译包。三是官方镜像无法直接复用：各组件基础镜像并不统一，除前端因使用 musl 运行时可整棵迁移外，其余组件均因运行库版本过高而无法在国产化平台上直接运行。

**解决途径。** 采用“能复用官方产物就复用、不能复用就在目标机本地编译”的分层策略（见表 44）：前端运行时整棵复用官方构建产物；插件守护进程交叉编译为完全静态二进制；代码沙箱采用官方二进制与随包兼容运行时双路径；服务端采用便携运行时配合高兼容依赖树；数据库与中间件随包携带源码在目标机本地编译。同时按 aarch64 架构重建全部离线包，包内携带架构标记，安装脚本执行前比对，拿错架构的包立即报错终止。

**验证要点。** 离线包内全部二进制文件的架构标记一致；安装前环境合规判定一次性给出结论；部署后自检全部通过，其中代码沙箱一项通过真实执行一段代码验证。

### 4.3 单张 32GB 显存下的模型配置与能力取舍

**技术难点。** 系统需要在单张 32GB 显存加速卡上本地部署对话、嵌入、重排三类模型，同时满足问答质量、并发能力（不少于 20 用户）与首字延迟（不超过 10 秒）三项要求。显存既是硬约束，也是决定问答质量的直接变量。

**问题根因。** 显存需求由权重、KV 缓存与框架开销三部分构成，其中 KV 缓存随并发数与上下文长度增长，是运行时最不可控的部分。三类模型的资源特征差异很大：对话模型是重算力、在线型；嵌入与重排是低算力密度、可批量型。若不区分对待，要么把显存浪费在低算力模型上，要么为迁就显存而牺牲对话模型规模，直接拉低参数准确性与知识完备性。

**解决途径。** 第一，把“只检索不理解”带来的显存红利转化为能力：取消视觉与语音模型后释放约 10 至 12GB 显存，使三类模型可以全部常驻显卡，无需 CPU 卸载，也没有加载与卸载的抖动。第二，在“模型规模”与“上下文与并发预算”之间做显式取舍，形成两套配置（方案 A 质量优先、方案 B 余量优先），先按方案 B 部署并跑基准测试，再按实测结果决定是否切换到方案 A。第三，用三项工程手段控制 KV 缓存增长：按并发上限预分配显存、设置单请求最大上下文、对超长会话强制截断并提示用户新开会话。第四，为需求变更预留方案 C：若后续要求引入图片识别或视频转写，可在方案 B 基础上直接加载相应模型，不需要更换硬件。

**验证要点。** 部署自检包含显存容量识别与一次真实推理；基准测试记录首字延迟、吞吐与显存峰值；把最终选定的组合与并发参数写入部署文档，作为验收与运维依据。
### 4.4 文本深度解析管线在国产 ARM 平台落地

**技术难点。** 变体 RAGFlow 架构的核心价值在于“文档读得懂”，而深度文档解析依赖版面分析、表格识别等模型，这些模型在上游方案中通常以容器镜像形态分发，在禁用容器、ARM64、离线摆渡的条件下无法直接使用。

**问题根因。** 一是模型以容器镜像分发，镜像内的推理运行时依赖特定运行库版本与 CPU 架构；二是版面分析与表格识别模型的算子可能未被国产加速卡的推理框架充分支持，需要算子迁移；三是解析吞吐与显存预算相互制约，解析模型不能与对话模型长期争抢显存。

**解决途径。** 把解析能力从容器中“取出来”：模型权重与配置文件单独取出，通过统一推理接口加载；推理运行时按加速卡厂商框架适配，对不支持的算子采用 CPU 回退并统计回退比例；解析任务执行完毕后释放其占用的显存，把显存交还给对话、嵌入与重排模型；索引与批量解析安排在非工作时段批处理执行。同时保留后端可切换设计：若真机实测证明某类文档在变体管线下解析质量不足，可通过配置把该文档类别切换到上游解析后端，不影响其他环节。

**验证要点。** 取 2 份真实困难资料（含跨页参数表的 PDF）做对照解析，比对条款编号是否保留、表格是否错行、数值是否串行、页眉页脚是否污染；记录解析耗时与显存峰值；把结论写入部署文档。
### 4.5 异构数据的统一接入与元数据模型

**技术难点。** 需求要求“文本、图片、视频多模态数据的统一采集、管理和维护”。三类数据的处理方式完全不同，需要一套统一的元数据模型把它们纳入同一套管理链路，才能在同一个界面里完成台账、版本、检索与溯源。

**问题根因。** 文本类数据可以解析出正文并进入语义检索，图片与视频在本设计中不做内容理解，因而**不能产出正文**。如果简单地把它们排除在知识库之外，就不满足“统一采集、管理和维护”；如果把它们的文件名当作正文塞进向量库，又会污染检索结果并拉低评价指标。两者都不可取。

**解决途径。** 设计**双路径、单模型**的接入方式。双路径：文本走深度解析产出正文片段；图片与视频走浅度处理产出资产记录。单模型：两类对象共用同一套元数据字段命名（资料编号、版本号、现行状态、章节、页码、定位锚点、密级、内容指纹、可检索字段），使治理、台账、检索与评价四个环节可以用同一套逻辑处理两类对象，避免出现第二条管理链路。二者的差异被收敛为一个字段——**可检索字段**：文本的可检索字段是正文，资产的可检索字段是图注标题、人工标签、资产名称与所属章节。

**验证要点。** 7 种格式各上传一份，检查是否都在同一台账中可见、都可按资料编号与版本号归集、都可被定位；抽查 20 条资产，确认元数据字段完整且能正确定位到所属资料与章节。
### 4.6 图片与视频“只检索不理解”条件下的可检索化设计

**技术难点。** 需求要求图片与视频也能被统一管理并检索，但不做内容理解意味着系统没有画面文字、没有画面对应的时间轴文本，资产本身无法参与语义检索。如何让“不理解”的资产仍然找得到、找得准、能溯源？

**问题根因。** 平台的入库机制对多模态数据本身存在硬性限制（图片不能作为知识库文档直接上传，平台内也不存在图像或视频转文本的入库路径）；而即便绕开该限制，把资产作为独立单元入库，也会因为缺少可检索文本而无法被向量检索命中。真正可用的检索入口只有一个——**它所属的那段文本**。

**解决途径。** 采用“**依附式检索 + 元数据兜底**”两条路径：

（1）**主路径——附件挂载于片段。** 图片与视频不作为独立可检索单元，而是通过资产契约挂载到所属的文本片段上。用户在问到相关条款时，该条款片段被检索命中，其挂载的图片与视频作为**引用附件**随片段一并返回，界面以缩略图或文件链接呈现，并标注“资料编号、版本号、章节、页码、图序号”。这样资产的召回率直接继承文本片段的召回率，不需要任何内容理解。

（2）**辅路径——独立资产检索。** 对暂时找不到合适归属片段、或需要单独管理的资产（如现场照片、操作录像），通过资产名称、图注标题与人工标签建立独立检索入口，供资料管理员与用户按标签查找。该路径的召回效果取决于标注完整度，因此系统在资产台账中对未标注资产做醒目标记并定期提示补录。

**边界与取舍。** 本方案明确接受一个代价：**图片画面内的文字与视频中的语音、画面内容不进入语义检索范围**。若甲方要求对图片内容或扫描件建立语义检索，则必须重新引入光学字符识别或视觉理解能力，需相应调整显存预算（见 3.10.2）与工期。该事项已列入待确认清单。

**验证要点。** 通过资料编号、章节、图注标题与标签四种方式分别检索同一张图片与同一段视频，均应命中并正确定位；在回答中确认附件随片段返回且界面可预览；抽查未标注资产的补录提示是否正常产生。
### 4.7 条款级溯源的三个契约与版本硬过滤

**技术难点。** 需求要求回答显示文档出处并可回溯原文位置，同时要求版本时效性达标（作废版本数值不得进入回答）。

**问题根因。** 通用检索的引用粒度只到文档段，元数据过滤能力弱，无法在检索期按现行状态做硬过滤。若仅靠提示词约束，属于概率性控制；一旦作废版本片段被召回，模型可能引用旧值，而这类错误在装备场景中后果严重。此外，若元数据由引擎自行推断而非来自统一清单，会出现同一份资料在不同环节记录不一致的隐性错误。

**解决途径。** 三管齐下。第一，文档契约统一元数据来源：解析与索引服务不得自行推断元数据，内容指纹不一致即拒绝入库。第二，检索契约把资料编号、版本号、现行状态、章节路径、页码作为元数据随片段返回，并强制注入“现行有效”过滤条件，调用方不可放宽——把版本控制从提示词约束升级为检索层约束，使作废片段在物理上无法被召回。第三，引用契约统一引用标识格式（资料编号、版本号、章节、页码），界面高亮与评价判定使用同一依据，避免“界面显示的出处”与“评价依据的出处”不一致。

**设计原则。** 安全与版本两条红线，能用确定性手段就不用概率手段；引用标识由入库锚点原样带回，不由模型生成。

### 4.8 基于数据库的交互查询

**技术难点。** 需求要求实现“基于数据库的交互查询”，这是相对传统知识库问答系统新增的能力，需要把自然语言问题自动转换为查询语句并安全执行，且编排平台完全不具备该能力。

**问题根因。** 准确率方面，自然语言到查询语句的转换在字段名不规范、存在同义词、多表关联、时间范围表述模糊的情况下错误率显著上升，装备台账类数据往往表名与字段名为拼音缩写，进一步加大难度。安全方面，生成式模型可能产出删表、改数语句，或通过联合查询、子查询绕过权限限制读取越权数据。口径方面，同一问题在不同统计口径下答案不同。

**解决途径。** 自建数据库查询服务并设置六道防线（见表 31）；建立语义层，为每张表与每个字段维护业务语义描述与同义词表，提示词中注入精简表结构而非完整建表语句；服务在返回数据的同时返回结构化口径说明，由编排层组织进回答；维护少样本示例库并把高价值问题固化为模板查询。

### 4.9 多模态场景下的满意度指标体系重构

**技术难点。** 需求要求评价模型包括主观评价与客观评价 2 个维度、每个维度包括 3 个指标。而既有系统的主观维度只有 1 个指标（用户评分），不满足要求。

**问题根因。** 既有系统的主观维度仅通过点赞点踩或单值评价指令获取单个分数，客观上无法拆出 3 个主观指标；且不能要求用户每次评价都填 3 个分数，否则采集率会大幅下降；多模态回答的评价证据来源发生变化（图片类需要评价画面还原是否充分，视频类需要评价时间定位是否准确），原有的纯文本评价锚点不足以覆盖；指标键名变更会同时影响工作流回执格式、评测服务解析、数据库表结构与历史数据迁移。

**解决途径。** 重构为“主观 3 项 + 客观 6 项”两层结构（见表 35）：主观维度由“用户明说则采用、未明说则从语气与是否解决问题推断”的方式获取，把用户负担降到最低；客观维度由大模型评委给出，其中 3 项质量类指标合成客观指数，3 项装备域专项指标以红线、降级与坏例方式参与判定而不进入指数权重；在此基础上合成主客观指数与综合满意度指数，并保留红线降级与封顶规则。同时把指标键名集中定义、两侧派生，配套增量迁移脚本，避免改动扩散。

### 4.10 大模型微调与迭代闭环

**技术难点。** 需求要求“能够实现大模型的训练及优化”，即真正做微调而非仅做提示词优化，而可用的训练资源只有一张 32GB 显存加速卡。

**问题根因。** 训练与推理环境完全隔离，无法拉取任何模型权重、训练框架或加速运行时，素材必须离线入网；单卡 32GB 显存同时要承载推理服务与训练任务，资源冲突明显；训练数据来自标注工作流产出的问答对，标注质量直接决定微调效果；通用能力退化在领域微调中非常常见。

**解决途径。** 构建五步闭环：数据构造（按标签筛选高质量样本、构造指令与回答对、按比例混入通用语料）、训练（采用低频适配微调并配合梯度检查点与分页优化器，使 7B 至 14B 级模型在单卡 32GB 上可完成训练）、评测（黄金集回归，对比准确率、CSI 与红线触发率）、部署（权重合并后转为推理服务，工作流无需改动）、闭环（回归结果与用户评价回流到数据构造环节）。训练期间通过显存编排临时让出推理服务的部分常驻模型，训练任务安排在非工作时段执行。

**防退化设计。** 训练集混入通用语料；设置回归红线：微调后黄金集不得出现新增 P0，CSI 均值不得低于基线；不达标不允许上线，回退到“检索增强 + 提示词迭代 + 知识补全”路径。

### 4.11 受限沙箱下代码节点可靠性与跨文件数据契约一致性

**技术难点。** 评价工作流与标注工作流中的指标计算、质检逻辑运行在平台的代码沙箱中，沙箱出于安全考虑限制了系统调用、文件系统与网络访问；同时整套系统由工作流编排文件与本地评测服务两部分组成，两者通过字段名与文本格式通信，任一侧改动不同步会导致静默断裂。

**问题根因。** 沙箱是独立常驻服务，通过接口暴露执行能力，一旦不可用，评价链路与标注链路直接断掉；官方发布的沙箱二进制要求较高的运行库版本，在低版本系统上无法直接运行；沙箱不提供第三方库，代码节点只能用标准库。契约方面，评价回执采用键值对格式，评测服务用正则解析，字段名一旦变更解析即失败；这类断裂不报错——工作流照常返回回执，用户看不出异常，只是数据没进库，往往到生成报表时才发现。

**解决途径。** 沙箱方面：采用双路径运行（官方二进制与随包兼容运行时，按目标机运行库版本自动选择）；为沙箱单独部署一套运行时，与主服务解释器隔离；部署自检真实执行一段代码验证沙箱可用；代码节点全部逻辑仅依赖标准库。契约方面：编写跨文件契约测试，从工作流文件中提取回执模板并与评测服务解析函数做往返一致性验证；指标键名集中定义、两侧派生；数据库结构变更提供增量迁移脚本；导入前用静态校验器检查节点连线、变量引用、分支句柄与代码节点语法，把错误挡在导入之前。

## 5 风险分析

### 5.1 管理风险

> 本节按模板要求由甲方（九部）填写。乙方就已知情况给出以下提示，供甲方参考。

（1）**需求变更风险。** 本项目技术路线涉及变体 RAGFlow 架构与编排平台的融合，接口与契约较多，若实施过程中调整检索后端或增减资料类型，会直接影响契约与回归基线。应对：合同生效后 15 日内共同确认需求细化说明与实施计划；架构性变更走书面变更流程并评估工期与回归范围。

（2）**资料提供风险。** 系统效果高度依赖甲方提供的资料完整性与准确性（现行版本资料、版本台账、术语对照表、业务数据库只读账号）。应对：明确资料提供时限；资料未到位时先以样例语料推进平台与流程开发，避免阻塞排期。

（3）**验收组织风险。** 验收涉及功能、指标、质量三类判定，其中质量指标需要一定规模的运行数据才能统计。应对：把可提前验证的项（格式支持、解析成功率、参数配置、部署自检）安排在阶段里程碑处验收，把需要运行数据的项（满意度指标、坏例闭环）安排在试运行期统计。

（4）**人员与培训风险。** 系统交付后需由甲方人员自主运维与持续运营（资料维护、评价例会、整改跟踪、索引任务调度）。应对：交付时提供标准作业程序、部署与排障手册，并安排现场培训。

### 5.2 技术风险

（1）**运行库版本不达标导致无法部署。** 应对：部署前环境合规检查一次性判定；已明确最低运行库要求，可提前更换操作系统版本。

（2）**显存预算与实际不符导致模型降档。** 应对：准备方案 A（质量优先）与方案 B（余量优先）两套配置，先用方案 B 实测，余量充足且质量确有提升空间时再切方案 A；显存峰值与首字延迟纳入部署自检与日常巡检。

（3）**加速卡对解析模型算子支持不足。** 应对：对不支持的算子采用 CPU 回退并统计回退比例；解析任务执行完毕后释放显存，不与对话模型长期争抢。

（4）**飞腾平台单核性能有限导致索引与批量解析耗时偏长。** 应对：索引任务批处理化并安排在非工作时段；验收前按实际硬件实测标定并发参数。

（5）**资产标注不完整导致图片与视频召不回。** 这是“只检索不理解”边界下的主要质量风险：资产的可检索性完全依赖其图注标题与人工标签。应对：资产登记与资料入库同步进行；资产台账对未标注资产做醒目标记并定期提示补录；把资产召回情况纳入覆盖缺口清单统计。

（6）**扫描件资料正文无法进入语义检索。** 同理，扫描件在不做识别的前提下只能作为资产登记，其正文不可检索。应对：在待确认事项中与甲方明确该边界；若确有必要，对扫描件单独引入识别能力并按 3.10.2 重新核算显存与工期。

（7）**引擎切换期出现双源不一致。** 应对：坚持单一真源，切换期只允许一个引擎对用户提供服务，另一引擎仅做影子对比；入库以内容指纹为幂等键。

（8）**数据库查询准确率不达预期。** 应对：维护少样本示例库；口径复述让用户可判断；高价值问题固化为模板查询。

（9）**微调后通用能力退化。** 应对：训练集混入通用语料；设置回归红线，不达标不予上线，回退到检索增强与提示词迭代路径。

（10）**指标契约变更导致采集断链。** 应对：跨文件契约测试强制执行；指标键名集中化；增量迁移脚本。

（11）**用户评价采集率低。** 应对：对话内评价与原生反馈双通道；回执设计极简降低评价成本；试运行期规范引导话术。

## 8 结论

本设计报告依据《基于大模型的智能查询及基于用户评测反馈的闭环迭代技术研究》需求方案与双方确认的技术协议，结合甲方确定的**变体 RAGFlow 架构与 Dify 融合**技术路线、**国产 ARM（飞腾 3000 平台）与单张 32GB 显存加速卡**的硬件条件，以及**图片与视频只检索、不理解**的处理边界，完成了系统的总体设计、分模块设计与关键技术解决途径设计。

**主要结论如下：**

（1）**需求全覆盖。** 需求方案提出的 7 项功能要求与 12 项技术指标，在本设计中均有明确的实现方案与验证方式；满意度评价模型设计为主观 3 项加客观 6 项，满足并超出“2 个维度、每维度 3 个指标”的要求。

（2）**技术路线清晰可行。** 变体 RAGFlow 架构承担“文本读得懂、片段找得准、引用落得实”，Dify 承担“流程编排、会话管理、反馈采集”，两者通过检索契约层解耦，只保留三条接缝与四个契约。该形态既保留了深度解析与片段级检索的能力优势，又避开了容器化与重型依赖在国产 ARM 平台上的落地风险，并保留了后端可切换能力。

（3）**处理边界明确。** 文本类数据做深度解析与语义检索；图片与视频只做采集、登记、维护与检索呈现，不做光学字符识别、画面理解、视频抽帧与语音转写。资产以引用附件形式挂载在所属文本片段上随片段返回，定位信息完整可溯源。该边界使处理链路显著缩短、算力开销大幅下降，也避免了系统对无法核实的内容作出推断。

（4）**硬件约束有明确答案。** 由于无需部署视觉与语音模型，释放出约 10 至 12GB 显存，三类模型可全部常驻显卡：方案 B（14B 级 INT8）占用约 23 至 25GB、余量 7 至 9GB；方案 A（32B 级 INT4）占用约 26 至 29GB，问答质量提升一档。建议先按方案 B 部署并完成基准测试，再按实测结果决定是否切换。

（5）**边界带来的取舍已如实说明。** 图片画面内的文字与视频中的语音、画面内容不进入语义检索范围，扫描件资料的正文同样不可语义检索；资产的可检索性取决于其图注标题与人工标签的完整程度。系统通过资产台账标记与补录提示控制该风险，相关事项已列入待确认清单（见表 63 第 5、6 项）。

（6）**关键难点有解、风险可控。** 项目识别的 10 项关键技术难点全部按“中等”难度定级，均有成熟方法可循与明确解决途径；针对运行库门槛、显存预算、算子支持、平台性能、资产召回、引擎切换、单卡微调等主要风险均给出了应对措施与备选路径。

综上，本设计方案技术路线明确、与目标平台条件相容、处理边界清晰、工程可行、风险可控，满足需求方案与技术协议的各项要求，可作为后续研制实施的依据。
