### 难点一：隔离内网环境下无 Docker 的全栈私有化部署

#### 难点描述

课题要求「采取本地部署搭建涵盖知识库和数据库的 AI 大模型」，而目标运行环境是**完全物理隔离的内网**，
且明确**不使用 Docker**。这意味着官方推荐的容器化部署方案全部不可用，
必须把 Dify 及其全部依赖拆分到裸机上以原生进程方式运行。

#### 技术根因（实测证据）

1. **依赖闭包极其庞大**。Dify 1.17.1 的 api 服务声明了 409 个 PyPI 直接与间接依赖，
   另有 41 个 workspace 本地子包（向量库供应商 30 个 + 链路追踪供应商 8 个 + 智能体框架）
   和 1 个 git 协议依赖，总计需要 801 个包才能完整运行。

2. **二进制兼容性构成了硬性系统门槛**。实测扫描整棵依赖树的 456 个 ELF 文件，
   最高 glibc 需求为 **2.28**（由 `bcrypt` 的 `_bcrypt.abi3.so` 决定）；
   而 `onnxruntime==1.23.2`（文档解析能力所需）**根本不提供 manylinux_2_17 的 wheel**，最低仅到 `manylinux_2_27/2_28`。
   这直接决定了：**目标机 glibc 必须 ≥ 2.28，CentOS 7（glibc 2.17）无法部署**。

3. **官方镜像无法直接复用**。Dify 官方各组件基础镜像并不统一：
   `dify-api` 基于 Debian 12（glibc 2.36）、`dify-sandbox` 基于 Debian 13（glibc 2.41）、
   `dify-web` 基于 Alpine（musl）、`dify-plugin-daemon` 基于 Ubuntu 24.04（glibc 2.39）。
   除了 web 组件因使用 musl 而可以整棵迁移外，其余三个都因 glibc 版本过高而无法在国产化平台上直接运行。

#### 为什么是难点

- 依赖不是「装不上」而是「装上了也跑不起来」——版本解析成功与运行期可用之间存在 glibc 这道隐形门槛，
  且该门槛只在**实际扫描二进制符号版本**后才能发现，常规做法会到部署后期才暴露。
- 离线环境无法 `pip install` / `npm install`，必须预先构建完整离线包，这对构建机的工具链完备性提出要求。
- 国产化平台（银河麒麟 V10、统信 UOS）的 glibc 版本随 SP 版本变化，需要分层设计以覆盖多个版本。

#### 解决路径

采用「**能复用官方产物就复用、不能复用就在目标机本地编译**」的分层策略：

| 组件 | 处理方式 | 理由 |
| --- | --- | --- |
| Web 前端 | 整棵复用官方镜像产物（musl 运行时 + Next.js 构建结果） | 实测零 glibc 依赖，可在任何发行版运行 |
| 插件守护进程 | 交叉编译为完全静态二进制 | 纯 Go 无 CGO，实测产出零依赖静态可执行文件 |
| 代码沙箱 | 官方二进制 + 随包 glibc 双路径 | 官方二进制需 glibc 2.34，低版本系统用随包加载器运行 |
| API 服务 | 便携 Python 运行时 + manylinux_2_28 依赖树 | 便携 Python 实测仅需 glibc 2.17，与依赖树短板解耦 |
| PostgreSQL / Redis | 随包源码 + 便携工具链在目标机本地编译 | 保证与目标机 glibc 完全匹配 |

| --- | --- |

主要风险是目标机发行版与 SP 版本不确定导致 glibc 不达标。已内置环境探测脚本，

### 难点二：文本、图片、视频异构数据的统一解析与归一化

#### 难点描述

课题要求实现「文本、图片、视频的多模态解析处理方法」与「多模态数据的统一采集和维护」。
三类数据的解析方式完全不同，需要设计统一的中间表示，才能进入同一套知识库与检索链路。

#### 技术根因（实测证据）

对 Dify 1.17.1 源码做了完整的能力边界核查，结论是**平台原生能力缺口很大**：

| 能力 | 核查结论 | 证据 |
| --- | --- | --- |
| 文本类文档解析（pdf/docx/xlsx） | 原生支持 | 使用 pypdfium2 与自研提取器 |
| 图片 OCR | **完全不具备** | `pytesseract`/`tesseract`/`paddleocr` 全仓库零命中 |
| 扫描件 PDF 文字提取 | **完全不具备** | PDF 提取器只做文本层抽取，无「文本层为空则转 OCR」分支 |
| 视频抽帧 / 转码 / 关键帧 | **完全不具备** | `keyframe` 零命中，`ffmpeg` 仅出现在测试夹具中 |
| 视频语音转写 | 需外挂（平台侧仅有音频 STT 工具） | 视频文件不会被自动转写 |
| 视频作为模型输入 | **无证据支持** | 后端仅消费视觉（VISION）特征，视频/音频特征枚举存在但无消费代码 |

此外，**`avi` 格式根本不在平台白名单内**（白名单为 mp4/mov/mpeg/webm），
而课题技术指标明确要求支持 mp4 与 avi 两种视频格式。

#### 为什么是难点

- 三类模态需要三套解析引擎（文档解析、OCR + 视觉理解、抽帧 + 语音识别 + 关键帧理解），
  且都必须能在离线环境运行，不能调用任何云服务。
- 解析结果要归一化成同一套结构（文本 + 模态标记 + 定位锚点 + 版本元数据），
  否则下游检索无法统一排序与引用。
- 视频解析是全链路中计算最重的一环：一次 10 分钟视频的抽帧 + 转写 + 关键帧理解
  涉及数千次视觉推理调用，需要考虑抽帧策略与算力预算的平衡。

#### 解决路径

自建**多模态解析服务**，对上提供统一接口，对下封装三类解析引擎：

```
输入（文本 / 图片 / 视频）
   │
   ├─ pdf / docx / xlsx ──→ 原生提取器 ──→ 文本 + 表格结构
   ├─ jpg / png / 扫描 PDF ──→ OCR 引擎 + 视觉大模型 ──→ 文字 + 画面语义描述
   └─ mp4 / avi ──→ ffmpeg 抽帧 → ASR 语音转写 → 关键帧视觉理解
                                    ──→ 带时间轴的文本（时间戳 + 画面描述 + 台词）
   │
   └─→ 统一归一化：正文文本 + 模态标记 + 定位锚点 + 版本元数据
```

关键技术决策：
- **视频采用「抽帧 + 转写 + 关键帧理解」而非逐帧理解**，用关键帧检测把视觉推理调用量降低一个数量级。
- **avi 采用前置转码为 mp4 的方式解决**，同时向平台提交白名单补丁，双保险。
- **定位锚点统一设计**：文本用章节号、图片用区域描述、视频用时间戳，使回答可溯源到具体位置。

#### 工作量拆解

| 工作项 | 人·天 |
| --- | --- |
| 解析服务框架与统一接口设计 | 3 |
| 文档解析引擎集成与表格结构保留 | 2 |
| OCR 引擎选型、离线部署与中文识别调优 | 3 |
| 视频抽帧策略与关键帧检测实现 | 4 |
| 语音识别引擎离线部署与标点恢复 | 2 |
| 归一化中间表示与定位锚点设计 | 2 |
| **小计** | **16** |

#### 风险与备选

主要风险是老旧设备视频（低分辨率、抖动、无字幕）的解析质量。
备选方案是引入人工标注兜底：解析质量不达标的片段进入人工复核队列，由标注工作流标记待补。

### 难点三：图片与视频进入知识库的可行路径设计

#### 难点描述

课题要求多模态数据「统一采集、管理和维护」，隐含要求图片与视频也要能被检索。
但平台的入库机制对多模态数据存在硬性限制，需要设计绕行路径。

#### 技术根因（实测证据）

1. **图片不能作为知识库文档直接上传**。平台强制要求知识库来源的文件扩展名必须属于文档类型集合，
   而 jpg/png 不在该集合内，上传阶段即被拒绝。

2. **平台原生的图片向量索引链路门槛极高**：需要向量化模型本身声明视觉能力，
   且图片必须以「分段附件」的形式绑定到某个文本分段上，而不是作为独立文档存在；
   同时要求向量数据库支持多模态向量。在离线环境下要同时满足这三个条件代价很大。

3. **图片与视频没有平台内的入库转换路径**。核查确认平台不存在任何「图像转文本」「视频转文本」的入库逻辑。

#### 为什么是难点

- 这不是「配置一下就能解决」的问题，而是平台架构层面的能力边界，只能绕行。
- 绕行方案必须保留可追溯性——用户看到回答时要知道依据来自哪张图、视频的哪一段，
  否则「文档出处显示」这项功能要求无法满足。
- 归一化成文本后，模态信息不能丢失，否则无法统计各模态的覆盖情况与检索质量。

#### 解决路径

采用「**模态归一化 + 元数据留存 + 定位锚点**」的绕行方案：

| 原始模态 | 入库形态 | 保留的元数据 |
| --- | --- | --- |
| 文本资料 | 原文分段 | 资料编号、版本号、章节号 |
| 图片 | 结构化文本（OCR 文字 + 视觉描述） | 图片文件名、区域描述、来源资料 |
| 视频 | 带时间轴的结构化文本 | 时间戳、关键帧序号、原始文件名 |

每条入库文本都携带「模态类型 + 定位锚点」两个字段，检索命中后可还原出
「来自哪份资料的哪个位置」，满足文档出处显示要求。

| 工作项 | 人·天 |
| --- | --- |
| 入库路径设计与限制验证 | 2 |
| 模态元数据模型设计与实现 | 2 |
| 定位锚点回填与出处渲染 | 2 |
| 各模态入库效果验证与调优 | 2 |
| **小计** | **8** |

### 难点四：基于数据库的交互查询（NL2SQL）

#### 难点描述

课题要求「实现基于知识库的智能化检索和**基于数据库的交互查询**」。
这是相对传统知识库问答系统新增的能力，需要把自然语言问题自动转换为 SQL 并安全执行。

#### 技术根因（实测证据）

**平台完全不具备该能力**：
- `text2sql` / `nl2sql` / `text_to_sql` 在源码中零命中；
- 平台内置工具仅有 4 类（音频、代码、时间、网页抓取），无任何数据库类工具；
- 工作流节点类型共 32 种，无任何数据库或 SQL 节点。

因此必须完全自研，并通过 HTTP 节点接入。

#### 为什么是难点

- **准确率问题**：自然语言到 SQL 的转换在字段名不规范、存在同义词、
  多表关联、时间范围表述模糊的情况下错误率显著上升。装备台账类数据往往表名与字段名为拼音缩写，
  进一步加大难度。
- **安全问题**：生成式模型可能产出 `DROP`/`UPDATE`/`DELETE` 语句，
  或通过 `UNION`、子查询绕过权限限制读取越权数据，必须做严格的白名单与语法校验。
- **口径问题**：同一个问题（如「有多少台设备」）在不同统计口径下答案不同，
  必须让系统明确复述查询口径，否则用户无法判断结果是否符合预期。
- **结果转述问题**：查询结果需要转成自然语言，且不能改写数值、不能四舍五入。

#### 解决路径

自建 **NL2SQL 查询服务**，设置四道防线：

1. **Schema 语义层**：为每张表、每个字段维护业务语义描述与同义词表，
   在提示词中注入精简后的表结构，而不是完整 DDL，降低上下文长度与误判率。
2. **SQL 安全校验**：解析生成的 SQL，仅允许单条 `SELECT` 语句，
   禁止 DDL/DML，禁止多语句，强制附加行数上限与超时。
3. **只读账号 + 白名单**：数据库侧使用只读账号，同时对可查询的表做显式白名单，
   敏感字段（如人员信息）在服务层脱敏。
4. **口径复述**：服务返回结果时同时返回结构化口径说明，由大模型组织进回答中。

| 工作项 | 人·天 |
| --- | --- |
| Schema 语义层与同义词表构建（按实际表结构） | 4 |
| NL2SQL 提示词工程与少样本示例设计 | 3 |
| SQL 安全校验与白名单机制 | 3 |
| 查询结果转述与口径复述 | 2 |

### 难点五：多模态场景下的满意度指标体系重构

#### 难点描述

课题技术指标要求「满意评价指标包括主观评价与客观评价 2 个维度，每个维度指标不低于 3 个」。
而既有系统的指标体系是 5 项质量维度加权，其中**主观维度只有 1 个指标（用户评分）**，不满足要求。

#### 技术根因（实测证据）

- 既有系统的主观维度仅通过「用户点 👍/👎」或发送评价指令获取单个分数，客观上无法拆出 3 个主观指标。
- 主观指标的获取渠道必须扩展：要么让用户多打几项分，要么从用户的自由文本评价中自动抽取。
- 多模态回答的评价证据来源发生变化：图片类回答需要评价「画面还原是否充分」，
  视频类回答需要评价「时间定位是否准确」，原有的纯文本评价锚点不足以覆盖。

#### 为什么是难点

- **主观指标的可得性**：不能要求用户每次评价都填 3 个分数，否则采集率会大幅下降，
  必须在「默认从语气推断 + 用户明说时采用」之间取得平衡。
- **红线判定要重新设计**：安全合规性、版本时效性这些红线指标在多模态场景下的证据来源不同
  （例如图片中的仪表读数是否被正确识别），判定逻辑必须重新梳理。
- **指标改动会扩散**：指标键名变更会同时影响工作流回执格式、本地评测服务的采集解析、
  数据库表结构与历史数据迁移，必须整体规划。

#### 解决路径

重构为「**主观 3 项 + 客观 6 项**」两层结构：

**主观维度（3 项，来自用户）**

| 指标 | 键名 | 取值 | 获取方式 |
| --- | --- | --- | --- |
| 满意度 | `satisfaction` | 1-5 | 用户明说则采用，否则按语气映射 |
| 有用性 | `usefulness` | 1-5 | 用户明说则采用，否则按「是否解决问题」推断 |
| 体验感 | `experience` | 1-5 | 用户明说则采用，否则默认值，抱怨时降分 |

**客观维度（6 项，由大模型评委给出）**

| 指标 | 键名 | 取值 | 性质 |
| --- | --- | --- | --- |
| 事实准确性 | `factual_accuracy` | 1-5 | 质量 |
| 知识完备性 | `knowledge_completeness` | 1-5 | 质量 |
| 相关性 | `relevance` | 1-5 | 质量 |
| 安全合规性 | `safety_compliance` | 0-5（0 = 不涉及） | 红线 |
| 版本时效性 | `version_currency` | 0-5（0 = 不涉及） | 红线 |
| 术语规范性 | `terminology_norm` | 1-5 | 专项 |

在此基础上合成两级指数：主观指数 SSI、客观指数 OSI，加权得到综合满意度指数 CSI，并保留红线降级规则。

### 难点六：大模型微调（LoRA/SFT）与迭代闭环

#### 难点描述

课题要求「能够实现大模型的训练及优化」，且明确要**真正做微调**，而非仅做提示词优化。
这要求构建完整的数据构造 → 训练 → 评测 → 上线闭环。

#### 技术根因（实测证据）

- 训练与推理环境是**完全隔离的内网**，无法拉取任何模型权重、训练框架或 CUDA 运行时，
  所有素材必须离线入网。
- 微调需要 GPU，而原有部署方案（纯 CPU 的 Dify 平台）中**完全没有 GPU 相关规划**，
  需要新增 GPU 服务器、驱动、CUDA、PyTorch 全套离线环境。
- 训练数据必须来自标注工作流的产出，标注质量直接决定微调效果，两者存在强耦合。

#### 为什么是难点

- **数据构造**：需要从标注产出的问答对中筛选、去重、构造指令微调格式，
  还要保证训练集与评测集不重叠，否则评测结果虚高。
- **效果验证**：微调后的模型必须通过黄金集回归验证**没有退化**，
  而通用能力退化在领域微调中非常常见，需要设计混合训练策略。
- **上线切换**：微调模型要与原模型做 A/B 对比，且推理服务要能在内网提供 OpenAI 兼容接口，
  否则 Dify 侧无法接入。
- **闭环周期**：从用户评价 → badcase 挖掘 → 数据补全 → 微调 → 回归 → 上线，整个周期要可重复执行。

#### 解决路径

构建五步闭环：

1. **数据构造**：从标注工作流输出的问答对中，按标签筛选出高质量样本，
   构造指令-回答对；同时混入一定比例的通用语料防止能力退化。
2. **训练**：采用 LoRA 低秩微调，显著降低显存需求，使单卡即可完成训练。
3. **评测**：使用黄金测试集做回归，对比微调前后的准确率、CSI、红线触发率三项指标。
4. **部署**：将 LoRA 权重合并后转换为推理服务，对内提供 OpenAI 兼容接口，
   Dify 通过模型插件接入，无需改动工作流。
5. **闭环**：将回归结果与用户评价回流到数据构造环节，形成迭代。

#### 工作量拆解

| 工作项 | 人·天 |
| --- | --- |
| GPU 环境离线部署（驱动/CUDA/PyTorch） | 4 |
| 训练数据构造与清洗流水线 | 3 |
| LoRA 微调脚本与训练调参 | 3 |
| 评测集构建与回归对比工具 | 3 |
| 模型合并、推理服务部署与平台接入 | 3 |
| **小计** | **16** |

#### 风险与备选

主要风险是微调效果不达预期或通用能力退化。备选方案是退回到
「检索增强 + 提示词迭代 + 知识库补全」的优化路径，仍可满足功能要求中的「训练及优化」表述，
但效果上限低于真实微调。**建议优先按真实微调推进。**

### 难点七：沙箱受限环境下的工作流代码节点可靠性

#### 难点描述

评价工作流与标注工作流中的指标计算、质检逻辑都运行在平台的**代码沙箱**中，
沙箱出于安全考虑限制了系统调用、文件系统与网络访问，代码节点必须在这一约束下可靠运行。

#### 技术根因（实测证据）

- 代码沙箱是**独立的常驻服务**，通过 HTTP 暴露执行接口，工作流的代码节点依赖它才能执行；
  沙箱不可用会直接导致评价链路与标注链路断掉。
- 沙箱依赖系统调用过滤库，且官方发布的二进制**要求 glibc ≥ 2.34**，
  在较低版本的系统上无法直接运行。
- 沙箱需要独立的 Python 解释器执行用户代码，该解释器路径可配置，但必须真实存在，否则服务启动即失败。

#### 为什么是难点

- 沙箱是安全机制，不能为了兼容性而降低安全等级（例如直接关闭系统调用过滤）。
- 代码节点是评价与标注的**唯一计算载体**，一旦不可用，整个迭代闭环断裂。
- 平台不提供沙箱内部的第三方库，代码节点只能用标准库，这限制了实现方式
  （例如不能依赖外部分词库、不能联网查表）。

#### 解决路径

- **双路径运行**：官方二进制 + 随包携带的兼容运行时，自动根据目标机 glibc 版本选择，
  既不在新系统上引入额外复杂度，也不在老系统上牺牲可用性。
- **解释器隔离**：为沙箱单独部署一套 Python 运行时，与主服务解释器隔离，
  代码节点无法导入主服务的内部依赖，避免越权访问。
- **自检前置**：部署自检脚本会**真实执行一段代码**来验证沙箱可用，
  而不是仅检查端口，避免「服务在跑但实际不可用」的假阳性。
- **纯标准库实现**：代码节点全部逻辑仅依赖 Python 标准库，保证在沙箱内可运行。

#### 工作量拆解

| 工作项 | 人·天 |
| --- | --- |
| 沙箱双路径适配与启动包装 | 2 |
| 独立解释器部署与依赖隔离 | 2 |
| 代码节点逻辑实现与边界处理 | 2 |
| **小计** | **6** |

### 难点八：DSL 与评测服务之间的跨文件数据契约一致性

#### 难点描述

整套系统由**工作流编排文件**与**本地评测服务**两部分组成，两者通过约定的字段名与文本格式通信。
任一侧改动不同步，链路就会静默断裂——系统看起来正常，但数据采集不到。

#### 技术根因（实测证据）

- 用户评价通过工作流生成的回执文本传回，回执格式采用键值对
  （形如 `[[EVAL_RECEIPT]]satisfaction=4,usefulness=4,experience=3,suggestion=...[[/EVAL_RECEIPT]]`）。
  评测服务用正则解析该格式，**字段名一旦变更，解析即失败**。
- 评价工作流输出的指标键名、本地数据库表的列名、报表字段三者必须一致。
- 本次指标重构（主观 1 项扩展为 3 项）就同时影响了：
  工作流回执模板、评测服务解析函数、数据库表结构、历史数据迁移四处。

#### 为什么是难点

- 这类断裂**不报错**：工作流照常返回回执，用户看不出异常，只是数据没进库，
  往往在生成报表时才发现，排查成本高。
- 契约横跨 YAML 与 Python 两种语言、两个文件，没有类型系统约束。
- 指标体系会随课题推进持续调整，契约变更不是一次性问题而是常态。

#### 解决路径

- **契约测试**：编写跨文件的契约测试，从工作流文件中提取回执模板，
  与评测服务的解析函数做往返一致性验证，任何一侧改动都会立刻让测试失败。
- **单一事实来源**：指标键名集中定义，工作流与评测服务均从同一处派生。
- **迁移脚本**：数据库表结构变更提供增量迁移，旧库无需重建。
- **静态校验前置**：导入前用静态校验器检查节点连线、变量引用、分支句柄、
  代码节点语法与模板语法，把错误挡在导入之前。

| --- | --- |
| 契约测试用例编写与维护 | 3 |
| 指标键名集中化与两侧派生改造 | 2 |
| 数据库迁移脚本与历史数据转换 | 2 |
| 静态校验器增强 | 1 |
| **小计** | **8** |

## 4. 难度定级的补充说明

本项目全部难点定级为「中」，理由如下：

1. **技术路径明确**：8 个难点所涉及的核心技术——离线依赖治理、OCR、语音识别、
   视频关键帧理解、检索增强生成、NL2SQL、LoRA 微调、契约测试——**均为业界成熟方法**，
   不存在需要理论突破的环节。

2. **难点来自组合而非单点**：单个技术不难，难在**把它们在完全隔离的内网、不使用容器的前提下组合起来**。
   例如「多模态解析」本身不难，但要求「离线运行 + 中文识别 + 保留时间轴定位 + 接入知识库检索」
   同时满足，就构成了实质工作量。

3. **风险可识别、可兜底**：每个难点都给出了主要风险与备选方案，
   最坏情况下仍能满足课题的功能与指标要求，不存在「做不出来导致课题失败」的路径。

4. **工作量真实且可度量**：本文档的工作量估算基于已完成的前期验证工作，
   全部 8 个难点均已产出可运行的原型或完成技术验证，不是纸面推演。
