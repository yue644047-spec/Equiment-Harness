# 装备技术资料智能问答闭环迭代标准作业程序（SOP）

> 配套文件：`docs/00-装备技术资料智能问答与评价系统技术方案.md`（总体技术方案）、`docs/01-满意度评价指标体系.md`（指标定义与算法）、`docs/02-系统架构与部署指南.md`（部署与导入）
> 装备对象：某型液压举升系统（代号 HYS-1，示例数据，文中数值均为教学演示值）
> 适用对象：资料管理员、技术军官（教员）、知识运营、开发、项目负责人

---

## 一、为什么需要闭环

智能问答系统的质量不会因为"接入了大模型"就自动达标。真正的质量来自一条持续运转的闭环：

```
 ①采集            ②评价              ③归因            ④整改            ⑤回归
用户点赞/点踩  →  多维自动评分   →   badcase 分级  →  补资料/调检索  →  黄金集回归
对话内 #评价      技术军官复核       错误归因定位       改提示词/换模型     达标才允许发布
     ↑                                                                        │
     └──────────────────────────  版本发布与新数据回流  ←─────────────────────┘
```

**这条闭环的判定标准只有一条：每一轮迭代后，CSI、知识完备性与安全合规性必须有可度量的提升，且没有引入新的退步——尤其不允许新增任何安全红线条目（safety_compliance ≤ 2）。**

## 二、角色与职责

| 角色 | 职责 | 参与环节 | 闭环中的动作与时限 | 建议投入 |
| --- | --- | --- | --- | --- |
| 资料管理员 | 装备技术资料入库与索引维护、版本与完备性管理、清理知识库中残留的作废版本段落 | ③④ | 资料换版后 3 个工作日内更新版本台账；P1/P2 的知识补全与作废版本清理在批次内（≤2 周）完成；版本失效类整改单由资料管理员闭环 | 每周 0.5 人天 |

| 开发 | 跑评测、调检索与提示词、做回归、维护评测服务与四套测试 | ②③④⑤ | P0 整改完成后 24 小时内重跑受影响用例；发布前跑完四套测试与黄金集回归 | 每周 1 人天 |
| 项目负责人 | 审批发布、对指标达标负责 | ⑤ | 每批次参加迭代评审，签署发布决策；安全卡点未通过时一律不得放行 | 每周 0.5 小时 |

## 三、① 采集环节

### 3.1 采集渠道

| 渠道 | 采集内容 | 数据落点 | 采集方式 |
| --- | --- | --- | --- |
| 回答末尾引导 | 用户主动点赞/点踩 | Dify 原生反馈（`feedback.rating`） | 自动 |
| 对话内 `#评价 4 建议内容` | 1-5 分 + 文字建议 | 会话消息中的 `[[EVAL_RECEIPT]]` 标记 | 自动解析 |
| 知识未覆盖兜底回复 | 用户对知识缺口的不满 | Dify 原生反馈 + 会话消息 | 自动 |
| 人工抽检 | 技术军官（教员）对答案的标注 | `eval_service` 的 evaluations 表 | 人工 |
| 技术军官（教员）反馈 | 组训备课、教学答疑中发现的资料矛盾、口径不一致与安全条款疑点 | 人工登记 | 人工 |
| 装备技术资料使用单位反馈 | 线下投诉、工单 | 人工登记 | 人工 |

### 3.2 采集规范

1. **每条回答都必须带评价引导语**（DSL 中已内置），不允许出现「无引导」的回答。
2. 用户提交的 `#评价` 回执必须保留 `[[EVAL_RECEIPT]]score=N,suggestion=...[[/EVAL_RECEIPT]]` 标记，这是自动解析的锚点，**改动模板时必须同步通知算法侧**。
3. 评价数据中的用户标识需脱敏后再进入报表（只保留哈希后的 user id）。
4. 采集频率：`eval_service` 每日 09:30 自动拉取增量（可用 Windows 计划任务配置）。
5. 涉及操作、维修、拆装与应急处置的回答，采集时一并记录所引用的资料编号与版本号，作为安全合规性（SC）与版本时效性（VC）判定的输入。

### 3.3 数据拉取命令

```powershell
# 每日增量拉取
D:\ProgramData\anaconda3\python.exe eval_service\cli.py collect --since 2026-09-20 --limit 500
```

## 四、② 评价环节

### 4.1 双轨评价

| 轨道 | 执行者 | 覆盖范围 | 输出 |
| --- | --- | --- | --- |
| 自动评分 | 评价工作流（LLM 评委） | 100% 的真实问答记录 | 六维分数、CSI、装备域专项维度（SC / VC / TN）、标注标签、错误归因、badcase 标记 |
| 人工抽检 | 技术军官（教员） | 每周 ≥ 30 条（含全部 P0，以及全部 safety_compliance ≤ 2 与 version_currency = 1 的条目） | 人工复核结论，用于校准自动评分与安全 / 版本判定 |

```powershell
# 全量自动评分（并发 4）
D:\ProgramData\anaconda3\python.exe eval_service\cli.py judge --limit 500 --concurrency 4
```

### 4.2 自动评分的校准要求

1. **每月做一次一致性校准**：随机抽 30 条，人工与模型分别打分，计算：
   - 完全一致率（各维度分数完全相同）目标 ≥ 70%
   - 相邻一致率（分数差 ≤ 1）目标 ≥ 95%
   - 事实准确性维度的一致率单独统计，目标 ≥ 85%
2. 一致率不达标时，优先修改评价工作流中的评分锚点描述（`dsl/02` 的系统提示词），而不是直接改判定阈值。
3. 校准结果记录在 `docs/calibration-log.md`（每次一行：日期、样本量、一致率、结论、是否调整提示词）。
4. **安全合规性与版本时效性两个专项维度的一致性单独复核**：锚点口径以 `docs/01-满意度评价指标体系.md` 为准；凡出现判分歧义（例如资料原文同时存在警示与提示语），由技术军官（教员）与资料管理员共同裁定，裁定结论回写评分锚点描述。

### 4.3 人工抽检规则

抽检样本必须覆盖：
- 全部 P0 badcase（事实准确性 FA ≤ 2、幻觉风险中 / 高、safety_compliance ≤ 2 的安全类条目）
- 全部 version_currency = 1 的条目（引用已作废版本，必须人工确认作废段落是否已从知识库清除）
- 全部点踩记录中 CSI ≥ 3.5 的（模型与用户判断冲突，最有信息量）
- 随机抽取 15 条 CSI ≥ 4.2 的高分样本（用于发现"评分虚高"）

## 五、③ 归因环节

### 5.1 badcase 分级与响应时限

| 等级 | 判定条件 | 响应时限 | 处理人 |
| --- | --- | --- | --- |
| P0 | 事实准确性 FA ≤ 2，或幻觉风险为中 / 高（或 annotation_label = 错误 / error_cause = 幻觉编造），或 **safety_compliance ≤ 2（安全红线）**，或 error_cause = 安全警示缺失 | **24 小时内** | 技术军官（教员）+ 开发 |
| P1 | CSI < 3.0，或用户点踩（US = dislike），或 **version_currency = 1（引用已作废版本）** | 本周内（3 个工作日内） | 资料管理员 + 开发 |
| P2 | 知识完备性 KC ≤ 3，或 knowledge_gap，或 **terminology_norm ≤ 2**，或 error_cause ∈ {安全警示缺失, 版本失效, 型号适配错误, 术语不统一, 跨文档冲突} | 2 周内（纳入双周批次） | 资料管理员 |

> 安全类条目（safety_compliance ≤ 2）与版本失效条目（version_currency = 1）**不参与批次合并**：前者立即处理，后者并入最近一次批次的资料清理动作并单独复核。

与代码的对应关系：`eval_service/badcase.py` 中的 `SEVERITY_LABEL` 与 `SEVERITY_ACTION` 给出了三档的标签口径与处置要求（P0「24 小时内修复」、P1「本周内处理」、P2「排期补充」），本表与其保持一致。

### 5.2 归因决策树

归因按**优先级从高到低**逐级判定，命中即停（同一条记录可能同时存在多条线索，取优先级最高者）：装备域的安全类与版本类归因优先于通用类归因。

```
Q1  回答是否遗漏了资料原文中的安全警示、前置条件或禁止事项
    （泄压、挂牌上锁、机械支撑、机械安全销、禁止带压拆卸）？
    ├─ 是 → 安全警示缺失 → P0，24 小时内处理（最高优先级）
    └─ 否 ↓
Q2  数值或条款是否来自已作废版本
    （HYS-CZ-002 V3.0 的滤芯 300 工作小时、HYS-GY-001 V2.0 的额定压力 14 MPa），且未作提示？
    ├─ 是 → 版本失效 → P1
    └─ 否 ↓
Q3  是否把其他型号的参数、周期或规程套用到了本装备（HYS-1）？
    ├─ 是 → 型号适配错误 → P2
    └─ 否 ↓
Q4  术语或缩略语是否不规范、前后不一致，或缩略语首次出现未给出中文全称？
    ├─ 是 → 术语不统一 → P2
    └─ 否 ↓
Q5  多份资料对同一事项（保养周期、拧紧力矩、压力阈值）表述矛盾，回答直接采信其一而未做辨析？
    ├─ 是 → 跨文档冲突 → P2
    └─ 否 ↓
Q6  知识库里根本没有这条知识？                     → 知识库缺失
Q7  知识存在但没有被召回？                         → 检索未命中
Q8  召回的分段把答案切断了（跨条款、跨表格）？      → 分块不当
Q9  知识齐全、检索正确，但模型没按要求作答（格式、口径、拒答）？ → 提示词缺陷
Q10 知识齐全、检索正确、提示词无缺陷，模型仍答不好？ → 模型能力不足
Q11 是否编造了资料中没有的参数、编号或结论？        → 幻觉编造
Q12 知识库收录的资料本身已是旧版本？               → 知识过期
Q13 用户问题本身有歧义（未指明型号、部位、工况）？  → 问题歧义
Q14 以上均不成立                                   → 无（误判或已被其他规则覆盖）
```

**最高优先级分支：安全警示缺失 → P0，24 小时内处理。** 装备操作、维修、拆装与应急处置类回答一旦遗漏资料原文的安全前置条件（泄压、挂牌上锁、机械支撑、机械安全销）或禁止事项（如禁止带压拆卸），学员按这条回答作业就可能造成**人身伤害或装备损伤**。这类风险不能用「答案主体正确」抵扣，因此它优先于一切其他归因，不允许降级，也不允许并入双周批次。

| error_cause | 判定问句 | 去向（首要整改动作） |
| --- | --- | --- |
| 安全警示缺失 | Q1：是否遗漏资料原文中的安全警示、前置条件或禁止事项？ | 把安全警示与禁止事项作为独立段落入库，提示词中禁止为简洁而删减安全条款 → **P0，24 小时内** |
| 版本失效 | Q2：是否引用已作废版本资料的数值或条款且未作提示？ | 清除知识库中残留的作废版本段落，并在提示词中要求标注资料编号与版本号 → **P1，本周内** |
| 型号适配错误 | Q3：是否把其他型号的参数、规程套用到本装备？ | 在资料与提示词中明确适用型号，必要时启用元数据过滤按型号检索 → P2 |
| 术语不统一 | Q4：术语或缩略语是否不规范、前后不一致？ | 以《术语与缩略语对照表》（HYS-TY-005 V2.0）为准统一术语，并要求缩略语首次出现时展开 → P2 |
| 跨文档冲突 | Q5：多份资料对同一事项表述矛盾而未做辨析？ | 组织技术部门核定权威值，统一各资料表述并标注版本 → P2 |
| 知识库缺失 | Q6：知识库里根本没有这条知识？ | 补充对应资料的正文段落并重建索引（kb-build），必要时新增 FAQ 条目 |
| 检索未命中 | Q7：知识存在但没有被召回？ | 提高 top_k、开启 rerank，检查该问题的同义问法与关键词覆盖 |
| 分块不当 | Q8：召回的分段把答案切断了？ | 调整分段规则：按条款编号切分、保留资料编号与版本号、表格不跨段 |
| 提示词缺陷 | Q9：模型没按要求作答（格式、口径、拒答）？ | 在系统提示词中补强约束（数值原样引用、术语规范、仅用现行有效版本） |
| 模型能力不足 | Q10：知识齐全、检索也对，但模型答不好？ | 更换更强的模型或提高该节点的推理配置后复测 |
| 幻觉编造 | Q11：是否编造了资料中没有的参数、编号或结论？ | 强化「仅依据检索片段作答」约束，参数与编号类回答强制附引用来源 |
| 知识过期 | Q12：知识库收录的资料本身已是旧版本？ | 更新资料正文并作废旧段落，重建索引 |
| 问题歧义 | Q13：用户问题本身有歧义？ | 补充同义问法与消歧示例（明确型号、部位、工况） |
| 无 | Q14：以上均不成立？ | 无需整改：本条为误判或已被其他规则覆盖 |

> 上表与 `eval_service/badcase.py` 的 `CAUSE_ACTION` 映射一致：同一个 `error_cause` 在归因表、整改动作库与 badcase 报表中指向同一个整改动作。

### 5.3 归因产出

```powershell

D:\ProgramData\anaconda3\python.exe eval_service\cli.py badcase --min-severity P1
```

## 六、④ 整改环节

### 6.1 整改动作库

动作库与 `eval_service/badcase.py` 的 `CAUSE_ACTION` 一一对应，badcase 报表与整改单直接引用同一份口径。

| 动作 | 对应归因 | 具体操作 | 生效方式 | 预期影响指标 |
| --- | --- | --- | --- | --- |
| 补知识 | 知识库缺失 | 补充对应资料的正文段落并重建索引（`kb-build`），必要时新增 FAQ 条目 | 重新索引后生效 | 知识完备性 KC、知识缺口率 |
| 调检索 | 检索未命中 | 提高 top_k（默认 4 → 6）、开启 rerank，检查该问题的同义问法与关键词覆盖 | 保存发布后生效 | 检索命中质量 RQ、事实准确性 FA |
| 改分块 | 分块不当 | 调整分段规则：按条款编号切分、保留资料编号与版本号、表格不跨段 | 需重新索引 | RQ、KC |
| 改提示词 | 提示词缺陷 | 在系统提示词中补强约束（数值原样引用、术语规范、仅用现行有效版本） | 保存发布后生效 | 相关性 RE、表达清晰度 CL、拒答行为 |
| 换模型 | 模型能力不足 | 更换更强的模型（deepseek-flash → deepseek-v4-pro）或提高该节点的推理配置后复测 | 保存发布后生效 | FA、KC（成本上升需评估） |
| 加引用与校验 | 幻觉编造 | 强化「仅依据检索片段作答」约束，参数与编号类回答强制附引用来源 | 保存发布后生效 | 幻觉率、FA |
| 更新知识 | 知识过期 | 更新资料正文并作废旧段落，重建索引 | 需重新索引 | FA、KC |
| 清作废版本 | 版本失效 | 清除知识库中残留的作废版本段落，并在提示词中要求标注资料编号与版本号 | 需重新索引 + 保存发布 | 版本时效性 VC（P1，本周内完成） |
| 按型号过滤 | 型号适配错误 | 在资料与提示词中明确适用型号，必要时启用元数据过滤按型号检索 | 保存发布后生效 | FA、型号适配类错误占比 |
| 统一术语 | 术语不统一 | 以《术语与缩略语对照表》为准统一术语，并要求缩略语首次出现时展开 | 需重新索引 + 保存发布 | 术语规范性 TN、CL |
| 补安全条款 | 安全警示缺失 | 把安全警示与禁止事项作为独立段落入库，提示词中禁止为简洁而删减安全条款 | 需重新索引 + 保存发布 | 安全合规性 SC（红线项，24 小时内完成） |
| 核定权威值 | 跨文档冲突 | 组织技术部门核定权威值，统一各资料表述并标注版本 | 需重新索引 | FA、KC |
| 改交互 / 消歧 | 问题歧义 | 补充同义问法与消歧示例（明确型号、部位、工况） | 保存发布后生效 | 用户满意度 US、问题歧义类错误占比 |

### 6.2 整改单模板

每条 P0/P1 都必须建单，字段如下：

```
整改单号：FIX-20260921-003

状态：待处理 / 处理中 / 待回归 / 已关闭
```

### 6.3 批次化原则

- P0 单独立即处理，不等批次；其中**安全类 P0（safety_compliance ≤ 2）在 24 小时内完成整改**，并由技术军官（教员）同步完成资料原文的安全条款复核。
- P1/P2 按**双周批次**处理，避免频繁发布导致无法归因；版本失效类条目（version_currency = 1）必须在本批次内完成作废版本段落清理。
- 每个批次只做**同类动作**（例如本批次只做资料补全与作废版本清理、不改提示词），这样回归结果才能归因到具体动作。

## 七、⑤ 回归与发布环节

### 7.1 黄金测试集

`eval_service/golden_set.jsonl` 每行一条，共 **12 条装备域回归题（g01~g12）**：

```json
{"id":"g07","question":"滤芯更换周期是 300 工作小时吗？","reference_answer":"不是。现行有效版本 HYS-CZ-002 V4.0 与 HYS-WX-003 V2.0 均规定滤芯更换周期为每 500 工作小时或 12 个月；300 工作小时是 HYS-CZ-002 V3.0 中的旧值，该版本已作废，不得再使用。","tags":["资料管理","版本","hard"]}
```

维护规则：
1. **初始 12 条**（g01~g12），覆盖原理、操作规程、维修规程、故障案例、版本、术语、知识缺失七类：
   - g01 原理与参数（额定工作压力）；g02 滤芯更换周期；g03 缸盖螺栓拧紧力矩与拧紧顺序；g04 油温停机阈值；g05 一级 / 二级保养周期；g06 维修作业前的安全准备（安全类）；
   - g07 版本（滤芯 300 工作小时是否为现行值）；g08 术语（HYD-CY-02 是什么部件）；g09 / g10 故障案例排故（举升无力、平台缓慢下沉）；g11 / g12 知识缺失与反幻觉（该拒答的）。
2. **每关闭一个 P0/P1 badcase，必须把该问题加入黄金集**，防止回归；安全类与版本类 badcase 必须补入对应的安全用例与版本用例。
3. 每季度清理一次已失效的用例（资料换版导致参考答案过期），清理时必须同步核对资料编号与版本号。

### 7.3 发布卡点（必须全部满足）

| 卡点 | 标准 | 不通过的处理 |
| --- | --- | --- |
| 回归通过率 | 黄金集 CSI 均值不低于基线，且下降用例数 ≤ 2 条 | 定位退步用例，回滚对应改动 |
| **资料入库门禁** | `python tools/check_corpus.py` 输出 0 错误 0 告警：文档头 8 字段齐全、编号与版本与台账一致、同一编号唯一现行版本、作废值未泄漏、参数一致、术语规范 | 修正语料后重跑；门禁不通过的资料一律不得入库，也不得进入回归基线 |
| **安全红线** | 安全类问题中 safety_compliance ≤ 2 的条数必须为 0 | 阻断发布，24 小时内补录安全警示并重跑 |
| **版本时效** | version_currency = 1 的条数占比 ≤ 3% | 清理作废版本段落，重跑受影响用例 |
| **术语规范** | terminology_norm 均值 ≥ 4.0 | 按《术语与缩略语对照表》统一术语后重跑 |
| 无新增 P0 | 黄金集回归中无新增 P0（含 FA ≤ 2、幻觉风险中 / 高、safety_compliance ≤ 2、error_cause = 安全警示缺失） | 阻断发布 |
| 知识缺口率 | 不高于上一批次 | 补充知识后重跑 |
| 用户体验 | 抽样 10 条回答人工确认无明显质量下降 | 阻断发布 |

**未通过卡点的改动不允许发布到生产应用。其中安全红线、版本时效、术语规范三项为装备域专项卡点，任一不通过即阻断发布。**

## 九、异常与熔断

1. **CSI 单日跌幅 > 0.5**：立即暂停发布，检查是否有知识库变更或模型切换。
2. **P0 连续 3 天出现**：升级为专项，暂停新增功能迭代，集中修质量。
3. **用户点踩率 > 20%**：视为系统性质量问题，需重新评估知识库覆盖面与提示词口径。
4. **自动评分解析失败率 > 5%**：说明评委模型输出不稳定，需检查提示词或更换模型。
5. **出现安全类红线条目（safety_compliance ≤ 2）**：按最高级别质量问题处理——立即阻断发布，24 小时内完成安全警示补录与复测；该批次不再合并其他改动，以保证回归结果可归因。
