## 0. 一句话目标（判据）

把问答当**文档质量探针**：每条回答必须可追溯到「资料编号 + 版本号（+ 条款号）」，由用户与自动评委共同判定**当前引用资料是否健全、是否合规**；
低分与缺陷经**归因前置**分流到「资料」或「系统」两侧，资料侧产出**记分卡 + 缺陷整改单 + 闭环率**，并驱动资料补全与版本治理。

判据（验收时只看这三样）：① 引用可追溯到资料/版本/条款；② 文档缺陷有证据链并能派单闭环；③ 口径与阈值可从文档和代码两侧自证一致。

## 2. 冻结口径清单（动这些 = 动验收，必须先改文档再改代码）

1. **CSI**：`0.30×US + 0.25×FA + 0.20×KC + 0.15×RE + 0.10×CL`；无用户评分时 `(0.25FA+0.20KC+0.15RE+0.10CL)/0.70`。
2. **四档判定**：优秀 ≥4.2、良好 ≥3.5、待改进 ≥2.8、不合格 <2.8；红线优先（FA≤2、SC≤2 直接不合格；VC=1 最多待改进）。
3. **维度分工**：FA/KC/RE/**CL** 进 CSI；SC/VC/TN 为装备域专项维度，**不进权重**，以红线与降级参与判定。
4. **badcase 语义**：布尔（`metrics.is_badcase`）；P0/P1/P2 由 `metrics.severity_of` 派生。工作流不得再输出 P0/P1/P2 字符串。
5. **评价回执契约（v2）**：
   `[[EVAL_RECEIPT]]satisfaction=N,usefulness=N,experience=N,suggestion=<原文>[[/EVAL_RECEIPT]]`
   v1 的 `score=`、历史 JSON、纯文本回退仅作兼容。
6. **主观三项**：满意度 / 有用性 / 体验感（1–5）；**缺项传空串 = 未评分**（不参与 SSI，不记 0 分）。
7. **标注标签**：正确 / 部分正确 / 错误 / 知识缺失 / 拒答不当 / 该拒答未拒答；归因 14 项（含装备域 5 项）。
8. **DSL 文件名**：`dsl/01-多模态智能问答-Chatflow.yml`、`dsl/02-满意度评价-Workflow.yml`、`dsl/03-多模态语料标注-Workflow.yml`；旧文件在 `dsl/_v1-原始备份/`，**禁止再引用旧名**。
9. **长期记忆注入契约（问答链 prompt）**：`orchestrator.build_prompt` 在【检索片段】之前注入【长期记忆】；**全局记忆恒生效，项目记忆仅当同名知识库参与检索时注入**；记忆与检索片段冲突时**一律以检索片段为准**（不改变"回答须可追溯到资料/版本/条款"这一判据）；记忆写入限管理员/审核员（`current_admin`）。**无记忆时 prompt 与旧版逐字一致**（契约不变，见 D40）。
10. **外部 DSL 导入契约（应用工作室 · 严格版）**：`POST /api/orchestration/workflows/import`（`current_admin`）接收任意 Dify 应用 DSL 文本（`.yml/.yaml/.json`），**严格校验、失败即拒收不落库**：① 由编排内核 `parse` 代劳 YAML 解析（产品侧 BFF venv 无 PyYAML）；② 顶层必须是映射且 `kind == "app"`；③ `graphon.inspect` 必须 `load_status == LOADABLE` 且 `node_count > 0`。通过后按 `app.mode`（`chat` 归一为 `advanced-chat`）以 **JSON 文本**写入 `workflows.dsl`（满足 `store.get_workflow` 的 `json.loads` 读取契约）。**任何一步不通过都不得产生半成品条目**（见 D42）。

## 4. 变更纪律（硬规则）

- **R1　改 DSL 必同步**：改动 code / prompt_template / variables / outputs 后，必须同步 `eval_service/judge.build_inputs`（输入契约）、`collector`（回执与结果解析）、`store`（落库列）、自检用例（test_code_nodes / test_contract / selftest），然后 `dify_sync_dsl.py --apply` 重新发布，并用服务 API 跑一次成功复验。
- **R2　门禁前置**：任何改动前后都要跑 `tools\run_all_checks.ps1`，7 个套件必须全绿；发布工作流后再用 `python tools\check_drift.py --online` 确认线上草稿与本地 DSL 一致。
- **R3　口径变更流程**：先改 `docs/01` 与本文 §2/§7（登记决策），再改代码，最后重算历史（报表/基线）并在文档标注版本。
- **R4　禁止"改测试让它变绿"**：测试红了先判定是实现漂移还是契约变更，两种情况都要留下记录与证据。
- **R5　交付树整洁**：`D:\app\dify` 只放长期有用的文件；一次性排查脚本放 `%TEMP%` 并在结束前清理。
- **R6　证据留痕**：结论必须带证据（文件:行号 / 命令输出 / HTTP 响应），没有证据一律标"未验证"。
- **R7　不做无授权扩围**：不引入 OCR、图像/视频理解、抽帧、语音转写，不容器化，除非甲方书面变更（见 §9）。

## 5. 已知平台缺陷与既定绕行（不要重复踩）

| 现象 | 根因 | 既定处置 |
| --- | --- | --- |
| 门户问答一直转圈，SSE 只有 `event: ping` | 本机 Dify 1.17.1 构建的流式监听器缺陷（阻塞模式正常） | BFF `/api/chat/stream` 12s 无内容即回落阻塞模式并按 SSE 帧下发；用户看到"整段返回"而非逐字 |
| Code 节点报 `sandbox disconnected` | 本机 sandbox_shim 被重启或连接被重置（间歇性） | 重跑即恢复；**不要随手重启 shim**；目标环境用官方 dify-sandbox |
| 语料标注抽不出问答对（qa_count=0） | 推理模型思考段复述 schema 的花括号，解析器锁错括号 | 两个工作流均已"先剥 `<think>` 再扫描可解析的 `{…}`"，并有回归用例 |
| kb_bridge 与 RAGFlow 抢 9380 | 演示脚本默认端口相同 | 以 RAGFlow 为准，kb_bridge 换端口启动 |
| 治理看板 8848 打不开 | 未常驻 | 双击 `启动治理看板.bat` |
| 前端渲染报错导致页面卡在"正在加载数据" | 渲染函数抛错被 Vue 吞掉 | 时间/字段已做容错（format.ts），并加了全局 errorHandler 打印 |
| 开图谱检索后问答变成「知识库未收录」 | Dify 出站 SSRF 超时默认 5s，而 KG 检索需 15~17s | 已把 `SSRF_DEFAULT_TIME_OUT/READ/WRITE` 提到 60s（D10）；改 Dify 环境变量后必须重启 API |
| 真实模式采集恒 0 条消息 | `list_messages` 未带 `user`，Dify 返回 404 Conversation Not Exists | 已修（dify_client/collector 透传 user）；`collect` 新增 `--user` 参数 |
| 评测服务连不上本机 Dify | `.env` 缺 `DIFY_BASE_URL` → 默认指向 cloud.dify.ai | 已在 `E:\llm-stack\.env` 补 `DIFY_BASE_URL=http://127.0.0.1:5001` |
| 重新解析后数据集片段计数翻倍（50→100） | RAGFlow 记账缺陷 | 逐文档实测无重复（仍 50 段），仅计数不准；评估以逐文档统计为准 |
| 调小 `chunk_token_num` 不改变分段 | naive 解析器对该 markdown 结构不敏感 | 改用"按小节拆分文档入库"或更换 chunk_method（见状态快照"分段实验"） |
| **真实 docx（含大表格）整篇入库失败** | 表格被当作**单个不可切分的片段**，超出 bge-m3 的 8192 token 上下文 → Ollama 返回 500 → 整篇 `run=FAIL`、0 片段 | 入库门禁：`tools/ragflow_ingest_docs.py --retry-failed` 自动把分段长度减半后重试；仍失败则人工拆表 |
| 嵌入吞吐低（bge-m3 单次调用 ~8s） | 本机 Ollama 走 CPU（无 GPU 加速） | 175 个片段的文档约需 25 分钟；目标环境必须评估 GPU 或更快的嵌入模型 |
| **RAGFlow 解析进程整进程崩溃（0xc000001d）** | 解析某份 docx 时在 `docx/enum/base.py from_xml`（python-docx 取段落样式）触发 Windows 非法指令，`task_executor` 直接退出 | 单消费者 = 单点故障：崩溃后队列无人消费，文档长时间停在「解析中」且无报错。**绕行：常驻两个消费者**（`RAGFLOW_WORKER=winhost_0/winhost_1`，同一个 Redis 消费组），崩一个另一个继续，未确认任务由 `get_unacked_iterator` 自动重取 |
| **知识图谱是一团毛线：标签糊在一起、混进 `var_chart`/`qdate` 之类代码标识** | 旧实现直接把切片关键词当实体（含代码 token），且把 256 个点全画上并常显标签 | 改为**实体抽取**（`product/graph.py`）：以知识内核分词结果为主、代号/章节号/领域后缀为补充；过滤代码标识与泛化词；实体分类（资料/代号/章节/参数/部件/术语）；边按每点 ≤3 条稀疏化；前端默认只画权重前 40 个、标签只常显前 45%，支持搜索/数量切换/点选看邻居。实测真实文档（176 切片）：80 实体 / 117 边、类别 {术语 46, 代号 27, 章节 7}、过滤噪声 7.8 万项、无代码标识残留 |
| **引用面板显示原始 HTML 表格标签**（`<table><tr><td>…`） | RAGFlow 解析器对表格片段保留 HTML 结构，前端此前按纯文本渲染 | 前端新增 `lib/richtext.ts`：表格片段白名单净化后渲染成真表格（`.pp-chunk` 样式，可横向滚动），普通片段转义换行；**提示词侧另做整形**（`product/textutil.py` 把表格还原成 `| 单元格 |` 文本），模型读得准且省 token——两边口径不冲突 |
| **前端已重建、用户却一直看到旧包**（旧图例竖排、旧提示文案） | 门户静态资源用 `StaticFiles` 直接挂载，**没设 `Cache-Control`**：浏览器按启发式规则长期复用 `index.html`，重建后的新 `index.html`（及其哈希资源名）根本取不到 | 已改为 `PortalFiles`：`index.html`/无扩展名路径返回 `no-cache, must-revalidate`（靠 ETag 回源校验），`assets/*` 返回 `public, max-age=31536000, immutable`。**提醒**：改前端后仍需让用户**强刷一次**（Ctrl+F5）；此后普通刷新即可拿到新版 |
| 新建知识库后解析报 `Model(@None) not authorized` | RAGFlow 建库接口不带 `embedding_model` 时 `embd_id` 落空 | BFF `/api/rf/datasets` 默认补 `bge-m3@Ollama`（`RAGFLOW_EMBEDDING_MODEL` 可覆盖）；门户建库页显示当前默认向量模型 |
