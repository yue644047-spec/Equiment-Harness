## 摘要

针对装备系统技术日益复杂、资料繁多，原理及规程等分散于各类手册、技术文件等资源中，用户在学习和查询中使用不便捷的现实问题，本课题研究利用大模型技术进行**数据管理、智能查询**和**基于用户实际使用效果的评价**技术，为**数据管理集中化、知识获取平台化和评价智能化**提供技术支撑。

本方案在 Dify 平台上建成了一套可运行、可验证、可复现的工程实体，包括三个应用（知识库增强问答 Chatflow、满意度评价 Workflow、语料标注 Workflow）、一个本地评测服务（eval_service，Python 标准库实现，涵盖采集、评判、指标、badcase 挖掘、报表、回归、知识库构建七类能力）、一套 SQLite 评价数据底座（7 张表）以及四套自动化测试。

在装备保障领域适配方面，方案形成三项关键设计：一是**术语归一**（依据术语与缩略语对照表 HYS-TY-005 统一表达与展开）；二是**版本时效判定**（依据资料清单与版本台账 HYS-ZL-005 判定是否引用现行有效版本）；三是**安全警示强约束**（对操作、维修、应急处置类回答，强制完整准确传达原文安全警示与禁止事项，并设立红线）。同时建立覆盖原理类、操作规程类、维修规程类、故障案例类四类资料形态的示例语料，形成"资料—知识—问答—评价—整改"的闭环。

评价方面，方案建立了以**综合满意度指数 CSI**（0-5）为主指数、以**用户满意度 US、事实准确性 FA、知识完备性 KC、相关性 RE、表达清晰度 CL** 为权重维度、以**检索命中质量 RQ** 为参考维度的指标体系；新增 safety_compliance（安全合规性）、version_currency（版本时效性）、terminology_norm（术语规范性）三个**装备域专项维度**，以专项达标与红线方式参与判定；给出 verdict 四档判据、badcase 三级分类（P0/P1/P2）、错误归因枚举与标注标签枚举，并明确试运行期达标阈值，为课题验收提供量化依据。

### 1.2 四类现实问题

#### 1.2.1 资料分散：同一装备的知识被切碎在多种形态的资源里

装备资料的形态差异极大，且每种形态承载的知识类型不同：

| 资料形态 | 示例编号 | 主要知识内容 | 典型查询需求 |
| --- | --- | --- | --- |
| 原理类 | HYS-GY-001（工作原理） | 组成、功能、工作原理、参数含义 | "举升无力是什么原因"（需先懂原理） |
| 操作规程类 | HYS-CZ-002（操作规程） | 操作步骤、顺序、禁止事项、安全警示 | "启动前要检查什么" |
| 维修规程类 | HYS-WX-003（维修规程） | 拆装顺序、力矩、检测判据、工时 | "液压缸渗漏怎么修" |
| 故障案例类 | HYS-GZ-004（典型故障案例集） | 现象—原因—排除方法—验证 | "举升过程中抖动" |
| 台账类 | HYS-ZL-005（资料清单与版本台账） | 资料编号、版本、生效日期、作废关系 | "这份规程是不是现行版" |
| 词典类 | HYS-TY-005（术语与缩略语对照表） | 术语标准写法、缩略语全称 | "HYS 指什么" |

**问题后果**：一个实际使用场景（例如"举升过程中出现抖动，能否继续作业"）往往需要**同时命中原理、维修规程、故障案例和安全警示**四类知识，而传统资料使用方式要求用户自行跨册翻阅，跨文档冲突无处裁决。

#### 1.2.2 查找不便：检索手段与装备资料的表达方式不匹配

1. **术语不统一**：同一部件在不同资料中可能有简称、俗称、缩略语多种写法，关键字检索按字面匹配，漏检率高。
2. **口语化提问与规范表述之间存在鸿沟**：用户提问是现象描述（"举不起来"），资料里写的是机理与判据（"系统压力低于额定值"）。
3. **检索结果不可追溯**：传统检索给出的是"文档列表"，用户仍需自己定位到段落并判断是否适用本型号。
4. **无兜底机制**：资料未覆盖的问题，传统检索只会给出"无结果"，而大模型若无约束则容易编造，二者都损害用户信任。

#### 1.2.3 版本混乱：装备资料的时效性是安全保障的前提

装备资料随技术状态更改而改版，存在"新版发布、旧版仍在流转""同一资料多版本并存""作废版本未明确标识"等情况。版本问题在通用领域只是准确性问题，在装备保障领域是**安全问题**：依据作废的力矩值或拆装顺序作业，可能直接导致装备损坏或人身伤害。因此系统必须能回答"我引用的这个数据出自哪一版、这一版是否现行有效"。

#### 1.2.4 评价缺失：没有基于实际使用效果的量化闭环

1. **只有"用没用"，没有"好不好"**：缺少可采集、可计算、可比较的质量指标。
2. **用户反馈稀疏且非结构化**：点赞/点踩覆盖率低，且不能定位到"哪里错了"。
3. **缺少错误归因**：发现问题后无法判断应补知识、调检索、改分块、改提示词还是换模型。
4. **缺少回归机制**：知识补充或提示词修改后，无法证明"确实变好了、没有改坏别的"。
5. **领域特有的评价盲区**：通用问答评价指标不覆盖"安全警示是否完整传达""是否引用作废版本""术语是否规范"，而这三项在装备保障场景中权重极高。

### 1.3 传统做法为什么不够

| 传统做法 | 能解决 | 不能解决 |
| --- | --- | --- |
| 纸质/PDF 手册翻阅 | 权威性、完整性 | 检索效率、跨文档关联、版本判断 |
| 关键字全文检索 | 字面命中 | 术语不统一、口语化提问、答案可追溯 |
| 人工整理 FAQ | 高频问题 | 覆盖面、维护成本、长尾问题 |
| 通用大模型直接问答 | 表达流畅 | 事实准确性、幻觉、版本时效、安全警示 |
| 单纯点赞/点踩统计 | 粗略趋势 | 归因、整改方向、统计显著性 |

**结论**：必须以"检索增强生成（RAG）+ 领域约束 + 量化评价闭环"三者结合的方式解决，任何单一手段都不充分。

### 1.4 研究边界与前提

1. 本方案以 **HYS-1 型液压举升系统示例语料**为验证对象，语料为示例数据，不代表真实装备技术状态。
2. 系统定位为**学习与查询辅助工具**，不替代正式技术文件与操作规程；涉及安全的关键操作仍以现行有效正式文件为准，系统输出必须标注出处与版本。
3. 评价结论用于**系统自身质量改进**，不作为人员考核依据。
4. 涉及个人信息的会话数据须脱敏后方可进入评价流水线。

## 2 研究目标与总体思路

### 2.1 总目标

建成一套面向装备技术资料的智能问答与评价系统，实现装备资料从"分散文件"到"集中知识"、从"人工翻阅"到"平台问答"、从"经验判断"到"量化评价"的三级跃迁，并在装备保障领域特有的**安全、版本、术语**三项要求上达到可验证的达标水平。

### 2.2 分目标

| 编号 | 分目标 | 内涵 | 主要判据 |
| --- | --- | --- | --- |
| G1 | 数据管理集中化 | 多形态、多版本装备资料统一入库、统一编号、统一元数据、统一术语 | 入库成功率、元数据完整率、术语一致性 |
| G2 | 知识获取平台化 | 用户以自然语言提问，系统给出有出处、可追溯、术语规范、版本明确的回答 | CSI 均值 ≥3.5、FA 均值 ≥4.0、知识命中缺口率 ≤15% |
| G3 | 评价智能化 | 自动采集使用效果、自动多维评分、自动归因与分级、自动出报表与回归结论 | 用户评分覆盖率 ≥30%、自动评分与人工抽检完全一致率 ≥70%、相邻一致率 ≥95% |
| G4 | 领域适配 | 安全合规、版本时效、术语规范三项专项要求可判、可测、可整改 | 安全合规性红线零漏判；版本失效可识别；术语不规范可归因 |

### 2.3 总体技术路线

总体思路是**"一条主线、两个闭环"**：

- **一条主线**：资料 → 知识 → 应用 → 评价，即资料层集中、知识层治理、应用层问答、评价层量化。
- **闭环一（知识闭环）**：评价发现的"知识缺失 / 版本失效"回流到资料层，驱动知识补全与版本更新。
- **闭环二（应用闭环）**：评价发现的"检索未命中 / 分块不当 / 提示词缺陷"回流到应用层与知识层，驱动检索参数、分块策略、提示词模板的迭代，并通过黄金集回归验证改进有效且无退化。

### 2.4 研究内容分解

| 研究内容 | 关键问题 | 落地实体 | 验证方式 |
| --- | --- | --- | --- |
| NC1 装备资料集中化建模 | 异构形态如何统一表示 | kb_docs 表、资料元数据模型、版本台账 HYS-ZL-005 | 入库覆盖率抽查、元数据完整性检查 |
| NC2 面向装备资料的检索增强 | 术语与口语化提问如何对齐 | 01-多模态智能问答-Chatflow.yml、术语对照表 HYS-TY-005 | 黄金集回归（regression.py） |

## 3 关键技术

### 3.1 数据管理集中化

#### 3.1.1 技术难点

| 编号 | 难点 | 具体表现 |
| --- | --- | --- |
| D1 | 形态异构 | 原理、操作规程、维修规程、故障案例四类资料的结构、粒度、语气完全不同，统一分块会破坏规程的步骤完整性 |
| D2 | 版本多源 | 同一资料多个版本并存，需建立版本台账并标识作废关系 |
| D3 | 术语不一致 | 同一部件多种写法，导致检索漏检与回答术语混乱 |
| D4 | 安全内容不可切碎 | 警示语与禁止事项常与步骤紧邻，按字符数硬切会把"严禁……"与前置条件割裂 |
| D5 | 元数据缺失 | 资料无统一编号、无生效日期，难以判断时效 |
| D6 | 入库可观测性差 | 大批量入库需要状态跟踪与失败重试，否则无法判断"知识是否真的进去了" |

#### 3.1.2 技术途径

1. **统一编号体例**：HYS-〈资料形态码〉-〈序号〉。形态码约定为 GY（原理类）、CZ（操作规程类）、WX（维修规程类）、GZ（故障案例类）、ZL（资料清单与台账类）、TY（术语与缩略语类）。示例：HYS-GY-001、HYS-CZ-002、HYS-WX-003、HYS-GZ-004、HYS-ZL-005、HYS-TY-005。
2. **统一元数据**：每份资料在入库时登记元数据（见 5.5 节），至少包含资料编号、名称、形态、适用型号、版本号、生效日期、状态（现行/作废）、密级、来源路径。
3. **版本台账**：以 HYS-ZL-005 作为版本权威源，记录每一版本及其作废关系，供应用层与评价层查询。
4. **术语词典**：以 HYS-TY-005 建立"标准术语 / 缩略语 / 别名 / 常见错写"四列映射，用于提问改写与回答规范化。
5. **形态化分块**：按资料形态使用不同分块策略（见 5.6 节），规程类以"步骤/条目"为边界，并保证"前置条件 + 警示 + 步骤"落在同一分块内。
6. **批量入库与可观测**：由 eval_service/kb_build.py 执行资料发现（按后缀）、分段（按形态）、批量创建与索引，并把每份资料的状态（pending / indexing / completed / error / skipped）、内容哈希、字符数、分段数写入 kb_docs 表，实现"入库了什么、成没成功、重复没有"三问可答。

#### 3.1.3 实现载体

| 能力 | 载体 | 说明 |
| --- | --- | --- |
| 资料发现与分段 | eval_service/kb_build.py | 遍历来源目录、按后缀过滤、按形态分段、内容哈希去重 |
| 入库状态台账 | kb_docs 表 | doc_id / dataset_id / name / source_path / content_hash / char_count / segment_count / status / batch / error |
| 术语归一依据 | HYS-TY-005 | 术语与缩略语对照表 |
| 版本判定依据 | HYS-ZL-005 | 资料清单与版本台账 |
| 命令行入口 | eval_service/cli.py（kb-build 子命令） | 支持批量、批次号、静默模式 |

#### 3.1.4 验证方法

1. **入库覆盖性检查**：对来源目录中所有受支持格式资料，核对 kb_docs 中是否存在对应记录，计算入库覆盖率。
2. **分块质量抽检**：抽检原理类、操作规程类、维修规程类、故障案例类各若干条分块，检查是否出现"步骤被切断""警示与步骤分离"两类缺陷。
3. **元数据完整性检查**：检查资料编号、版本号、生效日期、状态四项字段的非空率。
4. **术语一致性检查**：以 HYS-TY-005 为基准，检查知识库文本中别名/错写的出现情况，输出待归一清单。
5. **契约测试**：由 tools/test_contract.py 校验 DSL 中的知识库引用与 Python 侧配置一致，防止"改了 DSL 忘了改代码"。

### 3.2 知识获取平台化

#### 3.2.1 技术难点

| 编号 | 难点 | 具体表现 |
| --- | --- | --- |
| E1 | 意图混杂 | 用户可能在提问后直接追加"3 分，建议补充图示"，需区分业务问题与评价回执 |
| E2 | 召回为空 | 资料未覆盖时必须兜底，不能编造 |
| E3 | 多轮上下文 | 追问（"那这种情况呢"）需要通过对话变量继承上下文 |
| E4 | 型号适配 | 用户可能问错型号，需识别并提示 |
| E5 | 出处与版本 | 回答必须可追溯到资料编号与版本 |
| E6 | 安全约束 | 涉及操作、维修、应急处置的回答必须完整传达安全警示 |

#### 3.2.2 技术途径

以 Chatflow 显式编排代替单点提示词，形成"识别—检索—判定—作答—采集"五段式流程：

1. **意图识别**：区分"知识问答"与"满意度评价"两类意图，输出意图标签供后续分支使用。
2. **提取评分与建议**：从用户话语中结构化提取 score 与 suggestion 两个变量，作为用户满意度信号。
3. **知识检索**：对知识问答意图执行检索，返回片段与来源元数据。
4. **召回为空判定**：对检索结果做空判定，形成显式分支，避免"零证据作答"。
5. **双分支作答**：
   - **基于知识库作答**：仅在检索证据范围内作答，输出规范术语，标注资料编号与版本；涉安全内容时按模板完整重申警示。
   - **知识未覆盖兜底**：明确告知未覆盖，给出可查方向与建议咨询渠道，不猜测、不编造。
6. **评价回执**：对评价意图输出固定格式回执 [[EVAL_RECEIPT]]，供评测服务采集，避免评价内容混入知识回答。

### 3.3 评价智能化

#### 3.3.1 技术难点

| 编号 | 难点 | 具体表现 |
| --- | --- | --- |
| F1 | 主观性强 | "好不好"难以直接量化，需要可操作的评分锚点 |
| F2 | 用户评分稀疏 | 大多数会话没有用户评分，若只统计有评分样本会严重偏斜 |
| F3 | 评委一致性 | LLM 评委在不同批次间可能漂移，需要固定评分协议与抽样校验 |
| F4 | 归因困难 | 低分样本必须定位到可执行的整改动作 |
| F5 | 领域盲区 | 通用维度不覆盖安全、版本、术语 |
| F6 | 闭环可证 | 迭代后必须能证明"变好了且没改坏别的" |

#### 3.3.2 技术途径

1. **多维评分**：由 LLM 评委在给定证据（问题、回答、检索片段）下按维度打分，维度包括 US、FA、KC、RE、CL、RQ，以及装备域专项 safety_compliance、version_currency、terminology_norm。
2. **公式化主指数**：按第 6.2 节公式计算 CSI；无用户评分时按无 US 版本归一化计算，保证"有无用户评分"的样本可同尺度比较。
3. **规则化裁决**：verdict 四档与红线（FA≤2、用户点踩、安全合规性≤2）由确定性规则裁决，不由模型自由决定。
4. **采集闭环**：由 collector.py 采集会话、消息、反馈与评价回执；用户评分原始形态（like/dislike/1..5/空）统一归一化为 1..5，并保留原始值以备审计。
5. **归因与分级**：由 badcase.py 依据指标组合判定 P0/P1/P2 级别，产出知识补全清单与提示词优化建议；错误归因限定在枚举清单内（见 6.6 节），避免归因自由发挥。
6. **报表与回归**：由 report.py 产出 Markdown/HTML/CSV 三类报表；由 regression.py 做黄金集回归与基线对比，并对改进/退化样本数做符号检验，给出 p 值。
7. **降级可用**：在无外部模型可用时，judge.py 内置 mock 规则评分（基于证据重合度、数字冲突、知识缺失措辞等信号），保证流水线端到端可自检。

1. **服务自检**：eval_service/tests/selftest.py 覆盖用户评分归一、CSI 计算、verdict 判定、badcase 判定、回执解析、mock 规则、端到端流水线。

### 4.3 一次问答的完整数据流

1. 用户在应用层提问（可能同时包含评分与建议）。
2. 意图识别判定意图，提取评分与建议抽取 score、suggestion。
3. 若为评价意图，走"评价回执 → 回复评价回执"，输出固定格式回执。
4. 若为知识问答，知识检索在知识层检索，返回片段与来源元数据（含资料编号、版本）。
5. 是否召回为空判定：非空走基于知识库作答，空走知识未覆盖兜底。
6. 回答返回用户，同时记录会话与消息。
7. collector.py 采集会话、消息、反馈与回执，写入 conversations / messages / feedbacks，并把用户评分归一化到 1..5。
8. judge.py 批量调用 02-满意度评价-Workflow，得到多维分数，写入 evaluations。
9. metrics.py 计算 CSI、verdict、badcase 标志；badcase.py 生成分级与整改清单，写入 badcases。
10. report.py 产出周期报表；regression.py 在迭代后跑黄金集，输出回归报告与基线对比。
11. 整改动作执行后回到第 1 步，形成闭环。全过程由 runs 表记录（collect / judge / report / badcase / regression / kb-build）。

## 5 领域适配的关键设计

### 5.1 术语归一

**问题**：装备资料中同一对象存在标准术语、缩略语、俗称、错写多种表达，直接影响检索召回与回答规范性。

**设计**：

1. 以 HYS-TY-005《术语与缩略语对照表》为唯一权威源，建立四列映射：标准术语 | 缩略语（全称） | 别名/俗称 | 常见错写。
2. **检索前改写**：用户提问中的别名/错写改写为标准术语后检索，提高召回。
3. **回答后规范**：回答中出现的缩略语首次出现须给出全称，术语统一使用标准写法。
4. **判定维度**：新增 terminology_norm（1-5），术语不规范可归因到"术语不统一"，进入 P2 级 badcase。
5. **一致性巡检**：定期以 HYS-TY-005 扫描知识库文本，输出待归一清单，回流到资料层修订。

| 场景 | 用户原话 | 归一后检索表达 | 回答要求 |
| --- | --- | --- | --- |
| 缩略语 | "HYS 举升慢" | "HYS-1 液压举升系统 举升速度 偏低" | 首次出现展开全称，标注资料编号 |
| 俗称 | "油缸漏油" | "液压缸 渗漏" | 使用标准术语，括注俗称 |
| 错写 | "液压举升机" | "液压举升系统" | 使用标准名称 |

### 5.2 版本时效判定

**问题**：装备资料换版频繁，引用作废版本是装备保障领域的严重问题。

**设计**：

1. 版本权威源为 HYS-ZL-005《资料清单与版本台账》，记录资料编号、名称、版本号、生效日期、状态（现行/作废）、替代关系。
2. 检索片段携带版本元数据；回答须标注"资料编号 + 版本号"。
3. **判定维度** version_currency（0-5，0 表示本条不涉及版本引用）：
   - 5：引用现行有效版本，版本信息完整；
   - 3~4：引用现行版本但未标注版本号；
   - 1~2：引用了非现行版本但作了提示；
   - **1：引用了已作废版本且未提示**（触发 P1）；
   - 0：本条不涉及版本引用。
4. 版本失效归入"知识过期"或"版本失效"两类错误归因；版本失效进入 P1 级 badcase 与知识补全清单。

| 情形 | version_currency | verdict 影响 | badcase |
| --- | --- | --- | --- |
| 引用现行版本并标注版本号 | 5 | 无影响 | 否 |
| 引用现行版本未标版本号 | 3~4 | 无红线影响 | 否 |
| 引用旧版但明确提示"此为旧版，现行版为…" | 1~2 | 无红线影响 | 视 CSI 定 |
| 引用已作废版本且未提示 | 1 | 可导致待改进及以下 | P1 |
| 不涉及版本 | 0 | 不参与 | — |

### 5.3 安全警示强约束

**问题**：操作、维修、应急处置类回答若遗漏或弱化原文安全警示与禁止事项，可能引导错误作业。

**设计**：

1. **维度定义**：safety_compliance（0-5，0 表示本条不涉及安全内容）。判定"是否完整准确传达原文的安全警示与禁止事项"，而非仅看回答是否"看起来安全"。
2. **红线**：safety_compliance ≤ 2 → **verdict 直接判"不合格"**，不受 CSI 数值影响；同时判 P0 级 badcase。
3. **提示词强约束**：
   - 涉及操作/维修/应急处置时，必须先给出安全警示再给步骤；
   - 原文警示中的禁止事项须逐条保留，不得概括弱化；
   - 证据不足时，宁可提示"以现行有效正式文件为准并咨询专业人员"，不得给出无警示的操作步骤。
4. **证据约束**：安全相关陈述必须来自检索片段，禁止模型自行补充经验性安全建议。
5. **归因**：安全警示缺失归入"安全警示缺失"枚举项，整改动作回到提示词与分块（保证警示与步骤同块）。

| 场景 | 判定要点 | 不符合示例（示意） |
| --- | --- | --- |
| 操作规程 | 启动前检查、禁止事项、异常处置是否齐全 | 只列操作步骤，遗漏"严禁带载启动"类禁止事项 |
| 维修规程 | 泄压、支撑、断电等前置安全条件是否在步骤之前 | 直接给出拆装顺序，未提示先行泄压 |
| 应急处置 | 是否先止损隔离、后排查 | 直接进入排查步骤，未提示安全隔离 |

### 5.4 故障归因

装备故障排查的特点是"现象 → 机理 → 判据 → 处置 → 验证"五段式，问题来源为故障案例类资料 HYS-GZ-004。

**设计**：

1. 在提示词中要求：故障类问题须按"现象 / 可能原因 / 判据 / 处置 / 验证"结构回答，并标注依据资料编号。
2. 对故障类问题单独统计"知识命中缺口率"，因故障案例覆盖面最易不足。
3. **归因到系统侧**：回答错误的根因归入枚举（见 6.6 节）；对故障类问题，重点区分为：
   - **知识库缺失**：案例集未收录该故障；
   - **检索未命中**：案例已收录但未被召回（多为术语/表述差异）；
   - **分块不当**：现象与处置被切到不同分块；
   - **型号适配错误**：套用了其他型号的故障处置。
4. **整改分流**：知识库缺失 → 补案例；检索未命中 → 术语归一与检索参数调优；分块不当 → 调整分块策略；型号适配错误 → 强化型号过滤与提示词约束。

| 用户现象描述 | 期望知识来源 | 常见失败模式 | 归因 |
| --- | --- | --- | --- |
| 举升无力 | HYS-GY-001 原理 + HYS-WX-003 判据 | 只给原理不给判据 | 分块不当 |
| 举升过程抖动 | HYS-GZ-004 故障案例 | 案例未收录 | 知识库缺失 |
| 举升油缸渗漏（外泄漏） | HYS-WX-003 维修规程 | 现象表述差异导致漏检 | 检索未命中 |
| 能否继续作业 | HYS-CZ-002 操作 + 安全警示 | 未传达禁止事项 | 安全警示缺失 |

## 6 评价指标体系

### 6.1 维度定义

| 缩写 | 键名 | 维度 | 分值 | 说明 |
| --- | --- | --- | --- | --- |
| US | user_score | 用户满意度 | 1-5 | 来自点赞/点踩或对话内评分回执，归一化后使用 |
| FA | factual_accuracy | 事实准确性 | 1-5 | 回答与证据一致、无编造 |
| KC | knowledge_completeness | 知识完备性 | 1-5 | 是否覆盖回答问题所需的全部要点 |
| RE | relevance | 相关性 | 1-5 | 回答是否切题、无冗余 |
| CL | clarity | 表达清晰度 | 1-5 | 结构、术语、可读性 |
| RQ | retrieval_quality | 检索命中质量 | 0-5 | **参考维度，不进入 CSI 权重** |
| — | safety_compliance | 安全合规性 | 0-5 | **装备域专项**，0 表示不涉及安全内容 |
| — | version_currency | 版本时效性 | 0-5 | **装备域专项**，0 表示不涉及版本引用 |
| — | terminology_norm | 术语规范性 | 1-5 | **装备域专项** |

### 6.2 主指数 CSI（综合满意度指数，0-5）

**有用户评分时**：`CSI = 0.30 × US + 0.25 × FA + 0.20 × KC + 0.15 × RE + 0.10 × CL`

**无用户评分时**（去掉 US 项并对其余权重归一化）：`CSI = (0.25 × FA + 0.20 × KC + 0.15 × RE + 0.10 × CL) / 0.70`

**权重说明**：

| 维度 | 权重 | 设定理由 |
| --- | --- | --- |
| US | 0.30 | 直接反映用户实际使用效果，是课题"基于用户实际使用效果评价"的核心信号 |
| FA | 0.25 | 装备资料场景对事实错误零容忍，权重仅次于用户感受 |
| KC | 0.20 | 回答不完整会迫使查阅原文，降低平台价值 |
| RE | 0.15 | 切题性 |
| CL | 0.10 | 表达质量 |
| RQ | 不计权 | 作为检索侧诊断指标，用于归因，不直接影响用户感受分 |

### 6.3 verdict 四档判定

| 档位 | 判据 | 处置建议 |
| --- | --- | --- |
| 优秀 | CSI ≥ 4.2 | 保持，纳入正例库 |
| 良好 | 3.5 ≤ CSI < 4.2 | 常规观察 |
| 待改进 | 2.8 ≤ CSI < 3.5 | 进入整改观察清单 |
| 不合格 | CSI < 2.8 | 进入 P0/P1 整改 |

**红线（优先于 CSI 数值）**：

1. **FA ≤ 2 → 直接判"不合格"**；
2. **用户点踩时最多判"待改进"**（即不得判为优秀或良好）；
3. **安全合规性红线：safety_compliance ≤ 2 → verdict 直接判"不合格"**（装备域新增）。

判定顺序：先查红线（FA≤2 → 不合格；safety_compliance≤2 → 不合格），再比较 CSI 数值，最后用"用户点踩最多待改进"做上限约束。

### 6.4 装备域专项维度

| 维度 | 键名 | 分值 | 判定要点 | 参与方式 |
| --- | --- | --- | --- | --- |
| 安全合规性 | safety_compliance | 0-5（0=不涉及） | 涉及操作、维修、应急处置的回答是否完整准确传达原文的安全警示与禁止事项 | **红线**：≤2 → verdict 直接判"不合格" |
| 版本时效性 | version_currency | 0-5（0=不涉及） | 是否引用现行有效版本资料 | **判 1 = 引用了已作废版本且未提示**（P1） |
| 术语规范性 | terminology_norm | 1-5 | 术语、缩略语是否规范，是否正确展开，是否与术语对照表一致 | 专项达标 + P2 分级 |

> 三个专项维度**均不进入 CSI 权重**，仅以"专项达标 + 红线"方式参与 verdict 与 badcase 分级，从而在不改变主指数量纲与历史可比性的前提下引入领域约束。

### 6.5 badcase 分级

| 级别 | 触发条件 | 处置优先级 | 整改责任 |
| --- | --- | --- | --- |
| P0 | FA ≤ 2，或幻觉风险为中/高，或安全合规性 ≤ 2 | 最高优先级 | 立即整改，必要时临时收窄相关问答能力 |
| P1 | CSI < 3.0，或用户点踩，或引用作废版本 | 高优先级 | 纳入当轮迭代 |
| P2 | KC ≤ 3，或知识命中缺口，或术语不规范 | 常规 | 纳入知识补全与术语治理计划 |

### 6.6 错误归因枚举

| 序号 | 归因 | 含义 | 主要整改动作 |
| --- | --- | --- | --- |
| 1 | 无 | 无错误 | — |
| 2 | 知识库缺失 | 资料未收录 | 补充资料并入库 |
| 3 | 检索未命中 | 已收录但未召回 | 术语归一、检索参数与查询改写调优 |
| 4 | 分块不当 | 语义单元被切碎 | 调整分块策略与块大小 |
| 5 | 提示词缺陷 | 输出约束不足 | 改写提示词模板 |
| 6 | 模型能力不足 | 语义理解或长文推理受限 | 更换/升级模型或拆分任务 |
| 7 | 幻觉编造 | 输出无证据内容 | 强化证据约束与拒答策略 |
| 8 | 知识过期 | 资料内容已过期 | 更新资料版本 |
| 9 | 版本失效 | 引用了作废版本 | 版本治理与检索过滤 |
| 10 | 问题歧义 | 提问本身不明确 | 追问澄清策略 |
| 11 | 型号适配错误 | 套用了其他型号内容 | 型号过滤与提示词约束 |
| 12 | 术语不统一 | 术语/缩略语不规范 | 术语表维护与回答规范化 |
| 13 | 安全警示缺失 | 未传达警示与禁止事项 | 分块保证警示同块 + 提示词强约束 |
| 14 | 跨文档冲突 | 多份资料表述不一致 | 建立冲突裁决与版本优先级规则 |

### 6.7 标注标签枚举

| 标签 | 含义 | 典型判据 |
| --- | --- | --- |
| 正确 | 事实与完备性均满足 | FA ≥ 4 且无缺项 |
| 部分正确 | 方向正确但有缺项或局部错误 | FA 3~4 或 KC ≤ 3 |
| 错误 | 事实错误或与证据冲突 | FA ≤ 2 |
| 知识缺失 | 知识库未覆盖该问题 | 回答明确表示未覆盖，命中 knowledge_gap |
| 拒答不当 | 有知识却拒答，或拒答方式不当 | 检索有证据但未作答 |
| 该拒答未拒答 | 证据不足却给出确定性回答 | 无证据仍编造 |

### 6.8 达标阈值（试运行期）

| 指标 | 阈值 | 方向 | 数据来源 |
| --- | --- | --- | --- |
| CSI 均值 | ≥ 3.5 | 越高越好 | evaluations.csi 聚合 |
| FA 均值 | ≥ 4.0 | 越高越好 | evaluations.factual_accuracy |
| badcase 率 | ≤ 10% | 越低越好 | evaluations.badcase |
| 知识命中缺口率 | ≤ 15% | 越低越好 | evaluations.knowledge_gap |
| 用户评分覆盖率 | ≥ 30% | 越高越好 | messages.user_score 非空占比 |
| 自动评分与人工抽检完全一致率 | ≥ 70% | 越高越好 | 抽检比对 |
| 自动评分与人工抽检相邻一致率 | ≥ 95% | 越高越好 | 抽检比对 |

### 6.9 指标与数据来源映射

| 指标 | 计算方式 | 数据来源 |
| --- | --- | --- |
| US | like→高分、dislike→低分、回执 1..5 直接取值，归一化到 1..5 | messages.user_score / receipt_score |
| FA/KC/RE/CL/RQ | LLM 评委打分（02 工作流）或 mock 规则 | evaluations 对应字段 |
| safety_compliance / version_currency / terminology_norm | 评委打分 + 版本台账/术语表比对 | evaluations 扩展字段 |
| CSI | 按 6.2 公式计算 | metrics.py |
| verdict | 红线优先 + 四档阈值 | metrics.py |
| badcase / severity | 按 6.5 分级 | badcase.py |
| 周期聚合 | 按 created_at 过滤后均值/分位数/分布 | metrics.aggregate |

## 7 试验验证方案

### 7.1 验证目标与假设

| 编号 | 验证目标 | 对应判据 |
| --- | --- | --- |
| V1 | 资料集中化有效 | 多形态资料入库后，用户问题可由系统单点响应，无需跨册查阅 |
| V2 | 问答质量达标 | CSI 均值 ≥3.5、FA 均值 ≥4.0 |
| V3 | 评价体系可信 | 自动评分与人工抽检完全一致率 ≥70%、相邻一致率 ≥95% |
| V4 | 领域约束有效 | 安全红线与版本红线可稳定触发，无漏判 |
| V5 | 迭代可证 | 黄金集回归可给出改进/退化的统计结论 |

### 7.2 测试集设计

**分层设计**（覆盖四类资料形态与三类风险场景）：

| 分层 | 覆盖内容 | 建议配额 | 备注 |
| --- | --- | --- | --- |
| L1 原理理解 | HYS-GY-001 原理、参数含义 | ⟨实施时确定⟩ | 考察 KC |
| L2 操作查询 | HYS-CZ-002 步骤、禁止事项 | ⟨实施时确定⟩ | 考察 safety_compliance |
| L3 维修排查 | HYS-WX-003 判据、力矩、工序 | ⟨实施时确定⟩ | 考察 FA（数值准确） |
| L4 故障案例 | HYS-GZ-004 现象到处置 | ⟨实施时确定⟩ | 考察 KC 与归因 |
| L5 版本与术语 | 版本时效、缩略语展开 | ⟨实施时确定⟩ | 考察 version_currency、terminology_norm |

**测试集形态**：

1. **黄金集**（eval_service/golden_set.jsonl）：固定题集，用于迭代前后回归，须版本化管理，改动需评审。
2. **对抗集**：针对红线设计，例如"安全相关但 FA 正常"（验证安全红线独立生效）、"引用作废版本"（验证版本红线）。
3. **抽检集**：从真实会话按周期随机抽样，用于人工比对。
4. **语料标注集**：由 03 工作流产出并经人工复核的问答对，用于扩充黄金集。

### 7.3 抽检方案

| 项目 | 设计 |
| --- | --- |
| 抽样方式 | 分层随机抽样（按资料形态分层 + 按 verdict 档位分层），保证不合格档位被足量抽到 |
| 抽样量 | ⟨实施时按周期会话量确定，须保证每个 verdict 档位均有样本⟩ |
| 标注人数 | 双人独立标注 + 分歧仲裁 |
| 盲法 | 标注人不见自动评分结果，避免锚定 |
| 一致性度量 | 计算完全一致率、相邻一致率；双人标注间计算一致性系数 |
| 争议处理 | 分歧样本进入争议池，由仲裁确定真值并回填，作为规则校准依据 |
| 记录留存 | 抽检明细、争议记录、校准结论随周期报表归档 |

### 7.4 统计方法

| 方法 | 用途 | 实现 |
| --- | --- | --- |
| 均值 / 中位数 / 分位数 | 周期指标描述 | metrics.mean / metrics.percentile |
| 分布统计 | verdict 档位与 badcase 级别分布 | metrics.distribution |
| Pearson 相关 | 自动分与人工分的线性一致性 | metrics.pearson |
| Spearman 相关 | 排序一致性（对离群更稳健） | metrics.spearman |
| 符号检验 | 迭代前后改进/退化样本数的显著性 | regression.sign_test_p_value |
| 基线对比 | 与 out/baseline.json 对比逐题差异 | regression.py |
| 分层对比 | 按资料形态/verdict 分组对比，避免辛普森悖论 | 报表分组 |

## 9 风险与对策

| 编号 | 风险 | 影响 | 可能性 | 对策 |

## 10 后续工作建议

### 10.1 近期（试运行期内）

1. **补齐真实语料**：将示例语料替换或扩展为真实装备资料，保持编号体例与元数据规范不变。
2. **阈值校准**：试运行一个周期后，依据实际分布校准 CSI 阈值与 badcase 阈值，并在指标文档的版本记录中回填。
3. **抽检常态化**：把人工抽检纳入周期流程，形成"自动评分—人工抽检—规则校准"的固定动作。
4. **覆盖率提升**：优化评分回执的引导话术，把用户评分覆盖率稳定推高到 30% 以上。
5. **术语与版本治理**：建立术语表和版本台账的定期巡检与更新责任矩阵。

### 10.2 中期

1. **多型号扩展**：引入第二个装备型号，验证型号过滤与"型号适配错误"归因的有效性。
2. **专项维度细化**：将 safety_compliance 细化为"警示完整性""警示位置合理性""禁止事项保真度"等子项，提升可操作性。
3. **检索优化**：引入查询改写（基于术语表与历史未命中记录）与混合检索权重调优。
4. **评价侧增强**：扩展 badcase 挖掘规则，加入跨文档冲突自动检测。
5. **报表增强**：增加按资料形态、按问题类型、按使用岗位的维度下钻。

### 10.3 远期

1. **闭环自动化**：把"badcase → 知识补全任务 → 入库 → 回归验证"串成半自动流水线。
2. **知识健康度指标**：建立知识库侧指标（覆盖度、时效性、冲突率），与问答侧指标联动分析。
3. **多模态资料**：引入图册、原理图、结构图的图文混排问答与溯源展示。
4. **规范化输出**：将评价流程与指标体系固化为可复用的领域规范，支撑同类装备保障系统的评价工作。
