# 国产化环境适配方案

> **【已确认】目标 CPU：飞腾（ARM64 / aarch64）。**
> 该路线经实测验证完全可行——全部组件均具备官方 aarch64 版本，
> **ARM64 离线部署包已构建完成并通过兼容性校验**，详见第 11 章。

> 文档编号：EVAL-SPEC-008
> 项目名称：基于大模型的多模数据管理查询及迭代优化技术研究
> 编写时间：2026-09-22
> 密级：内部
> 结论摘要：**CPU 架构是决定性因素**。除龙芯（LoongArch）架构存在重大风险外，
> 兆芯/海光（x86）与飞腾/鲲鹏（ARM64）两条路线均可行；数据库层 Dify 原生支持多款国产产品，无需从零适配。

## 1. 国产化约束的影响面

「全部国产化」不是单一维度的替换，它同时约束六个层次，任一层不满足都会导致项目无法交付：

| 层次 | 国产化对象 | 对本项目的影响 |
| --- | --- | --- |
| ① CPU 架构 | 飞腾、鲲鹏、龙芯、兆芯、海光 | **决定性**：决定全部二进制产物是否需要重新构建 |
| ② 操作系统 | 银河麒麟 V10、统信 UOS、openEuler | 已按国产化系统设计，需确认 glibc 版本 |
| ③ 数据库 | 达梦、人大金仓、openGauss、Vastbase、OceanBase、TiDB | 影响元数据库与向量库选型 |
| ④ 中间件 | Redis、Nginx 的国产替代 | 影响组件选型与许可证合规 |
| ⑤ 计算芯片 | 昇腾、寒武纪、海光 DCU | 影响模型推理与微调训练方案 |
| ⑥ 模型与框架 | 国产开源大模型、国产推理框架 | 影响模型选型与部署方式 |

## 2. 第一决定性因素：CPU 架构

### 2.1 三条路线的可行性对比

| 架构 | 代表产品 | 现有方案可用性 | 需补充工作 | 风险评估 |
| --- | --- | --- | --- | --- |
| **x86_64 兼容** | 兆芯 KX-7000、海光 C86 | ✅ **可直接使用** | 无 | 低 |
| **ARM64（aarch64）** | 飞腾 S2500 / FT-2000+、鲲鹏 920 | ⚠️ 需重新构建离线包 | 重出 aarch64 版本离线包 | **低**（各组件均已确认存在 aarch64 版本） |
| **LoongArch** | 龙芯 3A5000 / 3C5000 / 3D5000 | ❌ **不可用** | 自建 Python 运行时 + 逐个编译依赖包 | **高**（详见 2.3） |

### 2.2 ARM64 路线可行性论证（逐项已验证）

| 组件 | 是否具备 aarch64 版本 | 验证方式 |
| --- | --- | --- |
| 前端运行时（官方镜像产物） | ✅ 有 | 实测镜像清单同时包含 linux/amd64 与 linux/arm64 |
| 代码沙箱（官方二进制） | ✅ 有 | 实测镜像清单同时包含两种架构 |
| 便携 Python 运行时 | ✅ 有 | 实测发布物含 aarch64-unknown-linux-gnu 构建 |
| Python 依赖树 | ✅ 有 | 依赖安装工具明确支持 aarch64-manylinux_2_28 目标平台 |
| 插件守护进程 | ✅ 有 | 纯 Go 无 CGO，可交叉编译出 aarch64 静态二进制 |
| PostgreSQL / Redis / 系统调用过滤库 | ✅ 有 | 均为 C 源码，可在目标机本地编译 |
| 便携编译工具链（Go / zig） | ✅ 有 | 两者均提供 linux-aarch64 发行版 |

**结论**：ARM64 路线**技术上完全可行**，主要工作量是重新构建 aarch64 版本的离线包，
预计增加 3 至 5 个工作日（含回归验证）。

### 2.3 LoongArch 路线风险评估（重要）

| 风险点 | 实测依据 | 影响 |
| --- | --- | --- |
| **便携 Python 无 LoongArch 构建** | 实测发布物共 20 种架构（含 aarch64、riscv64、ppc64le、s390x），**不含 loongarch64** | 必须自行从源码构建 Python 运行时，并对齐所有标准库依赖 |
| **依赖树缺 LoongArch 轮子** | 依赖树含 801 个包，其中加密库、数值计算库、分词库、推理运行时等均含平台相关二进制扩展 | 需逐个从源码编译，部分包的 C/C++ 依赖链极深，工作量不可控 |
| **Node.js 官方无 LoongArch 构建** | Node.js 官方发布物不含 LoongArch | 需使用第三方移植版，稳定性与维护性存疑 |
| **上游无验证** | Dify 官方未提供 LoongArch 支持 | 遇到问题无社区参考 |

**建议**：若甲方允许在 ARM64 与 LoongArch 之间选择，**强烈建议采用飞腾或鲲鹏（ARM64）**，
可复用成熟的 aarch64 生态；若甲方强制要求 LoongArch，则需单独评估并追加工作量，
建议在项目启动阶段通过原型验证（POC）确认可行性后再签订进度承诺。

```
DB_TYPE = "postgresql" | "mysql" | "oceanbase" | "seekdb"
```

其中 **OceanBase** 与 **seekdb** 为国产产品（MySQL 协议兼容），**无需任何改造即可直接使用**。

| 候选 | 国产属性 | 支持方式 | 建议 |
| --- | --- | --- | --- |

## 7. 计算芯片与模型层

### 7.1 推理与训练芯片

| 芯片 | 生态 | 推理 | LoRA 微调 | 迁移难度 |
| --- | --- | --- | --- | --- |
| **华为昇腾 910B** | CANN + MindSpore / torch_npu | ✅ MindIE / vLLM-Ascend | ✅ 可行 | 中 |
| **寒武纪 MLU** | Cambricon PyTorch | ✅ 有对应推理方案 | ✅ 可行 | 中 |
| **海光 DCU** | ROCm 兼容生态 | ✅ | ✅ | **低**（CUDA 代码迁移成本最小） |
| 龙芯 + 国产加速卡 | 生态最弱 | ⚠️ | ⚠️ | 高 |
| NVIDIA（不可用于全国产化） | CUDA | ✅ | ✅ | 低 |

**结论**：模型微调在国产加速卡上**可行但需适配**。建议：
- 优先选择 **海光 DCU**（ROCm 兼容，迁移成本最低）；
- 其次 **昇腾 910B**（生态最成熟，但需使用昇腾版 PyTorch，训练脚本需适配）；
- 微调采用 **LoRA** 方案，显存需求低，单卡即可完成，降低对芯片算力的要求。

针对飞腾（ARM64）平台的离线部署包**已构建完成并通过兼容性校验**。

### 11.3 防错设计

两个架构的离线包均带有 `ARCH.txt` 架构标记，
安装脚本在执行任何变更之前会先比对标记与本机 `uname -m`：

- 拿错架构的包会**立即报错终止**，不会安装到一半才失败；
- 报错信息明确指出应该使用哪个版本的包。

### 11.4 飞腾平台需注意的事项

| --- | --- |
