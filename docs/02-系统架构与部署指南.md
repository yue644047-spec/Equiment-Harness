### 1.3 重要前提：为什么必须手工导入

Dify Cloud **不提供 Console API Token**（该 Token 仅私有化部署可用）。因此**不能**用脚本调用 Console API
创建应用与知识库，**必须**由人在 Dify 网页界面里导入 DSL、创建知识库、创建 API 密钥——本文档所有部署
步骤都按「人在浏览器里点」来写。Service API（`app-xxx` / `dataset-xxx`）Cloud 版提供，用于运行期
调用与数据拉取，**不用于建应用**。

### 1.5 关键术语

**DSL**：Dify 应用编排文件（YAML），本方案目标版本 0.7.0；**Chatflow / Workflow**：Dify 的
`advanced-chat` / `workflow` 应用模式，前者可多轮对话、后者单次输入输出，适合被 API 调用；
**Service API**：应用发布后对外提供的 `/v1/*` 接口，用 `app-xxx` 密钥鉴权；**数据集 / 知识库**：
Dify 的 dataset，用 `dataset-xxx` 密钥调用其 API；**回执**：用户发送「#评价 N 建议……」后 Chatflow
返回的评价确认文本；**CSI**：综合满意度指数，定义见 EVAL-SPEC-001；**装备域专项维度**：
`safety_compliance`（安全合规性 SC）、`version_currency`（版本时效性 VC）、`terminology_norm`（术语规范性 TN），
三者**不进入 CSI 权重**，以专项达标与红线方式参与 verdict 与 badcase 判定。

## 2. 系统总览

### 2.1 四层架构

系统分为四层，**自上而下**依次是 Dify 应用层、评价工作流层、本地评测服务层、数据层。关键在于：
**Dify 侧只负责产生数据与评分，本地服务负责拉取、落库、聚合、出报表与闭环**。

```text
┌─ 第 1 层 Dify 应用层（cloud.dify.ai）─────────────────────────────────────────┐
│  [01 智能问答助手 advanced-chat]  ←→  [知识库 Dataset：分段 / 索引 / 召回]     │
│   意图识别 ─┬─ 评价反馈分支（参数提取 → 回执 → 回复）                          │
│             └─ 知识问答分支（知识检索 → 是否空 → 作答 / 兜底）                  │
│   发布渠道：WebApp（用户） / Service API（本地评测服务）                       │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │ Service API：拉取会话 / 消息 / 反馈；调工作流
┌─ 第 2 层 评价工作流层（Dify，两个 workflow 应用）─────────────────────────────┐
│  [02 满意度评价与数据标注]  LLM 多维评分 → 代码算 CSI → csi/verdict/badcase    │
│  [03 语料标注与问答对抽取]  文档 → LLM 抽取 → 质检 → jsonl / 复核表            │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │ POST /v1/workflows/run（评分）；03 产物回灌知识库
┌─ 第 3 层 本地评测服务层（D:\app\dify\eval_service，Python，无需 Docker）──────┐
│  config.py 凭据 | dify_client.py API 客户端 | collector.py 采集与回执解析      │
│  judge.py 批量评分 | metrics.py CSI/verdict/badcase | store.py SQLite         │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │ SQLite 单文件 eval_service\data\eval.db
┌─ 第 4 层 数据层 ─────────────────────────────────────────────────────────────┐
│  conversations / messages / feedbacks / evaluations / badcases / runs         │
│  kb_docs（知识库文档与索引进度）；报表目录 eval_service\out\                   │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 数据流向（闭环七步）

| 步 | 环节 | 发生位置 | 触发方式 | 产物 |
| --- | --- | --- | --- | --- |
| ① | 用户问答 | Dify 应用层（01 Chatflow） | 用户在 WebApp 提问 | 会话 + 消息（含检索片段） |
| ② | 反馈采集 | Dify 应用层 | 点 👍/👎，或发送「#评价 4 建议…」 | `feedback_rating`；正文里的 `[[EVAL_RECEIPT]]` 回执 |
| ③ | 拉取 | 本地评测服务层 | `collector.collect_once()` | SQLite：conversations / messages / feedbacks |
| ④ | 多维评分 | 评价工作流层（02） | `judge.judge_once()` 并发调用 | result_json / csi / verdict / badcase / safety_compliance / version_currency / terminology_norm → evaluations |
| ⑤ | 指标聚合 | 本地评测服务层 | `metrics.aggregate()` | 均值、分位、分布、CSI 与用户评分相关系数 |
| ⑥ | 报表 | 本地评测服务层 | 报表生成（开发中） | `eval_service\out\` 下的明细 + 汇总报表 |
| ⑦ | 闭环改进 | 双向 | 人工 | badcase 归因 → 补知识 / 调分块 / 改提示词 / 换模型 |

闭环链路：`用户问答 → 反馈采集 → 拉取 → 多维评分 → 指标聚合 → 报表 → 闭环改进（补知识 / 调检索 / 改提示词）`，
其中 03 产出的问答对经人工复核后回灌知识库，形成下一轮的正向输入。

### 2.3 两条评价通道

| 通道 | 采集方式 | 用户成本 | 数据落点 | 覆盖信息 |
| --- | --- | --- | --- | --- |
| A：原生反馈 | 回答下方的 👍 / 👎 | 极低 | `messages.feedback_rating` = `like` / `dislike` | 只有极性，无理由 |
| B：对话内评价指令 | 发送「#评价 4 希望补充XX说明」 | 需打字 | 回答正文中的 `[[EVAL_RECEIPT]]` 回执 | 1–5 分 + 文字建议 |

**通道 B 的链路**（本系统相对普通 Dify 问答的关键设计）：用户发 `#评价` 或自然语言评价 →
「意图识别」（question-classifier）分到 `满意度评价` 类 → 「提取评分与建议」（parameter-extractor）
抽出 `score` 与 `suggestion` → 「评价回执」（template-transform）生成带标记的确认文本 →
「回复评价回执」（answer）返回用户。

回执标记的**精确格式**（以 DSL 文件为准）：

```text
[[EVAL_RECEIPT]]score={{ score }},suggestion={{ suggestion }}[[/EVAL_RECEIPT]]
例如实际输出：[[EVAL_RECEIPT]]score=4,suggestion=希望补充滤芯更换周期的说明[[/EVAL_RECEIPT]]
```

> ✅ **格式约定（已对齐，勿随意改动）**：回执采用**键值对**而非 JSON，原因是 Jinja2 模板无法对用户
> 建议做 JSON 转义——建议里的引号或换行会把 JSON 打碎。`eval_service\collector.py` 的
> `parse_eval_receipt()` **同时支持三种写法**：规范键值对
> `[[EVAL_RECEIPT]]score=N,suggestion=…[[/EVAL_RECEIPT]]`；历史 JSON
> `[[EVAL_RECEIPT]]{"score":N,"suggestion":"…"}`；以及人类可读回退（正文中的
> 「满意度评分：N / 5」）。**改 Dify 回执模板时必须同步改 `collector.py`**，否则通道 B 断链。

### 3.4 数据表清单（SQLite，共 7 张）

| 表（主键） | 一行代表 | 关键字段 |
| --- | --- | --- |
| `conversations`（conversation_id） | 一个会话 | name、created_at、from_end_user_id、annotated |
| `messages`（id） | 一问一答 | query、answer、feedback_rating、retriever_resources_json、receipt_score、receipt_suggestion、user_score_raw、user_score |
| `feedbacks`（id） | 一条原生反馈 | message_id、rating、content、from_source |
| `evaluations`（message_id） | 一条评价结果 | 五个维度分、safety_compliance、version_currency、terminology_norm、csi、verdict、annotation_label、error_cause、badcase、result_json |
| `badcases`（message_id） | 一个坏例 | severity（P0 / P1 / P2）、reasons_json、safety_compliance、version_currency、terminology_norm |
| `runs`（run_id） | 一次运行 | kind（collect / judge / report / badcase / regression / kb-build）、status、stats_json |
| `kb_docs`（doc_id） | 一篇知识库文档 | dataset_id、source_path、content_hash、segment_count、status、batch |

> `store.py` 的 `SCHEMA_VERSION` 现为 `"2"`：`evaluations` 与 `badcases` 各新增
> safety_compliance / version_currency / terminology_norm 三列，`_migrate()` 用 `ALTER TABLE`
> 为旧库自动补列，**升级后无需删库重建**（见 9.1 第 20 条的验证方法）。

### 4.2 工作区需安装并授权 DeepSeek 插件

三个应用的所有 LLM 节点都指向同一个供应商标识与模型名，**插件没装或没授权，应用一律跑不起来**。

| 项 | 值 |
| --- | --- |
| 插件名称 | DeepSeek |
| 供应商标识（provider） | `langgenius/deepseek/deepseek` |
| 默认模型名（model） | `deepseek-flash` |
| 可选升级模型 | `deepseek-v4-pro`（用于「多维度评分」等对判断力要求高的节点） |
| 安装路径 | Dify 右上角头像 → **设置** → **模型供应商** → 搜索 `DeepSeek` → **安装** → 填入 API Key → **保存** |
| 验证方式 | 安装后列表中 DeepSeek 显示为**已授权**，展开可见模型列表 |

> 插件为工作区级资源，同一工作区下三个应用共享该授权；换工作区需重新安装授权。

### 5.2 模型选型建议

- **全部保持 `deepseek-flash`**：01 的四个节点（二分类、结构化抽取、高频作答与兜底）低温度、快、便宜，
  是成本最优解；若 01 答非所问率偏高，可只把「基于知识库作答」换成更强模型。
- **02 的「多维度评分（LLM 评委）」建议换 `deepseek-v4-pro`**：评委质量直接决定指标可信度。
- **03 的「问答对抽取与标注」**：文档长、量大时用 `deepseek-flash`，质量要求高时用 `deepseek-v4-pro`。

> 选型变更只影响质量与成本，**不影响接口契约**（输入输出字段名不变）。

### 5.3 换模型的三步操作（OpenAI / 通义千问 / 智谱等）

前提：目标供应商的插件已在 **设置 → 模型供应商** 中安装并授权。

- **第一步 点开 LLM 节点**：在「工作室」打开对应应用 → 进入画布 → **单击要改的节点**
  （如 01 的「基于知识库作答」、02 的「多维度评分（LLM 评委）」）→ 右侧弹出节点配置面板。
- **第二步 重新选择模型**：在面板顶部点击**模型选择器**（当前显示 `deepseek-flash`）→ 展开后先在左侧选
  **供应商**（OpenAI / 通义千问 / 智谱 AI 等）→ 再选具体**模型**（如 `gpt-4o-mini` / `qwen-plus` /
  `glm-4-flash`）。**温度、top_p 等参数保持不变**（意图识别与评分节点务必保持 temperature = 0），否则指标会漂移。
- **第三步 保存并发布**：点击画布右上角 **发布** → **发布更新**。修改未发布时只对当前调试生效，
  **Service API 调用的仍是旧版本**。

**逐个节点核对清单**（换供应商时容易漏）：

| 应用 | 需要改的节点 |
| --- | --- |
| 01 智能问答 | 意图识别、提取评分与建议、基于知识库作答、知识未覆盖兜底（共 4 个） |
| 02 满意度评价 | 多维度评分（LLM 评委）（共 1 个） |
| 03 语料标注 | 问答对抽取与标注（共 1 个） |
| 知识库 | Embedding 模型、Rerank 模型（在知识库设置里，不在画布上） |

**换模型后的三条注意事项**

1. **结构化输出稳定性**：02 与 03 依赖模型只输出干净 JSON。换到较弱模型后若代码节点频繁走到「解析为空」分支，
   应回退模型或在提示词中加强 JSON 约束。
2. **提示词措辞**：部分模型对「只输出 JSON，不要 Markdown 代码块」的遵循度不同，必要时在提示词末尾追加
   「禁止输出 json 代码块标记」。
3. **重新校准**：更换评委模型后 CSI 的绝对水平会变，请在试运行期重新校准阈值，**不要把新旧模型的分数直接比较**。

Dify 网页界面完成，**不涉及 Console API**。

### 6.1 创建知识库

1. 登录 <https://cloud.dify.ai> → 顶部导航点击 **知识库**，进入数据集列表页；
2. 点击左上角 **创建知识库** → 选择 **导入已有文本**（从本地文件导入）或 **创建一个空知识库**；

| 项 | 要求 |
| --- | --- |

| 密级标注 | 上传前逐份确认语料的密级标识（公开 / 内部 / 秘密等），并与《装备技术资料清单与版本台账》（HYS-ZL-005）的登记一致；**未定级资料不得入库** |
| 涉密不入云 | 涉密或敏感资料**默认不上传 Dify Cloud**；确需使用时先按本单位保密规定脱敏、降密，或改用经批准的本地化部署，并**单独建库隔离** |
| 访问控制 | 知识库只在**一个工作区**内维护，成员按最小必要授权；`dataset-xxx` 密钥只发给实施与运维角色，禁止跨项目复用（见 Step 5） |

其中 `8f3a1c2e-5b7d-4e91-a0c6-2d9f4b7e1a33` 就是知识库 ID。也可以直接运行（推荐，一次列出所有知识库及其 ID）：

### 6.2 分段设置（装备技术资料专用规则）

上传文档时，在**分段设置**页选择 **自定义**，按下表填写：

| 参数 | 推荐值 | 说明 |
| --- | --- | --- |
| 分段标识符 | 按条款编号切分：`\n(?=\d+(\.\d+)+)`（如 `4.3.2`）；再叠加标题层级 `\n### `、`\n#### `，空行 `\n\n` 只作兜底 | 装备资料以「章 - 节 - 条款」组织，**按条款编号切分**才能保证一条要求（一条安全前置、一条力矩要求）完整落在一段内 |
| 分段最大长度 | **600** tokens | 装备资料的条款含参数表与安全前置条件，本身自解释；比通用文档类分段略大，避免把「前置条件 + 操作步骤」切成两段 |
| 分段重叠长度 | **80** tokens | 约为最大长度的 13%，保证跨段引用的资料编号、版本号、条款号与上一段的结论不被切断 |
| 文本预处理规则 | 替换连续空格 / 换行符与制表符；删除 URL 与邮箱（可选，不影响数值）；**任何会删除、改写或合并数字的规则一律关闭** | 装备资料的价值主要在数字（压力、力矩、周期、温度），预处理不得改动数值与单位 |
| 分段数量上限 | 默认即可 | — |

**装备资料分段四条硬规则**（不满足会直接拉低 FA / KC，甚至触发安全红线）：

1. **按条款编号切分**：以 `4.3.2`、`7.2.7` 这类条款号作为第一优先边界，标题层级作为第二优先边界，
   空行只作兜底；**一条条款不得横跨两个 segment**。
2. **资料编号与版本号必须留在段内**：每段正文（或段首）要保留 `HYS-WX-003 V2.0` 这样的
   资料编号 + 版本号（语料已内嵌，分段时**不要**把它切到上一段去）；否则回答无法标注引用来源，
   `version_currency` 专项维度会直接掉档。
3. **表格不跨段**：参数表（滤芯更换周期表、保养周期表、螺栓力矩要求等）整表必须落在同一段内；
   若分段标识符把 `|` 表格行拦腰切开，应把表格前后的空行从标识符中移除，或改为「按条款号 + 表格前后各留一行」的切法。
4. **每段自解释**：读到任一片段应能独立回答「哪台装备、哪份资料、哪一版、什么要求」；
   段落不得以「同上」「见前条」「如下表」开头而没有上文。

**何时需要调参**

| 现象 | 调整方向 |
| --- | --- |
| 召回片段答非所问（噪声大） | 最大长度下调至 400–500，或**开启 Rerank**（装备域强烈建议，见 6.4） |
| 回答总是缺半边信息（安全前置条件丢失） | 最大长度上调至 800，或把重叠调到 100，并核对是否按条款编号切分 |
| 表格 / 参数表被切碎 | 检查分段标识符是否命中 `|` 行，改为按条款编号切分 |
| 同一主题召回出两个版本的数值 | 多半不是分段问题，而是**作废版本资料入库**：按 6.6 清除作废版本 |

### 6.3 索引方式：高质量 vs 经济

| 索引方式 | 原理 | 检索质量 | 成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| **高质量** | 调用 Embedding 模型把分段向量化，支持向量检索 + 全文检索 + Rerank | 高 | 有 Embedding 调用费用与时间 | **推荐**。装备技术资料问答、规程条款与参数检索 |
| **经济** | 仅关键词（倒排）索引，不做向量化 | 较低，依赖字面匹配 | 近乎为零 | 文档量很大且预算极紧、或只需关键词命中 |

> **本系统推荐「高质量」**：01 的回答质量直接决定满意度指标的分布，索引质量是其中最便宜的一环。若选
> 「经济」，需在 EVAL-SPEC-001 的基线里标注该差异，否则 CSI 会被系统性拉低。

### 6.4 Embedding 与 Rerank 模型建议

| 模型类型 | 建议 | 备注 |
| --- | --- | --- |
| Embedding（必选） | 中文效果好的多语 / 中文向量模型（如已授权的 `bge-m3`、`text-embedding-3-large`、通义 `text-embedding-v*`） | **「高质量」索引必须选择**；索引完成后**更换 Embedding 需重建索引** |
| Rerank（**装备域强烈建议开启**） | 支持中文的重排模型（如 `bge-reranker-v2-m3`、`gte-rerank`） | 装备资料**参数密集、术语相近**：额定工作压力 16 MPa / 溢流阀开启压力 17.5 MPa / 最高允许压力 18 MPa，一级 / 二级 / 三级保养 250 / 1000 / 4000 工作小时——纯向量召回极易把相近条款排到前面；Rerank 能显著提升 top_k 片段的相关性，代价是每次检索多一次调用 |
| 检索参数 | 01 的「知识检索」节点为 `top_k = 6`、未启用 `score_threshold`、**`reranking_enable = false`（仓库 DSL 的默认值）** | **部署时必须开启 rerank**：在画布点开「知识检索」节点 → 打开 **Rerank 模型** 开关并选择已授权的重排模型；不要为了开启它去手改 DSL 文件 |

> **关于 `reranking_enable` 默认关闭**：本仓库 `dsl\01-多模态智能问答-Chatflow.yml` 中该值为 `false`，
> 目的是让 DSL 在任何工作区**导入即可运行**（工作区未授权 Rerank 模型时开启会导致节点报错）。
> **部署到真实知识库时必须开启**，并在开启前后各做一次**召回测试**对比 top_k 片段的相关性。
>
> Embedding 与 Rerank 模型都需在 **设置 → 模型供应商** 安装授权后才会出现在知识库选项中。
>
> **本交付的完整产品（`platform/`，端口 8095）自带一路本机重排**：`platform/rerank_server.py`
> 把 `BAAI/bge-reranker-v2-m3` 交叉编码器暴露成 OpenAI 兼容的 `/v1/rerank`（默认
> `http://127.0.0.1:8196/v1`，用 `启动重排服务.bat` 起）。产品按「模型角色 · rerank」接入它：
> 先按 `top_k × RERANK_CANDIDATE_FACTOR`（默认 4）放大召回并把阈值放宽到 `min(阈值, 0.1)`，
> 再由重排模型逐条打分排序；`RERANK_MODE=off` 可一键关回纯混合检索，重排服务不可用时检索
> **自动回落**而不是报错。口径与实测见 `docs/16` ADR-D53。

### 6.6 资料元数据与版本台账

装备技术资料最致命的风险是**引用已作废版本的数值**（例如滤芯更换周期旧值 **300 工作小时**、
额定压力旧值 **14 MPa**）。因此除正文语料外，**必须上传《装备技术资料清单与版本台账》**
（`samples\05-装备技术资料清单与版本台账.md`，HYS-ZL-005 V1.0，2025-06-01）。

**四个元数据字段的作用**（每份资料、每个分段都应能对应到这四个值）：

| 字段 | 取值示例 | 作用 |
| --- | --- | --- |
| 资料编号 | `HYS-WX-003` | 唯一标识一份技术资料；回答引用时必须写出编号，便于资料员与使用人员回查原文 |
| 版本 | `V2.0` | 与编号组合才能定位到**具体一版**；同一编号多版本并存是最大的混淆来源 |
| 发布日期 | `2024-09-20` | 版本新旧的判据；与作废记录比对得出「现行有效」结论 |
| 现行状态 | 现行有效 / 已作废 | **决定该资料能否作为作答依据**；作废资料只能用于说明「已停用」 |

**版本台账与作废版本处置**

| 项 | 要求 |
| --- | --- |
| 台账入库 | HYS-ZL-005 必须上传，且**不得分段切碎表格**（见 6.2 硬规则 3）；台账是判定「哪一版现行有效」的唯一依据 |
| 作废版本不得入库 | 已作废的 **HYS-CZ-002 V3.0**（2021-05-10，滤芯周期旧值 **300 工作小时**）与 **HYS-GY-001 V2.0**（2019-07-22，额定压力旧值 **14 MPa**）**禁止上传到知识库**；如因历史对比必须保留，应单独建库或在文件名加 `作废-` 前缀，并在正文首行注明「本版本已作废，不得引用」 |
| 同一编号只保留一版 | 同一资料编号在库内只允许存在一个**现行有效**版本；升版时先删旧文档、再传新文档，避免同时召回两个版本的数值 |
| 作废值识别特征 | 出现 **300 工作小时**（滤芯更换周期）、**14 MPa**（额定压力）即高度可疑，按 9.1 第 16 条排查 |
| 上传与升版留痕 | 每次入库 / 换版在 `kb_docs` 表与本单位资料台账中同步登记：谁、何时、传了哪份、换成了哪一版 |

**元数据过滤（metadata filtering）建议配置**

Dify 知识库支持为文档设置元数据并在检索时按元数据过滤。装备域建议按下列三个键配置：

| 元数据键 | 建议取值 | 用途 |
| --- | --- | --- |
| 资料类别 | 原理 / 操作规程 / 维修规程 / 故障案例 / 资料管理 / 术语 | 提问意图明确时（如「怎么更换滤芯」→ 规程类）只在该类别内检索，降低跨类噪声 |
| 适用型号 | HYS-1（示例装备代号） | 库内混入其它型号资料时**必须过滤**，避免把其它型号的参数与规程套用到本装备（对应 `error_cause = 型号适配错误`） |
| 现行状态 | 现行有效 / 已作废 | 日常问答**只检索「现行有效」**；作废版本仅在用户明确询问版本沿革时才允许召回 |

> 元数据过滤是**降低版本类与型号类错误的最后一道闸门**，但不能替代本节开头的入库清理：
> 元数据填错等于没过滤，上传时必须逐份核对资料编号 / 版本 / 发布日期 / 现行状态四个字段。

### Step 6：把四个变量写入 `C:\Users\Administrator\.env`

**四个变量**

| 变量 | 含义 | 示例形态 |
| --- | --- | --- |
| `DIFY_BASE_URL` | Dify 服务地址 | `https://cloud.dify.ai` |
| `DIFY_APP_API_KEY` | 01 问答应用的密钥 | `app-xxxx` |
| `DIFY_EVAL_API_KEY` | 02 评价工作流的密钥 | `app-xxxx` |
| `DIFY_KB_API_KEY` | 知识库密钥 | `dataset-xxxx` |

**方式一（推荐）：隐藏回显逐条写入**

在 PowerShell 中逐条执行。`Read-Host -AsSecureString` 保证**输入时不回显**，
屏幕上不会出现密钥明文；最后把内容追加到 `.env`。

```powershell
# 0) 确认 .env 路径与父目录
$envPath = "C:\Users\Administrator\.env"
Test-Path (Split-Path $envPath -Parent)

# 1) Dify 地址（非敏感，直接写）
Add-Content -Path $envPath -Value "DIFY_BASE_URL=https://cloud.dify.ai" -Encoding UTF8

# 2) 写入函数：隐藏回显 + 立即落盘 + 变量清零
function Set-EnvSecret {
    param([string]$Name, [string]$Prompt)
    $secure = Read-Host $Prompt -AsSecureString
    $ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
    try {
        $plain = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
        Add-Content -Path $envPath -Value ("{0}={1}" -f $Name, $plain) -Encoding UTF8
        Write-Host ("[OK] {0} 已写入（长度 {1}）" -f $Name, $plain.Length) -ForegroundColor Green
    }
    finally {
        [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
        $plain = $null
        Remove-Variable secure -ErrorAction SilentlyContinue
    }
}

# 3) 逐条执行（回车后粘贴密钥，屏幕不回显）
Set-EnvSecret -Name "DIFY_APP_API_KEY"  -Prompt "粘贴 01 问答应用密钥 (app-...)"
Set-EnvSecret -Name "DIFY_EVAL_API_KEY" -Prompt "粘贴 02 评价工作流密钥 (app-...)"
Set-EnvSecret -Name "DIFY_KB_API_KEY"   -Prompt "粘贴 知识库密钥 (dataset-...)"
```

> **若 `.env` 已存在同名变量**，`Add-Content` 会产生重复行。执行前先清理旧行：
>
> ```powershell
> $envPath = "C:\Users\Administrator\.env"
> if (Test-Path $envPath) {
>     $keep = Get-Content $envPath | Where-Object {
>         $_ -notmatch '^\s*(DIFY_BASE_URL|DIFY_APP_API_KEY|DIFY_EVAL_API_KEY|DIFY_KB_API_KEY)\s*='
>     }
>     Set-Content -Path $envPath -Value $keep -Encoding UTF8
> }
> ```
>
> 备选做法：把四行 `KEY=VALUE` 一次性用 `Read-Host -AsSecureString` 读入后
> `Add-Content` 追加（同样不回显），适合已有整理好的密钥清单。

**写入后自查（只显示掩码，不显示明文）**

```powershell
$envPath = "C:\Users\Administrator\.env"
Get-Content $envPath | ForEach-Object {
    if ($_ -match '^\s*(DIFY_[A-Z_]+)\s*=\s*(.*)$') {
        $k = $Matches[1]; $v = $Matches[2].Trim()
        if ($v.Length -gt 10) { $m = $v.Substring(0,6) + "****" + $v.Substring($v.Length-4) } else { $m = "(空)" }
        "{0,-20} {1}" -f $k, $m
    }
}
```

**文件权限收紧（仅当前用户可读）**

```powershell
$envPath = "C:\Users\Administrator\.env"
icacls $envPath /inheritance:r
icacls $envPath /grant:r "$($env:USERNAME):(R,W)"
```

> 🔒 **纪律要求**：密钥**只**写入 `.env` 或密码管理器。
> 不要把密钥贴到聊天窗口、群消息、截图、工单系统或任何代码仓库里。
> 如果不慎泄露：立即到 Dify 的 **访问 API → API 密钥** 里**删除该密钥并重建**，然后更新 `.env`。

#### 8.3 造数与观察要点

无真实数据时，在 WebApp 里手工造 10–20 条数据（覆盖正常 / 知识缺失 / 错误 / 版本陷阱四类），逐条观察：

  不出现「未收录」话术；
- 问**带版本陷阱**的问题（如「按 HYS-CZ-002 V3.0，滤芯更换周期是 300 工作小时吗？」）→ 必须拒绝作废
  版本数值，并给出现行值（HYS-CZ-002 V4.0：每 500 工作小时或 12 个月，以先到为准）；
- 问**涉及安全前置**的问题（如「如何更换滤芯？」）→ 必须给出停机 → 切断电源并挂牌上锁 → 系统泄压至
  0 MPa → 机械支撑稳固 → 油温降至 45 ℃ 以下五步，缺一步即应被判 `safety_compliance <= 2`；
- 问**知识库里没有**的问题 → 走兜底分支，开头必须是「当前知识库未收录与该问题直接相关的内容。」；
- 点一次 👍 再点一次 👎 → 第二次覆盖第一次，`messages.feedback_rating` 最终为 `dislike`；
- 发送 `#评价 4 希望补充滤芯更换周期的说明` → 回复含「✅ 已记录你的评价」与末尾 `[[EVAL_RECEIPT]]` 标记。

> 更完整的造数清单见 `samples\冒烟测试问题清单.md`（22 道题，含 6 道陷阱题），
> 每题都写明了期望答案要点与验证点（数值准确性 / 版本 / 安全前置 / 术语 / 参数取整）。

也可跳过 01，直接用 `POST /v1/workflows/run` 给 02 传一组 question / answer，单独验证评分工作流。

| # | 检查项 | 怎么查 | 通过标准 | 不通过的后果与补救 |

| 3 | 意图识别是否命中 | 调试面板依次发三种输入，看「意图识别」的分支走向 | `#评价 4 希望补充XX` → 满意度评价；「滤芯多久需要更换一次」→ 知识问答；「这个回答不对」→ 满意度评价 | 评价语被当普通问题检索，回执不产生、通道 B 全丢；在「类别」里补示例或改写 `instruction`，确认 temperature = 0 |
| 4 | 回执是否含 `[[EVAL_RECEIPT]]` 标记 | 发 `#评价 4 测试建议`，**展开回复原文**（不是看渲染结果） | 末尾出现 `[[EVAL_RECEIPT]]score=4,suggestion=测试建议[[/EVAL_RECEIPT]]` | 采集器抓不到分数与建议；点开「评价回执」节点（`1700000000004`）确认 `template` 末尾标记未改动。⚠️ 该标记当前为键值对格式，与 `collector.py` 的 JSON 正则不一致，见 2.3 |

### 9.1 排查速查表

## 10. 安全与合规

### 10.1 密钥管理

| 要求 | 做法 |
| --- | --- |
| 唯一存放位置 | `C:\Users\Administrator\.env` 或企业密码管理器；**不写入代码、DSL、工单** |
| 禁止传播 | 不贴到聊天窗口、群消息、截图、文档正文；本文档全文**不含任何真实密钥** |
| 权限收紧 | 用 `icacls` 移除继承，仅授权当前用户读写（见 Step 6） |
| 分权原则 | 问答应用、评价工作流、知识库使用**独立密钥**，便于按需吊销、定位来源、分别限流 |
| 轮换周期 | 建议 **90 天**轮换一次；人员离职或交接后**立即轮换** |
| 泄露处置 | 立即在 Dify 侧**删除该密钥并重建** → 更新 `.env` → 用 `check_env.py check` 复验 → 检查 `runs` 表近 24 小时的异常调用 |
| 日志卫生 | 客户端与自检工具只输出**掩码**（形如 `app-abc****wxyz`）；贴日志求助前先确认无明文密钥 |

### 10.2 用户数据脱敏

评价流水线会把用户的**原始提问与回答**落库，这是合规风险最集中的环节。核心原则：**能算指标就不留原文；
必须留原文时，限制访问权限并设定留存期。**

| 数据类型 | 风险 | 处理要求 |
| --- | --- | --- |
| 提问中的个人信息 | 用户可能在问题里粘贴姓名、手机号、身份证号、工号 | 入库前对 `messages.query` 做正则脱敏（手机号 / 身份证 / 银行卡 / 邮箱），或对敏感资料整条排除 |
| 回答中的个人信息 | 知识库文档若含人名与联系方式，回答会带出来 | 知识库文档上传前脱敏（见 6.5 入库前自查） |
| 反馈建议原文 | `suggestion` / `feedback_content` 可能含个人信息 | 进入报表前脱敏；badcase 导出时以 **ID + 哈希** 替代原始文本 |
| 用户标识 | `from_end_user_id` 可用于关联个人行为 | 落库时**哈希化**（如 SHA-256 加盐），报表只展示哈希前 8 位 |
| 检索片段 | `retriever_resources_json` 含知识库原文 | 与知识库文档同等级别保护，不导出到个人终端 |

### 10.3 评价数据留存期限建议

| 数据 | 建议留存期 | 理由 | 到期动作 |
| --- | --- | --- | --- |
| 原始会话与消息（含提问 / 回答原文） | **90 天** | 满足 badcase 复盘与回归评测需要，又不过度积累个人信息 | 归档后删除原文，仅保留指标与哈希 ID |
| 用户反馈原文（`feedbacks.content`） | **180 天** | 改进建议需要较长周期跟踪落地情况 | 汇总进改进台账后删除原文 |
| 评价结果（`evaluations` 六维分 + CSI） | **长期（≥ 2 年）** | 不含个人信息，是趋势分析与验收的核心证据 | 保留，按季度归档 |
| badcase 明细 | **180 天** | 整改闭环通常在一个季度内完成 | 标注处理结论后删除原文，保留分级与原因 |
| 装备技术资料文档与分段 | 与该资料版本的**现行状态**一致 | 作废版本会直接污染回答质量（版本失效类 badcase，P1） | 资料版本作废时同步下架文档，并更新 6.6 的版本台账 |
| 运行日志（`runs`） | **1 年** | 审计与问题追溯 | 保留汇总，清理明细 |
| 报表产物（`eval_service\out\`） | **1 年** | 汇报与验收留档 | 年度归档后清理 |

**合规要点**：**告知与同意**——试用前告知「问答内容与评价会用于服务改进」（01 的开场白已含引导语）；
**最小必要**——只采集 `question / answer / contexts / user_score / suggestion / meta`，不采集 IP、设备；
**可删除**——用户要求删除时凭 `from_end_user_id` 哈希值定位并物理删除相关行；**不得外传**——评价数据
仅限本单位内部使用，不得上传第三方平台做二次训练；**模型侧合规**——确认供应商数据使用条款（是否用于训练），
必要时改用本单位已审批的模型供应商。

### 10.4 资料密级管理与参数准确性责任

**资料密级管理**（对应 6.1 的建库要求）

| 要求 | 做法 |
| --- | --- |
| 先定级后入库 | 上传前逐份确认语料的密级标识（公开 / 内部 / 秘密等），与《装备技术资料清单与版本台账》（HYS-ZL-005）的登记一致；**未定级资料不得入库** |
| 涉密不入云 | 涉密或敏感资料**默认不上传 Dify Cloud**；确需使用时先按本单位保密规定脱敏、降密，或改用经批准的本地化部署，并**单独建库隔离** |
| 访问最小化 | 知识库只在**一个工作区**内维护，成员按「谁需要谁可见」授权；`dataset-xxx` 密钥只发给实施与运维角色，禁止跨项目复用（见 Step 5 与 10.1） |
| 台账与留痕 | 每次上传 / 换版 / 下架在**知识库文档列表**、**单位资料台账**与项目 `kb_docs` 表**三处**同时留痕（谁、何时、哪份、哪版） |
| 作废版本下架 | 资料升版后**立即下架旧版本**（见 6.6）；作废版本留在库里等于给回答埋下版本失效风险 |
| 评价数据不外流 | 会话原文与评价结果仅限本单位使用，不得上传第三方平台做二次训练（见 10.2） |

**参数类回答的准确性责任**

- **系统定位是辅助查阅**：回答只依据知识库中的**现行有效**资料，并引用**资料编号 + 版本号 + 条款号**；
  它不构成现场作业指令，现场作业必须以**正式签发的现行有效技术资料**为准。
- **数值不得改写**：压力、力矩、周期、油温油压阈值、负载限值等参数必须与原文**逐字一致**，
  禁止换算、取整、单位替换或「约等于」式表述；出现即 `factual_accuracy <= 2`，按 **P0** 处理。
- **安全条款不得省略**：涉及操作、维修、拆装与应急处置的回答，必须完整保留资料原文的安全警示与禁止事项；
  遗漏关键安全前置条件（泄压、挂牌上锁、机械支撑、机械安全销）判 `safety_compliance <= 2`，
  **verdict 直接判「不合格」**，并作为 P0 badcase **24 小时内**修复。
- **版本责任**：回答涉及版本时必须给出现行有效版本；引用已作废版本数值且未提示的判 `version_currency = 1`，
  verdict 最多「待改进」，按 **P1（本周内）** 整改。
- **术语责任**：缩略语首现应给出中文全称，同一部件前后用词一致；`terminology_norm <= 2` 计入 badcase，
  按 **P2（排期）** 整改，避免因术语歧义导致误操作。
- **责任边界**：CSI 与装备域专项维度用于衡量**回答质量与资料完备性**，不替代技术责任人的审签；
  参数类回答若与正式资料冲突，**一律以正式资料为准**，并立即按第 9 章流程排查知识库版本与分段。
